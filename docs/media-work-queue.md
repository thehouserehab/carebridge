# 사진·영상 검사 작업 큐와 재시작 복구

2026-10-05. 개편안 P1의 파일 전달 후속. 파일 수신/검사와 같은 PostgreSQL에 작업을 보관하고, 명시적으로 실행한 작업자가 기존 비공개 저장·격리 준비·권한 기반 후보 제공 경로를 재사용한다. **API·화면 서버 연결·운영 자동 시작·공개 배포·유료 자원·실제 아동 파일은 활성화하지 않았다.** 전체 개편안과 국내 운영 준비는 여전히 진행 중이다.

## 현재 동작

```text
원본 수신 완료 + queued 등록: 하나의 DB 트랜잭션
  → 명시적 작업자: 잔존 디코더 회수 → 만료 파일/임대 유지보수
  → 실행 가능한 대화방 잠금(SKIP LOCKED)
  → 저장된 원 소유자의 현재 관계/계정/과거 열람 범위 재확인
  → inspecting + 별도 후보 intent + running/동일 임대: 하나의 트랜잭션
  → 기존 원본 검사·격리 전체 처리·후보 검사·비공개 저장/해시 재조회
  → 불변 증거 + ready + completed: 하나의 트랜잭션
```

원본 첨부 ID·manifest·권한과 기존 기록/피드백/공유 연결은 보존한다. 큐 등록/검사로 메시지·임상 기록을 자동 만들지 않는다. 공유용 후보가 손상되면 원본으로 우회하지 않는 013 규칙도 유지한다.

## 상태와 재시도

| 큐 상태 | 의미와 다음 행동 |
| --- | --- |
| queued | 원본 수신이 확정됐으며 자동 처리 의도가 DB에 존재한다. 메모리 이벤트/알림 유실로 누락되지 않는다. |
| running | 업로드 검사와 동일한 임대 ID·만료·버전으로 한 번의 시도를 시작했다. |
| retry | IO/검사 장애 또는 만료된 작업 회수 후, DB 시각 기준 1·2·4·8초 대기 후 다시 선택한다. |
| completed | 기술적 파일 ready 또는 정확한 탐지의 rejected. 성공한 파일의 후속 바인딩·취소와 별개로 처리 당시 결과를 보존한다. |
| blocked | 5회 시도 후 보류. 자동·기존 수동 검사 모두 여섯 번째 시도를 거부한다. 원본을 임의 삭제하거나 재승인하지 않는다. |
| cancelled | 사용자가 취소했거나 비연결 임시 파일이 만료됐다. 늦은 작업은 임대/버전과 파일 fence로 거부한다. |

재시도마다 다른 후보 키와 임대를 만든다. 업로드 ID/발신 ID를 새로 만들어 중복 전송하는 방식이 아니다. 기존 소유자의 **명시적 수동 검사 재시도**는 대기 시간보다 먼저 할 수 있지만 5회 한도는 공유한다. 보류 작업의 관리자 검토/재개 화면과 승인된 재처리 정책은 아직 제공하지 않는다. 보류 원본은 기존 임시 보관 기한까지 유지하고, 사용자는 기존 취소 경로를 이용할 수 있다.

큐는 `cb_media_work_queue`에 식별자·원본 객체 참조·횟수·불투명 임대·시각·고정 실패 코드만 저장한다. 파일명·바이트·임상 텍스트·검사 원문·비밀번호/세션 토큰은 넣지 않는다. `source_key`도 내부 접근 식별자이므로 공개 응답/로그에 내보내지 않는다.

## 동시성·권한·복구

- 기존 방 → 참여자/소속/계정 → 업로드 → 큐 잠금 순서를 유지한다. 방이 잠겨 있으면 `SKIP LOCKED`로 다른 아이의 작업을 진행한다. 조회 snapshot의 버전을 신뢰하지 않고 잠금 후 현재 파일/큐 상태와 실행 시각을 다시 확인한다.
- `Conversations.inRoomTransaction`으로 기존 현재 권한 검사를 한 트랜잭션에서 재사용한다. 큐의 eligibility JOIN은 선택 최적화일 뿐 권한 승인 경로가 아니다. 입력에서 대상 사용자의 역할·세션·저장 키를 받지 않는다.
- 원 소유자의 계정/소속이 정지됐거나 담당 관계/열람 시작점이 바뀌면 선택하지 않는다. 처리 중 권한이 해제돼도 최종 `ready`를 확정하지 않는다. 그러한 원본은 임의로 다른 치료사에게 넘기지 않으며 기존 임시 기한/유지보수로 회수한다.
- 강제 종료로 `running/inspecting`이 남으면 새 인스턴스가 자연 임대 만료 후 후보를 차단/회수하고 retry로 전환한다. 디코더의 불확실한 생성/종료는 **먼저** `recoverRetained`로 확인하며, 해결되지 않으면 새 업로드 시도를 소비하지 않는다.
- DB 커밋 응답이 유실되면 다른 인스턴스가 파일/큐의 실제 상태를 읽는다. 이미 `ready/completed`인 작업을 다시 실행하지 않는다. 저장된 불변 증거도 중복 생성하지 않는다.
- graceful stop은 AbortSignal로 현재 검사를 취소하고 격리 종료/정리 또는 보류 판정과 DB 정산을 기다린다. `start`가 먼저 반환하고 이전 작업을 뒤에서 계속 수행하는 방식이 아니다.

## 실행 경계

`server/media-work-queue-worker.mjs`의 `MediaWorkQueueWorker`는 생성만으로 실행되지 않는다. 내부 `runOne({ signal })`은 한 건을 처리하고, `start({ signal })`은 명시적 중단 신호와 50~60000ms 범위의 polling으로 실행한다. 운영 모드의 기본 생성자는 **실제 일치하는 `DecoderJobJournal`이 있는 준비 서비스**를 요구한다. `localTestMode:true`는 선언된 합성 시험에서만 사용한다. 이 옵션을 요청/브라우저에서 받거나 운영 구성에 넣으면 안 된다.

아직 운영 CLI·서비스 관리자/systemd·자동 재시작·모니터링 경보는 설치하지 않았다. 각 프로세스는 별도 준비 인스턴스와 같은 승인 엔진/image에 맞는 공유 디코더 원장을 사용해야 한다. 웹 서비스와 비신뢰 파일 작업자에는 엔진 socket을 주지 않는다. 서비스 시작 시 운영 최소 DB 권한·비공개 파일 권한·자원 예산·승인 runtime·국내 통제를 별도로 확정해야 한다.

추가형 `014-media-work-queue.sql`은 001~013 SQL/체크섬을 변경하지 않는다. 기존 quarantine/inspecting의 작업만 원 상태/버전/키/증거를 바꾸지 않고 등록한다. 기존 ready/bound 파일을 재검사하거나 새 큐/검사 증거가 있는 것처럼 포장하지 않는다. 운영 마이그레이션을 실제 적용한 것은 아니다.

- 서버 **470개 통과**(기존 453 + 큐 17), 실패/취소/건너뜀 0. 큐 등록/확정 실패 롤백·새 인스턴스·실제 임시 디스크·DB 시각 재시도·5회 보류·권한 해제·취소/만료·응답 유실·늦은 완료·SQL 우회·중단 대기·운영 원장 필수·013→014 원본/증거 보존을 확인했다. 큐 단위의 준비 결과는 선언된 합성 fixture이며 실제 검사 증거와 구분한다.
- 실제 **PostgreSQL 18.6의 23개 통과**(기존 18 + 큐 5). 별도 연결 풀의 큐/수신 롤백·동시 한 번 선점·잠긴 방 건너뛰기·현재 사용자 정지를 확인했다. 별도 생성한 정확한 자식 프로세스가 실제 선점한 것을 IPC로 확인한 후 그 PID만 SIGKILL하고, 종료 signal·자연 임대 만료·새 인스턴스의 다른 임대/후보·과거 완료 거부·최종 큐 확정까지 확인했다. 이 자식 시험은 **SQL/실제 프로세스 복구**이며 검사 중 native 컨테이너/운영 디스크/PC 장애 전체 조합을 입증한 것은 아니다.
- 실제 **ClamAV/격리 FFmpeg/Linux IO/PGlite 결합 18개 통과**. 기존 분리 저장 첫 사례를 `queued → MediaWorkQueueWorker.runOne → 원본/후보 실제 검사·전체 디코딩·실제 저장 → ready/completed` 경로로 실행한다. 시험 전용 명시적 local mode·tmpfs/PGlite이며 운영 영구 매체/전원 손실 증거가 아니다. 컨트롤러 종료 0·OOM false·자기 컨테이너/정의 볼륨/image tag 정리를 확인했다.
- 루트 로컬 단위·구문/정적 빌드·whitespace 검증은 별도로 실행한다. 이번 작업은 화면을 변경하지 않았으므로 브라우저/실물 기기 검증을 재실행한 것으로 주장하지 않는다.

초기 큐 fixture에서 콜백의 바이트 인자를 source factory로 잘못 해석한 6개 실패를 바로잡았다. 첫 전체 회귀에서는 새 작업자의 파일명이 기존 오프라인 `prepareDecodedMedia` 파일과 충돌했다. 기존 파일과 그 두 후속 변경을 이 채팅의 원래 작성 이력에서 복원하고 새 파일을 `media-work-queue-worker.mjs`로 분리했다. 기존 프로토콜 13개·전체 회귀·실제 검사 결합을 재실행했으며, 실패 실행을 성공으로 집계하거나 검증기를 우회하지 않았다.

## 변경 파일과 남은 우선순위

- 신규: `server/migrations/014-media-work-queue.sql`, `media-work-queue.mjs`, `media-work-queue-worker.mjs`, 큐 단위/native/자식 시험.
- 연결: `server/media-uploads.mjs`, `conversations.mjs`, `media-preparation.mjs`, `decoder-jobs.mjs`, 기존 native storage 사례·PG/native Docker allowlist·시험 완료 조건·기존 업그레이드 예상 목록.
- 문서: README·서버 기반·PostgreSQL·013 저장 문서와 본 문서. UI·API·의존성/lock·운영 설정은 변경하지 않았다.

2026-10-06 후속은 [015 센터 자원 제한](media-resource-limits.md)이다. 센터 전체의 보수적 용량 예약·새 예약 이동 구간 빈도·검사 대기량과 명시적 정책/중지를 추가했고, 용량 부족 작업을 건너뛰어 다른 센터가 진행하도록 했다. 기존 큐 횟수·현재 권한·동일 업로드 ID와 후보 제공 정책은 유지한다. 운영 값을 선택하지 않았고 미설정 센터는 신규 예약/검사 객체 할당을 거부한다. 위 470/23개는 014 당시이며 후속 전체 결과는 015 문서를 따른다.

이후 [016 보류 검토·재개](media-work-reviews.md)를 추가했다. 기존 5회 누적 횟수를 유지하고 현재 관리자의 명시적 영수증 한 건에 추가 한 번만 부여한다. 최대 추가 3건/누적 8회는 기술적 안전 상한이며 전체 검사·원 소유자 권한·기한·자원 경로를 우회하지 않는다. 기존 필드/상태·원본·증거를 보존하고 재개가 파일 승인/공유가 되는 것을 막는다. 위 470/23/18개는 014 당시 범위이며 최종 전체 검증은 016 문서를 따른다.

2026-10-06 실행 경로 후속은 [작업자 종료·상태·복구 경계](media-worker-lifecycle.md)다. 중단 신호와 DB/회수 오류가 겹치면 실패로 유지하며, 검사 후 디코더 회수까지 기다린다. 최소 process-local 상태와 opt-in SIGTERM/SIGINT runner를 추가했다. 운영 감독자·영속 heartbeat·자동 시작/재시작은 아니며 최신 검증은 해당 문서를 따른다.

다음 순서는 ① 운영 supervision·영속 감시/경보·실제 위임 정책 ② 원본/후보/증거/backup/fence의 보존·파기·과거 파일 전환 및 운영 영구 매체/백업 검증 ③ 국내 공급자·키/로그/지원/계정 복구·메일·관리자 운영 준비 ④ 마지막 API/화면 연결·다른 실물 기기 전송·통신 단절/재접속 검증이다. 자원 한도는 weighted fairness/센터별 CPU 배분/악용 방지 전체나 실제 청구 사용량 측정이 아니다.
