# 가정 활동 첨부와 기록의 당시 참고 열람

2026-10-09. 가상 자료 로컬 API 연결의 후속이다. 실제 아동 자료·외부 접속·공개 배포 보류는 유지한다. 기존 4173 정적 프로토타입은 변경하지 않는다.

## 범위와 데이터 의미

가정 활동 경험을 저장할 때 검사 완료된 사진·영상을 함께 보낼 수 있다. 보호자에게는 해당 대화 참여자에게 첨부도 공유됨을 안내한다. 치료 기록의 기본 비공개 첨부와 다른 동작이며, 보호자 피드백에는 공유 선택 체크박스를 두지 않는다.

보호자가 피드백 1판의 사진을 2판에서 영상으로 교체해도, 치료 기록에서 이미 참고한 1판의 사진은 바뀌지 않는다. 기록 수정도 기존 고정 참고를 보존한다. 새로 참고하는 경우에는 확인한 소식 버전을 저장 요청에 포함해 도중 변경을 조용히 받아들이지 않는다. 참고 파일은 기록의 공유 첨부에 자동 포함되지 않는다.

SQL 스키마·인증 구조를 추가하지 않고 기존 `ActivityFeedback`, `Records`, 버전별 미디어 연결, `MediaAccess`를 사용한다. 준비 첨부 모드 여부는 서버의 실제 파일 서비스 설정에서 결정한다. 기본 메모리/격리 실행기는 여전히 첨부 저장·열람을 허용하지 않는다.

## 열람 경계

| 열람 | 기준 | 허용 범위 |
| --- | --- | --- |
| 대화의 활동 경험 첨부 | 현재 피드백 메시지 | 현재 소식 열람 권한이 있는 참여자 |
| 특정 활동 경험 판의 첨부 | 피드백 ID·메시지 ID·정확한 판 | 권한이 있는 치료사만 |
| 기록의 당시 참고 첨부 | 기록 ID·정확한 기록 판·참고 메시지 ID | 해당 기록을 읽을 수 있는 치료사만 |

추가 콘텐츠 경로는 다음과 같다. 모든 경로 앞에는 인증된 센터·대화방 범위가 붙는다.

- `/messages/:messageId/feedback-revisions/:revision/attachments/:uploadId/content`
- `/records/:recordId/revisions/:revision/references/:messageId/attachments/:uploadId/content`

서버는 관계·과거 열람 경계·원본 결합을 다시 확인한다. 업로드 소유권이나 파일 ID만으로 여는 경로는 없다. 공유 철회 후 보호자는 원 활동/피드백의 파일을 더 이상 열 수 없지만, 치료사의 허용된 임상 참고는 별도 기록 권한으로 보존된다. 삭제·숨김은 임상 참고의 영구 파기와 다르다. 센터 관리자에게 임상 내용 접근을 추가하지 않는다.

브라우저는 같은 고정 출처의 첨부 정보 조회 → 인증된 크기 제한 파일 읽기 → 같은 출처 재조회 이후에만 Blob URL을 만든다. 과거 버전 조회 실패를 최신 버전으로 대체하지 않는다. 계정·방·역할·화면 변경, 부모 창 종료, 권한 재확인 실패 시 읽기·재생·임시 URL을 정리한다.

## 초안과 재시도

대화·기록·활동 경험은 각각 분리된 선택 소유자를 사용한다. 활동 경험 선택은 계정·센터·방·피드백 ID로 구분한다. 한 선택 목록은 최대 6개, 각 용도별 메모리 보유 상한은 24개·100MB이며 세 소유자의 합산 상한은 72개·300MB다. 서버 저장 한도와는 별도다. 선택은 메모리 전용이며 새로고침 후 미저장 파일 선택 복구를 보장하지 않는다.

저장 요청에는 파일 ID·피드백 판·요청 번호를 고정한다. 결과가 불명확하면 같은 본문과 요청 번호로 확인하고, 성공 영수증 전에는 파일 선택을 비우거나 바꾸지 않는다. 확정 거절 뒤에는 원문을 다시 노출하지 않는 첨부 정리 화면에서 남은 선택의 상태 확인·취소만 허용한다. 방/계정 권한을 잃으면 메모리 선택을 제거한다. 새 파일을 임의 승인하거나 성공한 것으로 간주하지 않는다.

### 실제 E 피드백·참고 첨부

실행 `7b53fb21-3d85-4582-a1b3-fbbdbf1c3c64`는 **9개 흐름 모두 통과, 실제 종료 코드 0**이었다. 결과는 `test-results/synthetic-e-session-7b53fb21-3d85-4582-a1b3-fbbdbf1c3c64.json`, 브라우저 증거는 `test-results/native-feedback-attachments-7b53fb21-3d85-4582-a1b3-fbbdbf1c3c64/results.json`, 로그는 `test-results/feedback-attachments-native-20261009-a.log`다.

1. 치료사가 텍스트 가정 활동을 공유하고, 보호자가 실제 검사 완료 PNG를 1판(F1) 피드백에 저장했다.
2. 치료사가 명시적으로 ‘다음 기록에 참고’를 선택하고, 정확한 F1 파일을 열어 디코딩한 뒤 새 기록에 참고를 저장했다. 참고 사진이 원기록의 공유 파일에 자동 포함되지 않음을 확인했다.
3. 보호자가 F1 사진을 제외하고 검사 완료 MP4를 2판(F2)에 저장했다. 실제 저장 성공 응답을 한 번 잃은 뒤 같은 본문·파일 ID·요청 번호로 재시도해 2판 영수증을 재확인했다. 검사 승인·성공 저장·역할을 흉내 낸 것은 아니다.
4. 치료사는 정확한 F2 판에서, 보호자는 현재 피드백에서 같은 영상을 실제 재생했다. 보호자가 현재 메시지에서 제외된 F1 파일을 읽으려 하면 404였다.
5. F2 교체 후에도 치료 기록 1판의 당시 참고 파일은 F1 PNG와 크기·응답 바이트 해시가 같았다. F2를 같은 기록 참고 경로로 요청하면 거부했다.
6. 원 공유 종료 후 보호자의 현재 파일·과거 판 파일·기록 참고 경로는 모두 404였다. 보호자 화면에서도 원문·파일명이 제거됐다. 치료사는 새로고침 후 별도 기록 권한으로 F1 파일을 다시 열 수 있었다.

PNG 응답은 91바이트, SHA-256 `b5942de479d452d10a7b4dc1aaf5db0be28026dc0eb3d636d30817b31c3c0f25`; MP4는 2,439바이트, `ef37ea0ee9a695063a68d60bed11d7d4500696d38cce822f25dd92a261ca71e5`다. 파일 ID와 원문은 모두 이 실행에서 생성한 합성 자료다. 두 업로드 모두 격리→검사 중→준비 완료, 실패 코드 없음으로 진행했다. PNG 20MiB·MP4 100MiB 예약만 사용했으며 기존 120MiB 한도를 늘리거나 세 번째 파일을 추가하지 않았다.

API·작업자 실제 종료 코드 0, close·파이프 닫힘·종료 대기, DB 정지·시험 키 정리, 브라우저/컨텍스트 종료를 확인했다. E의 합성 DB·미디어 진단 자료는 오프라인 보존하며 독립 백업이 아니다.

### 기존 기록 경로 회귀의 중간 실패

같은 소스로 기존 기록 첨부 모드를 실행한 `220d2d05-848f-4f9c-804f-abbc434a31e1`은 **실패, 실제 종료 코드 1**이다. `test-results/feedback-attachments-record-regression-20261009-a.log` 및 해당 `synthetic-e-session-*.json`, `native-record-attachments-*/results.json`에 보존했다. PNG는 준비 완료였으나 영상 검사 중 상태 조회의 정상 응답을 기다리다 시간 초과가 발생했다. 화면에는 연결 확인 불가와 결과 불명 안내가 표시됐고 파일 선택은 남아 있었다. 브라우저 오류·예상 밖 요청은 0이었다. 저장·선택 공유 등 뒤쪽 검사는 실행되지 않았으므로 통과로 계산하지 않는다.

현재 도우미는 각 상태 갱신에서 HTTP 200 응답을 15초간 기다린다. 이 실패만으로 실제 무응답, 다른 HTTP 상태, 요청 취소를 구별할 수 없으며 전체 180초 파일 준비 한도가 소진된 것으로 단정하지 않는다. 다음 진단에서는 민감정보 없이 상태 코드·취소·잔존 자원 종류를 구별해야 한다.

API가 종료 완료 IPC를 보낸 뒤에도 실제 종료·close가 늦어 30초 관측 기한을 넘겼다. 종료 요청 후 약 44.7초에 실제 종료 코드 0과 모든 파이프/close가 확인됐지만, 앞선 시간 초과 실패를 취소하지 않는다. 작업자는 정상 종료됐고 DB 정지·키 폐기·브라우저 종료도 확인했다. 저장 실행 `fdfd52bb-8086-45ee-85fe-f15f871f6872`의 PID·TLS·자격증명·공통 세션 잠금은 없었으며 해당 검사/디코더/생성기 label의 컨테이너·이미지·볼륨도 각 0이었다.

원인은 아직 확정하지 않았다. 제한 시간·검사 승인·종료 판정을 완화하거나 Node/보안 설정을 바꾸지 않았다. 소유 자원의 종료를 확인한 뒤 같은 소스의 새 가상 세션 `05c60d66-3a08-47f4-9bad-823e20b1a169`으로 재실행하여 **기록 첨부 8개 흐름 모두 통과, 종료 코드 0**을 확인했다. 로그는 `test-results/feedback-attachments-record-regression-20261009-b.log`다. 준비 파일·기본 비공개·동일 저장 요청 재시도·정확한 기록 판·선택 공유·보호자 영상·비공개 파일 차단·새로고침을 확인했다. 오류/예상 밖 요청 0, 브라우저·작업자·API·DB·키 정리 정상이며 API 실제 종료는 요청 후 약 45ms였다. 두 실행의 시작·종료 소스 지문은 위 피드백 실행과 같다. 재실행 성공은 앞선 실패의 근본 원인 해결 증거가 아니다.

### 기존 일반 대화 첨부 회귀와 최종 정리

### 분리 재현: 동적 비밀번호 거절 뒤 남는 연결

설치된 실제 `pg` 8.23.0 / `pg-pool` 3.14.0에서 다음 메커니즘을 별도로 확인했다. 동적 비밀번호 Promise가 거절되면 Client는 접속 오류를 전달하며 접속 타이머를 해제한다. Pool은 해당 Client를 관리 목록에서 제외하지만 그 경로에서 연결을 닫지 않는다. 이후 `pool.end()`는 관리 목록이 비었다는 이유로 완료될 수 있다.

새 `server/tests/postgres-password-failure-lifetime.test.mjs`의 **2/2 시험, 실제 Node 종료 0**으로 확인했다. 증거는 `test-results/postgres-password-failure-lifetime-20261009.tap`이다. 이 시험은 위 전체 서버 회귀 이후 추가해 별도로 실행했으며 기존 1,239개에 포함됐다고 계산하지 않는다.

1. 자체 소유 127.0.0.1 서버가 합성 PostgreSQL 초기 인증 요청만 보낸다. 비밀번호 함수는 즉시 거절하며 비밀번호 패킷은 전송하지 않는다. `connect()` 거절·`pool.totalCount=0`·`pool.end()` 완료 뒤에도, 설정한 연결 시간 250ms보다 긴 500ms 후 TCP 1개가 열려 있었다.
2. 대조군에서는 비밀번호 Promise를 미완료 상태로 유지했다. 실제 연결 시간 초과가 발생한 경우에는 TCP가 닫혔다.

두 시험은 정확히 자신이 생성한 소켓·서버를 finally에서 정리하고 실제 종료를 확인한다. E·실제 DB·TLS 설정·DPAPI·실제 비밀번호를 사용하거나 변경하지 않는다. 이것은 **드라이버의 실패 연결 정리 공백을 재현한 증거**이지 이번 E 실행에서 비밀번호 공급자 오류가 발생했다는 증거는 아니다. 제품 코드는 아직 이 공백을 보완하지 않았으므로 해결 완료로 표시하지 않는다.

다음 구현은 설치 패키지를 직접 수정하거나 소켓을 `unref`로 숨기지 않고, 애플리케이션의 DB 연결 소유 계층에서 실패한 접속의 실제 종료를 보장하는 방향으로 검토한다. 정상 연결·TLS 거절·비밀번호 함수 거절·동시 종료를 각각 검증해야 한다. 성공으로 둔갑시키는 자동 재시도, 제한 시간 연장, 파일 검사 생략은 하지 않는다.

## 2026-10-09 실패 DB 연결의 종료 보완

앞 절은 수정 전 진단 기록이다. 후속 구현은 `server/postgres-pool.mjs`에서 드라이버의 공개 Client `connect/end`와 Pool `Client` 옵션을 이용해 연결 종료를 관리하고, `server/database.mjs`의 실제 PostgreSQL 팩토리에 연결했다. 설치 패키지·드라이버 내부 필드·SQL 스키마는 수정하지 않는다. 외부에서 임의 Client 클래스로 바꾸는 옵션은 허용하지 않는다.

접속이 실패하면 해당 연결의 `end` 완료 뒤 원래 접속 오류를 딱 한 번 전달한다. 늦은 성공/중복 오류 콜백이 결과를 바꾸지 않는다. Pool이 이미 연결을 목록에서 제거했어도 시작된 종료 작업은 별도로 추적한다. 전체 close는 Pool 종료와 남은 연결 종료를 모두 기다리고, 여러 close 호출은 같은 Promise를 반환한다. 종료 실패는 보존해 후속 close가 성공으로 보이지 않게 한다. 접속 중·사용 중인 정상 연결을 조기에 끊지는 않는다.

트랜잭션 인터페이스와 기존 `databaseFromPool` 주입 경로, 사용자·역할 권한 검사, TLS, 동적 비밀번호 재조회/버퍼 정리, 비밀번호 공급자와 DB의 시간 제한은 유지했다. 자동 재시도·자격증명 캐시·추가 타이머·`unref`·운영 데이터/배포 변경은 없다.

### 집중 검증 범위

- 새 `server/tests/postgres-pool.test.mjs` 9개는 드라이버 메서드 대역으로 종료 순서, 여러 종료의 대기, 원래 오류 보존, 동기 예외, 중복/늦은 콜백, 종료 실패의 지속성, 삭제된 연결의 대기 등을 검증한다. 실제 TCP 증거로 합치지 않는다.
- `server/tests/postgres-password-failure-lifetime.test.mjs`는 원래 raw 드라이버 대조군 2개를 유지하고 총 10개로 확장했다. 실제 설치 드라이버와 자체 소유 루프백 TCP로 동기/비동기 비밀번호 오류·잘못된 반환값·늦은 응답·동시 접속 실패를 확인한다. 실패 시 비밀번호/SQL 패킷은 없고 정상 Terminate 패킷만 허용한다. 서버 쪽 FIN을 통제해 접속 거절과 close가 실제 연결 종료 전에 완료되지 않는지도 확인한다. 정상 연결 재사용으로 3개 트랜잭션을 처리하는 경로도 포함한다.
- 초기 동시성 시험 1개는 가짜 비밀번호 Promise를 실제 콜백 진입 전에 거절해 발생한 시험 경합이었다. 콜백 2개 진입을 명시적으로 기다리도록 고쳤으며 제품의 성공 조건/시간 제한을 완화하지 않았다. 최종 10개는 모두 통과했고 재실행을 별도 검사 개수로 늘려 계산하지 않는다.

이 집중 시험의 가짜 서버는 실제 PostgreSQL·TLS·DPAPI·E 저장 검증이 아니다. HTTP 503을 일으킨 구체 오류가 비밀번호 공급자였다고 확정하지 않으며, 이 수정으로 모든 간헐 오류가 해소됐다고 선제 주장하지 않는다.

### Windows 확인 파일의 동시 읽기 경합 수정

### 후속 구현과 수동 확인 경로 정정

위 다음 단계 문장은 당시 상태다. API만 정상 재시작하는 후속 구현·실행법·검증 결과는 [동일 가상 세션 실행기](synthetic-e-session.md)를 따른다. 작업자/DB/PC 재시작이나 완전히 종료된 세션 재개까지 지원하는 것은 아니다.

앞 두 실행의 별도 수동 확인에서 공통 잠금을 `private/.carebridge-interactive-session.json`으로 조회한 것은 잘못된 경로였다. 실제 경로는 `E:/CarebridgeBeta\private\checks\.carebridge-interactive-session.json`이다. 따라서 잘못된 수동 조회를 당시 잠금 부재의 증거로 사용하지 않는다. 당시 실행기 자체의 소유 검증·`secretsDisposed:true` 결과는 유지하며, 2026-10-09 후속 작업 시작 전에 올바른 경로의 부재를 다시 확인했다. 이후 실제 검증도 이 정확한 경로를 사용한다. 이전 PID/TLS/자격증명 경로와 개별 Docker label 확인은 이 경로 정정과 별개다.
