# 목표·일정 서버 작성과 기록 맥락 보존

2026-10-01. P1의 서버 내부 서비스 `Goals`, `Appointments`를 구현했다. 화면의 서버 연결과 목표·일정 HTTP API는 마지막 단계로 남겨 두었다. 현재 웹앱은 계속 로컬 데모 저장소를 사용한다.

## 현재 동작

담당 치료사는 공동 목표의 제목·설명·상태(`active / achieved / paused`)를 작성·수정한다. 현재 연결된 보호자와 치료사는 최신 공동 목표를 조회한다. 센터 관리자는 목표 원문을 조회하지 못한다. 이는 로컬 프로토타입의 공동 목표 조회 범위를 유지한 것이다.

담당 치료사와 센터 관리자는 일정의 날짜·시간·진행 시간·제목·장소·상태(`scheduled / attended / absent / cancelled`)를 작성·수정한다. 보호자는 현재 연결된 아동의 일정을 조회한다. 센터의 일정 조회는 운영 필드만 반환하고 목표·치료 원본·대화·내부 메모를 조회하지 않는다.

같은 센터에서 취소되지 않은 일정의 아동·현재 담당 치료사·장소가 겹치면 저장을 거부한다. 구간은 시작 포함·종료 제외이므로 10:00~10:40과 10:40~11:20은 허용한다. 진행 시간은 10~180분, 분 단위 입력이며 같은 날 안에 끝나야 한다. 자정 종료는 시간 덧셈의 날짜 넘김으로 계산하지 않고 분 수로 검사한다. 날짜·시간은 센터의 국내 현지 일정으로 저장하며 UTC 시각으로 임의 변환하지 않는다.

취소는 이력을 삭제하지 않고 자원을 비운다. 취소를 되돌릴 때도 현재 다른 일정과의 충돌을 검사한다. `attended`, `absent`는 기존 규칙대로 취소가 아니므로 해당 시간의 이력을 계속 차지한다. 취소되지 않은 새 일정/변경에는 활성 담당 치료사가 필요하다. 담당자 미배정·계정/소속 비활성 상태에서는 새로 확정할 수 없고, 센터가 취소하는 것은 허용한다.

## 수정 이력과 치료 기록

실제로 내용이 바뀌면 목표·일정의 새 수정본을 자동 생성한다. DB에서도 이전 수정본의 덮어쓰기·삭제와 원본의 아동/대화방 변경을 거부한다. 같은 내용의 저장은 수정본을 늘리지 않으며 별도 처리 영수증만 남긴다.

`Records.save`는 목표와 연결 일정의 당시 수정본을 함께 저장한다. 목표 제목·상태 또는 일정 시간·장소·출결이 바뀌어도 이전 치료 기록의 `goalSnapshot`, `appointmentSnapshot`은 변하지 않는다. 공유 요약에는 이 임상 맥락 원문을 추가하지 않는다.

기록 작성 시작 때 확인한 `expectedGoalRevision`, `expectedAppointmentRevision`을 보내면 저장 전 내용 변경을 `CONTEXT_CHANGED`로 거부한다. 이후 화면/API 연결에서는 이 필드를 항상 전달해야 한다. 기존 내부 호출과 요청 해시를 유지하기 위해 미전달 호환 경로는 현재 저장 시점의 수정본을 연결한다. 일정이 없는 기록에는 예상 일정 수정본을 보낼 수 없다.

일정 정정·취소가 연결된 기록을 자동 삭제하거나 수정하지 않는다. 새 회기는 새 일정 ID로 생성하고, 기존 일정의 정정은 동일 회기의 정보를 바로잡는 용도로 사용한다. 기록 하나가 참조한 일정은 기존처럼 같은 센터·아동이어야 하며, 한 일정에 두 개의 현재 기록을 만들 수 없다.

## 서비스 계약

모든 `actor`는 검증된 서버 세션의 `{ centerId, userId }`다. 권한은 DB의 활성 사용자·센터 소속·현재 아동 관계에서 판단한다. 요청 본문의 역할은 권한으로 사용하지 않는다.

| 메서드 | 입력과 응답 |
| --- | --- |
| `Goals.save(actor, input)` | `conversationId`, `goalId`, `clientId`, `expectedRevision`, `content: { title, description?, status? }`. 신규 예상 수정본 0. 수정은 현재 번호가 일치해야 한다. 전체 내용 저장이며 부분 패치가 아니다. |
| `Goals.get(actor, input)` | `conversationId`, `goalId`로 최신 공동 목표. 치료사만 `revision`으로 과거 수정본 요청 가능. |
| `Goals.list(actor, input)` | `conversationId`, `after?`(ID), `limit?`(최대 100), `expectedRevision?`(대화방 revision). `goals`, `revision`, `nextCursor`, `hasMore`, `resetRequired` 반환. 연속 페이지에서 같은 revision을 사용한다. |
| `Appointments.save(actor, input)` | `conversationId`, `appointmentId`, `clientId`, `expectedRevision`, `content: { date, time, duration, title, room, status? }`. 신규 0, 수정은 현재 번호 확인. |
| `Appointments.get(actor, input)` | `conversationId`, `appointmentId`로 현재 일정. 센터/치료사만 `revision`으로 이전 일정 정보 조회 가능. |
| `Appointments.list(actor, input)` | `dateFrom`, `dateTo`(포함, 최대 93일), `conversationId?`, `limit?`(최대 100), `after?`, `expectedVersion?`. 아동을 생략하면 센터는 전체, 치료사/보호자는 현재 연결 아동의 일정만 조회. |

저장 응답은 `{ kind, id, revision, changed, replayed }`이다. 같은 사용자·센터의 동일 context 요청 ID/내용은 이전 영수증을 반환한다. 다른 내용·아동·명령에 같은 ID를 재사용하면 `IDEMPOTENCY_CONFLICT`다. 오래된 재시도로 최신 수정본을 되돌리지 않는다. 새로고침 후 최신 내용은 별도 `get`으로 조회한다. 재시도에도 현재 권한이 필요하다. 영수증은 이전 처리의 ID/버전만 반환하며 임상 원문을 포함하지 않는다.

일정 목록 응답은 `{ appointments, version, nextCursor, hasMore, resetRequired }`이다. 커서는 `{ date, time, conversationId, appointmentId }`로 같은 시간의 일정도 구분한다. 커서로 다음 페이지를 요청할 때는 첫 응답의 `expectedVersion`이 필수다. 일정 또는 담당 관계가 바뀌면 센터의 `schedule_version`이 증가하고 이전 목록은 교체 조회해야 한다. 다른 사람의 접근 권한은 실제 조회 때 다시 판단한다.

현재 일정의 `therapistId`는 현재 활성 담당 관계를 뜻한다. 과거 일정 수정본은 당시 담당자를 저장하지 않은 구조이므로 `therapistId: null`을 반환하며 현재 담당자를 과거 담당자로 표시하지 않는다. 치료 기록의 작성자는 별도로 보존된다.

## 열람 범위와 충돌 처리

최신 공동 목표와 운영 일정은 현재 팀이 이어서 치료를 준비하는 정보다. `from_now` 연결도 최신 정보는 조회한다. 반면 치료사가 목표/일정의 **이전 수정본**을 직접 조회할 때는 대화의 과거 열람 시작 순번을 적용한다. 보호자는 이전 수정본을 직접 조회하지 못한다. 센터는 운영 일정의 이력을 조회하지만 목표·임상 원본에는 접근하지 못한다. 대화·공유본·피드백의 기존 과거 열람 규칙은 그대로 유지된다.

일정 저장과 담당 관계 교체는 **센터 일정 잠금 → 아동 대화방 → 사용자/소속 → 참여 관계** 순서로 처리한다. 센터 단위 잠금을 공유해 서로 다른 아동의 일정 변경과 담당자 교체가 충돌 검사 사이에 끼어들지 않도록 한다. 작은 초기 센터를 위한 직렬 처리이며 대규모 동시 처리 성능을 보장하지는 않는다.

DB는 일정 원본이 바뀌면 충돌을 검사한다. 담당 관계 변경은 최종 참여자 구성이 확정되는 커밋 시점에 다시 검사한다. 새 치료사가 이미 다른 아동의 겹치는 시간에 배정되어 있으면 관계·열람 범위·읽음 초기화·영수증까지 모두 취소한다. 운영자가 충돌 일정을 조정한 뒤 같은 요청으로 재시도할 수 있다. 직접 SQL로 관계/일정을 변경하는 유지보수 코드도 동일한 센터 우선 잠금 순서를 따라야 한다.

변경 감사 역할의 영수증에는 대상 ID·수정본·요청 해시·처리 시각만 저장한다. 목표 설명·일정 제목·원문·자격 증명은 포함하지 않는다. 수정본·원본·처리 영수증·방 순번·센터 일정 버전은 같은 트랜잭션에 속한다.

## 기존 데이터 전환

007은 기존 001~006 SQL을 수정하지 않는 추가형 마이그레이션이다. 기존 목표·일정의 ID·내용을 보존하고 현재 값을 수정본 1로 캡처한다. 당시 작성자·변경 시각·대화 순번은 알 수 없으므로 null이다. 캡처 시각은 이관 시각이며 원래 작성 시각으로 사용하지 않는다.

기존 치료 기록에는 당시 목표/일정 수정본이 없었으므로 `goalRevision`, `appointmentRevision`과 스냅샷은 null로 유지한다. 이관 시점의 최신 목표·일정을 과거 기록의 맥락으로 추측해 연결하지 않는다. 이후 저장하는 기록부터 당시 수정본을 명시적으로 남긴다. 알 수 없는 이전 수정본은 전체 이력 권한(시작 순번 1)이 있는 치료사에게만 직접 조회된다.

기존 일정의 시간/진행 시간 형식이 새 분 단위·당일 종료 제약에 맞지 않으면 마이그레이션은 전체 롤백한다. 조용히 날짜나 시간을 고치지 않는다. 운영 데이터 반입 전에는 별도 사전 검사와 복구 가능한 백업이 필요하며, 현재 브라우저 데이터를 이관하지 않았다.

서버 테스트는 가상 자료만 사용하는 인메모리 PGlite다. 실제 PostgreSQL 여러 연결의 잠금 경쟁·응답 유실·부하 시험은 아직 수행하지 않았다. 센터 단위 잠금의 처리량과 대기 시간도 측정해야 한다. PostgreSQL/psql 실행 파일은 현재 로컬 환경에서 확인되지 않았다. 서버 배포 패키지는 공통 `src/context-fields.js`도 포함해야 한다.

목록·원본 버전 확인은 저장 계층 계약이다. 화면 → 실제 계정/API → 운영 DB → 다른 기기 경로는 아직 구현·검증하지 않았다. 이후 [비공개 임시 업로드 기반](media-upload-storage.md), [첨부 원본 연결·공유 접근](media-binding-storage.md), [기본정보·기존 계정 연결](profiles-provisioning.md)을 구현했다. 최신 전체 결과는 [서버 기반 문서](server-foundation.md)를 참고하며 위 80개/28개와 브라우저 결과는 목표/일정 단계 당시 증거다. 실제 파일 엔진·보존/파기 정책·국내 운영/메일/복구/백업과 마지막 API/화면 연결은 남아 있다. 로컬 첨부는 보존한다.
