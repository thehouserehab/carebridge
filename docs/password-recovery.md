# Carebridge 비밀번호 분실 복구 — 내부 처리와 가상 로컬 연결

## 2026-10-10 가상 로컬 API 연결

별도 로컬 화면에서 `.test` 재설정 요청 → 비공개 시험 전달 → 새 비밀번호 설정 → 기존 세션 종료 → 일반 로그인을 연결했다. 기존 내부 `Auth`·스키마를 재사용한다. 복구 요청은 동일한 안내만 반환하며, 완료 응답 유실은 재설정 재전송 없이 일반 로그인으로 확인한다. 현재 세션은 명시적으로 로그아웃해야 하고 복구 응답은 쿠키를 설정하거나 지우지 않는다.

변경 파일·최종 검증·제한은 [가상 비밀번호 복구 API 연결](local-api-connection.md#2026-10-10-가상-비밀번호-복구-api-연결)을 따른다. 실제 메일·이메일 소유 확인·외부 접속·영속 운영·독립 백업은 아직 연결/완료하지 않았다. 아래는 **각 이전 단계 당시**의 내부 준비 기록이며 현재 로컬 API 구현 상태와 구분한다.

## 2026-10-08 초대·복구 안내의 내부 전달 준비

P101의 계정 진입을 이어갈 수 있도록 `server/account-delivery.mjs`를 추가했다. 기존 `Auth` 발급 → 현재 DB의 수신자/토큰 상태 재확인 → 고정 안내문 구성 → 주입된 전달자 한 번 호출을 묶는다. 실제 메일 업체·SMTP·공개 HTTP·사용자 화면과는 연결하지 않았다. 기존 Node/PostgreSQL 인증 구조를 유지하는 인증·백엔드 스킬의 범위로 구현했으며, 새 인증 공급자나 의존성은 추가하지 않았다.

### 내부 호출과 실패 계약

`new AccountDelivery({ auth, origin, transport, timeoutMilliseconds? })`의 의존성은 신뢰하는 서버 설정이다. `origin`은 경로/쿼리/fragment/자격정보가 없는 정확한 HTTPS origin만 허용한다. 입력 요청의 Host·redirect를 링크 생성에 사용하지 않는다. 현재 링크 경로는 `/account/invitation#token=…`, `/account/password-recovery#token=…`이며 **향후 연결용 계약이지 동작 중인 페이지가 아니다.** 토큰을 HTTP 요청 URL에 직접 넣지 않도록 fragment를 선택했지만 브라우저 기록·스크립트·메일 처리자의 노출까지 제거하는 것은 아니다.

| 호출 | 허용 입력 / 결과 |
| --- | --- |
| `invite(actor, { centerId, email, role })` | 신뢰하는 인증 경계가 확인한 actor. 기존 `Auth.createInvitation`이 현재 관리자 권한을 다시 검사한다. 역할은 치료사/보호자만 허용한다. |
| `recover({ email })` | 기존 등록 계정 발급 정책을 유지한다. 요청자가 다른 수신 주소·사용자 ID·토큰·발신자·redirect를 추가하면 거부한다. |
| `Auth.accountDeliveryRecipient({ purpose, token })` | 신규 읽기 전용 단일 조회. DB의 이메일·만료 시각만 반환하며 이메일은 비열거 속성이다. 초대의 현재 발급자 권한/수락 가능성, 복구의 현재 활성 계정, 미사용·미철회·미만료 조건을 확인한다. |
| `transport.send(envelope, { signal })` | 주입한 신뢰 전달자를 한 번 호출한다. `to`, `subject`, `text`, `link`는 비열거·동결 속성이고 `purpose`만 일반 열거된다. 단일 ASCII 주소만 허용하며 주소 목록·표시 이름·개행/제어문자를 거부한다. 실제 발신 계정은 향후 전달 어댑터의 승인된 설정이어야 한다. |

결과의 일반 JSON에는 모든 유효 요청에 동일한 `publicResponse`만 포함한다. 명시적으로 접근하는 비열거 `internal`은 발급 상태 `issued / not-issued / unknown`과 전달 상태 `accepted / rejected / unknown / not-attempted`만 포함한다. **이 내부 상태는 계정 존재를 드러낼 수 있으므로 공개 응답·일반 분석 로그로 내보내면 안 된다.** 비열거 속성은 실수로 JSON/기본 inspect에 섞이는 것을 줄이는 장치이며 암호화·접근 통제·메모리 완전 소거가 아니다.

- `accepted`는 전달자가 수락했다고 응답한 상태이지 수신함 도착이나 사용자의 읽음이 아니다.
- 발급 중 DB 오류는 커밋 결과를 추정하지 않고 `unknown`이다. 수신자 확인 실패·권한/토큰 종료는 전달자를 호출하지 않는다. 내부 예외 원문·토큰·이메일을 결과나 오류에 붙이지 않는다.
- 전달 예외·잘못된 응답·시간 초과는 `unknown`이며 자동 재시도하지 않는다. 기본 대기는 10초이고 신뢰 설정에서 1~60,000ms를 허용한다. timeout 시 AbortSignal을 보내지만 원격 요청 취소나 미전달을 보장하지 않는다. 늦은 수락/거부는 이미 반환한 결과를 바꾸지 않는다.
- DB 재확인 트랜잭션이 종료된 뒤 전달자를 부른다. 외부 I/O 동안 DB 잠금을 잡지 않는다. 재확인 이후 철회/만료가 경합할 수 있으므로 기존 초대 수락·비밀번호 재설정의 최종 권한/만료 검사가 계속 적용된다.
- 원문 토큰을 파일·DB·영속 큐에 새로 저장하지 않는다. 따라서 프로세스 종료 후 미전달 요청 복구·같은 토큰 재전송을 보장하지 않는다. 실패한 초대의 기존 대기 행과 복구 재발급 제한을 자동 해제하지 않는다. 전달 재시도/중복/재발급 책임과 영속 큐는 별도 설계·운영 결정이 필요하다.

고정 HTTPS 도메인과 요청 Host 비사용, 계정 존재와 무관한 응답/시간 처리 및 변경 후 통지 원칙은 [OWASP 비밀번호 복구 지침](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), 비밀값 로그 배제는 [OWASP 로깅 지침](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)을 참고했다. fragment와 10초 대기는 이 프로젝트의 선택이며 OWASP가 지정한 값이 아니다. 동일 JSON만으로 시간 기반 계정 추측이 차단되지 않는다. 실제 공개 연결 전에는 독립 비동기 처리·응답 시간·전체 요청 제한·CSRF/Origin·안전한 landing page를 검증해야 한다.

## 현재 상태와 변경 이유

[본인 비밀번호 변경](password-change.md)은 유효한 로그인 세션과 현재 비밀번호가 필요하므로 비밀번호를 잊은 사용자의 복구 수단이 아니다. [최소 계정 보안 사건](account-security-events.md)을 유지하면서, 기존 [Auth 서비스](../server/auth.mjs)에 `preparePasswordRecovery`와 `completePasswordRecovery`를 분리해 추가했다. 새 인증 공급자·클라우드·의존성은 사용하지 않는다.

등록 이메일로 전달할 복구 수단을 준비하는 것과, 그 수단을 가진 사용자가 새 비밀번호를 확정하는 것은 별도 단계다. 센터 관리자 역할이나 요청자가 제출한 사용자 ID를 본인 확인으로 대신하지 않는다. 기존 계정·센터 소속·아동 관계·임상 기록·메시지를 재생성하거나 재활성화하지 않는다.

## 내부 계약과 공개 응답의 구분

| 메서드 | 입력 | 반환 및 경계 |
| --- | --- | --- |
| `Auth.preparePasswordRecovery` | `{ email }`만 허용. 이메일은 기존 규칙으로 정규화 | 발급 가능한 활성 계정이면 내부 전달 객체, 없거나 정지·발급 제한 상태이면 `null`. 사용자 ID·다른 수신 주소·역할·redirect URL 입력은 거부 |
| `Auth.completePasswordRecovery` | `{ token, newPassword, confirmation }`만 허용 | 성공 시 `{ passwordChanged: true, reauthenticate: true }`. 새 세션·자동 로그인·사용자 목록·계정 메타데이터는 반환하지 않음 |

준비 메서드의 전달 객체는 `expiresAt`과 **비열거 속성**인 `email`, `token`을 가진 동결 객체다. 일반 `JSON.stringify`에 원문 토큰과 이메일이 섞이는 실수를 줄이지만, 두 값은 신뢰하는 내부 코드에서 명시적으로 읽을 수 있다. 암호화된 메모리, 로그 유출 방지 보장, 영속 outbox 또는 메일 전달 완료 증거가 아니다.

이 반환값을 HTTP 응답으로 그대로 내보내면 안 된다. `null`과 전달 객체의 차이, 만료 시각, 처리 시간만으로도 계정 존재를 노출할 수 있다. 향후 공개 요청 경계는 일관된 안내를 먼저 제공하고, 신뢰하는 전달 작업만 등록 계정의 주소를 사용해야 한다. 예를 들어 “등록된 계정이라면 복구 안내를 보내드립니다”와 같은 문구·상태·응답 시간의 일관성을 별도로 구현·검증해야 한다. 현재 메서드는 공개 응답 시간의 균등성을 보장하지 않는다.

현재 [인증 HTTP 모듈](../server/auth-http.mjs)에 복구 경로를 추가하지 않았다. `/api/auth/password/forgot`, `/api/auth/password/reset`에 대한 기존 처리 결과가 404이며 복구 메서드를 호출하지 않는 것을 집중 시험에서 확인했다. 로컬 데모의 역할 선택도 실제 계정 복구나 메일 소유 확인이 아니다.

| 시간당 제한 | 최근 1시간 동안 동일 계정에 발급된 행을 세어 최대 3회. 이미 사용·폐기된 발급 이력도 포함 |
| 재발급 | 기존 미사용·미폐기 토큰을 닫고 새 토큰을 같은 트랜잭션에서 저장. 새 행 삽입 실패 시 기존 토큰 폐기도 롤백 |
| 비밀번호 | 기존 12~128자·scrypt 정책 유지. 공백/Unicode 원문을 임의 정규화하지 않으며 확인 입력의 완전 일치와 현재 비밀번호와의 차이를 검사 |
| 완료 | 토큰 사용 처리 → 새 해시·변경 시각·실패 횟수/임시 잠금 초기화 → 해당 계정의 모든 미폐기 세션 폐기 → `password.recovered` 사건 저장을 한 트랜잭션으로 처리 |
| 결과 | 정상 로그인 절차를 다시 거쳐야 함. 다른 사용자의 자격·세션과 센터/아동/임상 자료는 변경하지 않음 |

발급 요청만으로 비밀번호·세션·로그인 실패 횟수를 바꾸거나 계정을 잠그지 않는다. 제한된 요청도 기존 정상 로그인을 차단하지 않는다. 다만 등록 이메일을 실제로 안전한 복구 채널로 확인·전달하는 절차와 전송 실패 대응은 아직 연결되지 않았다.

유효한 토큰은 기존 비밀번호 실패로 생긴 임시 잠금을 해소할 수 있지만, `cb_users.active=false`인 사용자의 복구는 거부한다. 정지된 센터 소속·아동 참여 관계는 복구 성공 뒤에도 정지 상태 그대로다. 계정 비활성화를 우회하거나 센터의 접근 승인을 복원하지 않는다.

미존재·잘못된 용도·만료·폐기·이미 사용된 토큰은 `PASSWORD_RECOVERY_INVALID`로 거부한다. 비밀번호 확인 불일치와 동일 비밀번호는 자격 변경이나 토큰 소비 없이 수정 가능한 오류로 남는다. 이들은 내부 오류 코드이며, 향후 공개 경계의 안전한 오류 문구·로그 정책을 대신하지 않는다.

토큰 소비, 새 해시, 전체 세션 폐기, 사건 INSERT 중 하나라도 실패하면 함께 롤백한다. 성공 응답 유실은 실패 전 원복이나 성공으로 단정하지 않는다. 자동 재발급·재로그인·명령 재실행을 하지 않으며, 이미 소비된 토큰을 다시 사용해 두 번째 변경을 만들 수 없다. 전달 객체 반환 전 커밋 응답이 유실되어 원문 토큰을 받지 못한 경우도 별도 전달/재요청 복구 설계가 필요하다.

## 경합·만료·저장 제약

[021 마이그레이션](../server/migrations/021-password-recovery.sql)은 `cb_auth_password_resets`와 `cb_password_reset_guard`, `cb_password_reset_invalidate`를 추가한다. 001~020 원문을 고치거나 기존 계정에 복구 토큰을 일괄 생성하지 않는다.

저장 필드는 `token_hash`, `user_id`, `created_at`, `expires_at`, `consumed_at`, `revoked_at`뿐이다. 원문 토큰·비밀번호·이메일·임상 내용은 새 테이블에 넣지 않는다. 미사용·미폐기 토큰은 사용자당 하나만 허용한다. ID·대상·생성/만료 시각은 수정할 수 없고, 사용·폐기된 토큰을 다시 열거나 두 종료 상태를 동시에 지정할 수 없다. 생성/종료 시각은 DB 트리거가 확정한다.

준비·완료는 계정 행 → 활성 사용자 행 → 복구 토큰 순서로 잠근다. 완료 전 토큰의 사용자 ID를 조회하는 것은 잠글 계정의 단서를 얻는 단계이며 자격 승인 자체가 아니다. 실제 승인 시 계정, 활성 상태, 토큰의 미사용·미폐기·만료 상태를 다시 확인한다. 비밀번호 해시 계산이나 잠금 대기 중 만료될 수 있어 소비 UPDATE와 DB 트리거에서 DB 시각을 재검사한다. 실제 여러 PostgreSQL 연결에서의 경합 증거는 아래 검증표에서 별도로 관리한다.

DB 트리거는 비밀번호 또는 등록 이메일 변경, 사용자 활성→비활성 전환 시 남은 미사용 토큰을 폐기한다. 이후 사용자를 다시 활성화해도 이전 토큰을 되살리지 않는다. 이미 사용·폐기된 행은 그대로 남는다. 복구 요청에는 소속·관계 활성화, 관리자의 타인 비밀번호 대리 설정, 과거 이메일로 복귀하는 기능이 없다.

`password.recovered` 사건은 폐기된 세션이 0개여도 저장할 수 있도록 021에서 기존 사건 제약을 확장했다. 기존 `password.changed`, `sessions.revoked`의 양수 조건은 유지한다. 기록하는 수는 미폐기 세션 UPDATE 행 수이며 현재 접속 중인 기기 수가 아니다. 사건에는 원문 토큰·이메일·비밀번호를 추가하지 않았다.

## 권한·보존·백업 복원

[권한 정책](../server/database-privilege-policy.mjs)은 **v5 / 테이블 62개 / 함수 52개 / sequence 2개**다. 새 테이블에 대한 권한은 다음과 같다.

| 역할 | 복구 토큰 테이블 권한 |
| --- | --- |
| migration 소유자 | 검토된 스키마·권한 변경. 사용자 요청을 처리하는 계정으로 사용하지 않음 |
| 앱 runtime | SELECT·INSERT 및 `consumed_at`, `revoked_at` 두 컬럼 UPDATE만 허용. DELETE·TRUNCATE·토큰 ID/수명 변경 권한 없음 |
| 백업 | SELECT만. 원문 토큰은 없지만 계정 식별자·토큰 해시를 포함하는 고신뢰 자료로 취급 |
| bootstrap / worker / PUBLIC | 새 테이블 접근 없음. 새 트리거 함수의 직접 호출 권한도 추가하지 않음 |

앱 runtime은 신뢰하는 서버 역할이지 보호자·치료사별 DB 계정이 아니다. 권한 목록만으로 API의 신원 확인이나 사용자별 접근 통제를 대체하지 않는다. 021과 v5 적용·권한 재검토가 필요하며 런타임에서 migration 또는 GRANT를 자동 실행하지 않는다.

해시와 내부 사용자 ID가 남으므로 익명 자료가 아니다. 새 토큰 테이블의 계정 FK는 계정 삭제 시 연쇄 삭제되지만, 이것이 서비스의 계정 삭제 승인이나 보존 기간을 정한 것은 아니다. 최소 보안 사건은 기존 보존 규칙을 유지한다. 만료 토큰의 운영 보존·파기 기간, 백업 사본과 사건의 삭제 책임·절차는 미확정이며 임의의 보관 일수나 자동 삭제를 추가하지 않았다.

[복원 격리](recovery-quarantine.md)는 새 테이블도 잠근 뒤 사용자 비활성화 트리거와 남은 토큰의 명시적 폐기로 모든 미사용 토큰을 닫는다. 이미 비활성인 사용자의 토큰과 만료되었지만 아직 폐기되지 않은 토큰도 포함한다. 사용·기존 폐기 행은 덮어쓰지 않고 기존 불변 격리 영수증에 새 집계 컬럼도 추가하지 않는다. 완료와 정확한 재시도 모두 사용자·세션·초대·복구 토큰의 닫힘을 확인하며 실패하면 `RECOVERY_QUARANTINE_AUTH_OPEN`으로 거부한다.

[복원본 대조](recovery-state-comparison.md)는 격리 영수증을 제외한 **61개 테이블**을 비교한다. 새 토큰 테이블에서는 격리로 더 엄격해지는 `revoked_at`만 제외하고, 해시·대상·생성/만료·사용 시각과 행 자체는 비교한다. 대상에 미사용·미폐기 토큰이 하나라도 남으면 `RECOVERY_STATE_AUTH_OPEN`으로 거부한다. 일치해도 `serviceReleaseAllowed:false`이며, 토큰 재발급·계정 재활성화·격리 해제를 승인하지 않는다.

공개 자산 SHA-256은 `3a6b8536ec5160414e384dc4ad1c9ff79ddea3a7e7372bb6e1c7f149c6341ef4`로 이전 화면 검사 소스와 동일하며, 정적 빌드의 33개 파일 바이트도 소스와 일치했다. 이번에는 브라우저 검사를 다시 실행하지 않았다. 중간 권한 정책 검사에서 `PASSWORD`가 테이블명 `password_resets`까지 잘못 잡아 실패했고, SQL 키워드 경계를 검사하도록 정규식을 고친 뒤 통과했다. 이후 전체 서버 최종784와 실제 E48 결과가 위 수치다.

## 남은 위험과 다음 구현 순서

1. **전달·통지 계약:** 내부 객체를 받을 신뢰 작업자, 등록 복구 주소의 확인, 전달 실패/중복·응답 유실 대응, 성공 후 비밀번호 변경 통지를 구현해야 한다. 원문 비밀번호는 메일에 넣지 않으며 토큰/링크를 일반 로그·분석 도구·지원 기록에 남기지 않아야 한다. 현재는 실제 메일을 보내지 않는다.
2. **최종 HTTP·화면 경계:** 계정 존재 여부와 무관한 안내·응답 시간, HTTPS, 요청 크기·Origin/CSRF 검토, 요청/시도 제한, 안전한 오류 응답이 필요하다. 현재 계정당 발급 제한은 IP·분산 공격·미존재 계정 요청·토큰 대입·해시 계산 남용 전체를 막는 장치가 아니다.
3. **복구 URL과 브라우저 노출:** 허용된 서비스 도메인으로만 링크를 구성하고 요청 Host/redirect 값을 그대로 사용하지 않아야 한다. 복구 화면의 `Referrer-Policy: no-referrer`, 캐시·접근 로그·외부 스크립트·오류 수집의 토큰 노출을 점검해야 한다. 아직 URL 형식이나 외부 메일 공급자를 확정하지 않았다.
4. **화면과 검증:** 새 비밀번호·확인 입력, 만료/재발급 안내, 입력 오류 복구, 완료 후 일반 로그인 흐름을 실제 브라우저와 다른 기기에서 검증해야 한다. 유효 토큰 증명과 센터 소속/아동 접근 권한은 계속 분리한다.
5. **운영 전제:** 독립 백업·복구 키 회수, 보존/파기와 담당자, 국내 저장·전달 경로 및 접근 통제를 준비해야 한다. E 드라이브 안의 사본은 독립 백업이 아니다. 그 전에는 합성 자료만 사용하며 실제 아동 자료 입력·수집, 외부 접속 개방, 실제 계정에 대한 메일 발송을 시작하지 않는다.

공개 응답의 일관성, 일회용·만료 토큰, 새 비밀번호 재입력, 변경 통지와 일반 로그인, 안전한 URL·referrer 경계는 [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)를 참고했다. 15분·60초·시간당 3회는 현재 프로젝트의 구현값이며 OWASP가 정한 보편적 수치나 법적 보존 기준이라고 하지 않는다.

## 변경 파일과 재검증

- 제품 내부 처리: `server/auth.mjs`, `server/migrations/021-password-recovery.sql`, `server/database-privilege-policy.mjs`, `server/recovery-quarantine.mjs`, `server/recovery-state-comparison.mjs`. 기존 인증 공급자·001~020·사용자 화면·HTTP 경로는 바꾸지 않았다.
- 검사: `server/tests/auth-password-recovery.test.mjs`, `server/auth-password-recovery-native-tests.mjs`, native 등록 회귀, 기존 권한/격리/대조 시험과 마이그레이션 기대 목록. `server/database-privileges-native-check.mjs`, `server/recovery-state-native-check.mjs`, Windows·일반 PostgreSQL 실행기 및 Docker 명시적 파일 허용 목록도 새 스키마/시험에 맞췄다.
- 문서: 이 문서, README·전체 완료표·기존 비밀번호 변경/보안 사건 문서의 후속 안내. 인증·백엔드 설계 스킬의 기존 구조 우선 원칙에 따라 공급자 교체나 외부 자원 생성 없이 내부 구성요소만 확장했다.

서버 회귀는 `node --test --test-concurrency=2 server/tests/*.test.mjs`, 공개 화면 회귀는 `npm test`, 구문/정적 빌드는 `npm run check`와 `npm run build`로 실행한다. Windows E 검사는 기존 `test:database-privileges:e-drive` 및 `test:recovery-state:e-drive`의 합성 전용 명령이며, 실제 운영 DB에 적용하는 명령이 아니다. 이번 작업은 커밋·푸시·배포·실제 메일 발송을 하지 않았다.
