# 가상 로컬 API 기록 첨부·선택 공유

작성 2026-10-09. 사용자가 승인한 가상 자료 로컬 API 연결의 후속이다. 기존 4173 정적 프로토타입, 공개 배포, 실제 아동 자료·외부 접속 보류는 바꾸지 않는다.

후속: [가정 활동 첨부·기록 당시 참고 열람](local-feedback-attachments.md)을 추가했다. 아래 기능 범위·시험 수·두 소유자 메모리 한도와 미연결 목록은 기록 첨부 단계 당시의 이력이다. 최신 기능, 세 소유자 한도, 성공/실패 및 미확정 지연은 후속 문서를 따른다.

## 연결 범위

기존 E 가상 세션의 준비 첨부 모드에서 치료 기록에 사진·영상을 저장하고, 선택한 파일만 보호자 공유본에 포함한다. 새 SQL 스키마나 별도 권한 체계를 만들지 않고 `Records`, 버전별 미디어 연결, `MediaAccess`를 재사용한다. 기본 메모리/격리 모드는 계속 첨부 저장·열람을 허용하지 않는다.

1. 치료사가 기록 입력에서 가상 파일을 선택하고 업로드한다. 기존 실제 검사·처리가 끝나야 저장할 수 있다. 업로드만으로 보호자에게 전송하지 않는다.
2. 새 첨부는 모두 비공개다. 기록에 저장된 파일은 정확한 기록 버전의 권한으로 연다. 임시 원본이나 업로드 소유권만으로 열지 않는다.
3. 보호자에게 보낼 파일만 명시적으로 선택하여 기록에 저장한다. 공유 미리보기에서 수신자·요약·선택 파일을 확인한 뒤 별도 공유한다.
4. 보호자는 공유 메시지에 포함된 파일만 열 수 있다. 비공개 기록 경로나 제외 파일로 접근하면 거부한다. 이전 공유본의 철회·재공유 권한 규칙은 유지한다.
5. 저장 결과가 불명확하면 같은 요청 번호·기록 버전·첨부 ID·공유 선택으로 다시 확인한다. 성공 영수증을 받기 전에는 파일 선택을 바꾸거나 성공한 것으로 비우지 않는다.
6. 저장 처리 중 화면이 원문 없는 영수증 확인으로 바뀌었다가 첫 요청이 확정 거절되면, 남은 첨부를 잃지 않도록 같은 기록 ID의 ‘미저장 첨부 정리’ 화면을 유지한다. 원문은 복원하지 않고 기존 선택의 상태 확인·취소만 허용한다. 새 파일 선택·업로드·공유 변경·저장은 차단한다.

대화와 기록의 파일 선택은 다른 소유자가 관리한다. 기록 선택은 계정·센터·아동 방·기록 ID로 구분한다. 브라우저 영구 저장소에 파일 선택이나 자격증명을 저장하지 않으며 새로고침하면 미저장 선택은 사라진다. 대화 선택과 기록 선택의 메모리 상한은 각각 24개·100MB이며, 앱 전체 합산 최대 48개·200MB다. 이는 임시 선택 메모리 상한이고 서버 저장 용량·한 기록의 첨부 개수 제한과는 별개다.

## 권한·수명 경계

- 서버 준비 모드는 실제 `MediaAccess` 설정에서만 파생한다. 브라우저 표시값·본문·쿼리로 켤 수 없다.
- 기록 파일 경로는 `/records/:recordId/revisions/:revision/attachments/:uploadId/content`다. 양의 정수 버전을 반드시 지정하며 최신 버전으로 암묵 대체하지 않는다.
- 기록 파일은 치료사만, 공유 파일은 현재 공유 메시지 열람 권한이 있는 참여자만 조회한다. 센터 관리자에게 임상 내용 접근을 추가하지 않는다.
- 브라우저는 해당 버전의 첨부 정보 조회 → 인증된 제한 크기 파일 읽기 → 같은 버전의 권한·첨부 정보 재조회 순서가 모두 성공한 뒤에만 Blob URL을 만든다.
- 화면·방·계정·역할 변경, 연결 범위 재확인, 닫기 시 읽기를 중단하고 재생·미디어 요소·Blob URL을 해제한다. 초안 정리는 완전히 조회된 현재 허용 방 목록에만 근거한다.
- 기존 HTTP 동시 읽기 제한·실제 스트림 종료 대기·후보 파일 검증·민감정보 없는 오류 응답은 공통 경로로 유지한다.
- 기록 창이 닫히거나 원문 재확인이 실패하면 열린 기록 첨부 뷰어도 즉시 정리한다. 다음 주기 조회까지 남기지 않는다.

### 실제 E 기록 첨부 통합

실행 `a30fa6c6-cd3c-4ab8-bc19-ed6729ebab2e`는 **8개 흐름 모두 통과, 실제 종료 코드 0**이었다. 결과는 `test-results/synthetic-e-session-a30fa6c6-cd3c-4ab8-bc19-ed6729ebab2e.json`, 브라우저 증거는 `test-results/native-record-attachments-a30fa6c6-cd3c-4ab8-bc19-ed6729ebab2e/results.json`, 전체 로그는 `test-results/record-attachments-native-20261009-a.log`에 있다.

- PNG/MP4 모두 격리→실제 검사·처리→준비 완료를 거쳤고 실패 코드는 없었다.
- 두 파일 모두 기본 비공개로 저장했다. 첫 저장의 실제 성공 응답을 한 번 잃은 뒤 같은 본문·첨부 선택·요청 번호로 재시도하여 1판 영수증을 재확인했고 중복 기록을 만들지 않았다.
- 치료사는 비공개 PNG를 정확한 기록 1판에서 열고 실제 디코딩했다. 공유 선택을 바꾼 2판 저장 후에도 1판의 선택 정보는 그대로였다.
- 공유 미리보기에는 영상 한 개와 확인할 수신자만 나타났고 내부 수행·반응·다음 계획·메모·비공개 파일명은 없었다. 보호자는 공유 메시지에서 실제 영상을 재생했다.
- 보호자가 공유 메시지의 비공개 PNG ID 또는 원기록 1/2판의 파일 경로로 접근한 실제 HTTP 조회는 404였다. 새로고침 후에도 공개·비공개 선택이 유지됐다.
- 치료사 기록/PNG 뷰어는 1440·320px, 보호자 영상은 390px에서 확인했다. 이는 모든 조합의 실물 기기 시험이 아니다. 캡처 8장 중 좁은 기록·뷰어, 보호자 영상, 공유 미리보기 4장을 직접 확인했으며 긴 파일명·체크박스·버튼의 가로 넘침은 관측되지 않았다. 분홍 영역은 계정 마스킹이다.

Chromium `149.0.7827.55`, 소스 247개의 시작·종료 지문은 `bf1e7638d04a8d43f5367a714106203e618198c40571bd1d555e1460adb1da92`로 같았다. 오류·예상 밖 브라우저 요청은 0이었다. 콘텐츠 증거는 치료사/기록 1판과 보호자/공유 메시지를 구분하여 파일 ID·형식·크기·응답 바이트 해시를 기록했다.

API/작업자 모두 실제 종료 코드 0, close·파이프 닫힘·종료 대기 완료, PostgreSQL 정지와 시험 키 정리, 브라우저/컨텍스트 종료를 확인했다. 저장 실행 `ff9bb0ad-e9cf-4acd-a346-164d0f8bb71b`의 postmaster PID·TLS·자격증명 폴더·세션 잠금은 정리 후 없었다. 검사 소유 label `cf1ea7b3-ae3e-4e98-8436-cac4d7e7b70e`, 디코더 `257b5711-5cf6-46fd-9076-f95bcd8b888c`, 생성기 `c6cc16f9-2ece-457d-8efc-2a8ab2a347d6`의 컨테이너·이미지·볼륨도 각각 0개였다. Docker Desktop 자체와 기존 사용자 프로토타입은 종료하지 않았다. 합성 E DB·미디어 진단 자료는 오프라인 보존하며 실제 자료나 백업이 아니다.

### 기존 실제 대화 첨부 경로 재검증

공통 업로더·뷰어 변경의 회귀를 위해 기존 기본 모드도 별도 새 E 세션에서 직렬 실행했다. 실행 `c7d5b5ef-1043-4484-be5e-72bc49044589`는 실제 종료 코드 0으로 통과했다. 결과는 `test-results/synthetic-e-session-c7d5b5ef-1043-4484-be5e-72bc49044589.json`, 브라우저 결과는 `test-results/native-prepared-c7d5b5ef-1043-4484-be5e-72bc49044589/results.json`, 로그는 `test-results/record-attachments-existing-flow-20261009-a.log`다.

사진·영상 대화 첨부 2개 경로에서 실제 준비 상태·첨부만 전송·수신 후 새로고침·디코딩·포커스 복원을 확인했다. 영상은 실제 재생을, PNG는 발신 응답 유실 후 동일 요청 재시도를 확인했다. 홈 일정·구조화 기록·비공개 항목 제외 미리보기·공유 수신·가정 피드백 수신·새로고침 6개 기존 흐름도 통과했다. 오류·예상 밖 요청은 0이며 250개 소스의 시작·종료 지문은 `3c36bae15346f6591b8051eaa28517c7af7067f11c6a4144f0d921b8350f2f44`로 같았다. 두 도우미의 지문 대상 파일 목록이 달라 기록 전용 모드의 지문과 값은 다르다.

API/작업자 실제 종료 코드 0·close·파이프 닫힘, DB 정지·키 정리·브라우저 종료를 확인했다. 저장 실행 `f7e7bf3d-8c52-4661-abeb-7d67f60c087f`의 PID/TLS/자격증명/세션 잠금은 없었고 검사 `4453ca61-a537-424f-a8ce-da1421cf9e1a`, 디코더 `6f90e6b5-628c-4795-9d34-42056b0ce0e0`, 생성기 `275349cd-cce1-4929-9c39-0999063c2e34` label의 컨테이너·이미지·볼륨은 각각 0개였다.

변경 범위 24개 파일의 엄격 UTF-8·후행 공백·충돌 표식 검사와 scoped `git diff --check`를 통과했다. 공개 정적 자산 35개는 소스/배포 폴더 해시가 같고 `dist/local-api`는 없다. 커밋·push·배포·런타임 교체는 하지 않았다. 확장 native 55개 회귀를 이번에 다시 실행했다고 주장하지 않으며, 이번 실제 검증은 위 두 가상 세션 흐름이다.

```powershell
# 프로젝트 루트의 로컬 시험
node --test --test-concurrency=1 tests/*.test.mjs
npm run check
npm run build
# server 폴더의 서버 회귀
node --test --test-concurrency=1 tests/*.test.mjs
```

실제 기록 첨부 모드는 기존 검증된 PostgreSQL·PowerShell·Docker/검사 이미지·Playwright/Chromium 준비가 필요하다. `PLAYWRIGHT_MODULE`, `STUDY_CHROMIUM_EXECUTABLE`은 기존 확인된 절대 경로를 지정한다. 임의 운영 DB나 기존 사용자 브라우저는 사용하지 않는다.

```powershell
node tests/windows-synthetic-session-check.mjs --record-attachments --base E:/CarebridgeBeta --powershell '<검증된 pwsh.exe 절대경로>' --confirm-synthetic-e-drive
```

실행마다 새 가상 세션을 만들며 원래 120MiB 예약 한도에서 PNG 하나와 MP4 하나만 준비한다. 기존 메시지 PNG·영상 회귀는 별도 새 세션의 기본 모드로 유지한다. 같은 파일을 기록과 메시지에 이중 연결하거나 저장 한도를 늘리지 않는다. 시험은 E PostgreSQL·실제 검사 작업자·API·독립 Chromium 계정으로 수행하고, 종료 후 소유 자원 정리 결과까지 확인한다.

## 남은 범위와 위험

가정 피드백 첨부·기록에 참고한 과거 소식의 첨부 열람은 이번 기록 자체 첨부와 다른 수신 범위이므로 아직 연결하지 않는다. 피드백 편집의 기존 첨부 제거 방지 규칙도 유지한다. 다음은 이 두 흐름을 각각 불변 버전으로 연결·검증하는 작업이다.

같은 가상 세션을 프로세스 재시작 뒤 다시 여는 기능, 실제 여러 기기·실사용자 사용성 검증, 독립 백업, 운영 보존·파기/복구는 미완료다. 과거 Windows 작업자 비정상 종료·DB 열기 지연의 원인도 미확정이다. 새 회귀가 성공하더라도 이전 실패가 해결됐다는 근거로 바꾸지 않는다. E의 합성 진단 자료는 별도 백업이 아니며 실제 자료 수용 근거가 아니다.
