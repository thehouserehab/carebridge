# 원본·공유용 파일의 분리 저장과 원자적 사용 가능 전환

2026-10-05. 개편안 P1의 사진·영상 서버 저장 후속이다. 준비된 후보를 메모리에서 반환하는 데서 끝내지 않고, **실제 비공개 파일 저장·불변 검사 증거·권한 기반 후보 제공**까지 기존 `MediaUploads` / `MediaAccess`에 연결했다. API·화면·공개 배포·실제 아동 자료·유료 자원은 활성화하지 않았다. 전체 개편안과 국내 운영 준비는 미완료다.

## 현재 동작

이 문서는 013 분리 저장 작업 당시의 증거다. 이후 [014 검사 작업 큐](media-work-queue.md)에서 수신/큐 등록·임대 선점·결과 확정·명시적 polling과 재시작 회수를 연결했다. 아래 453개/18개 SQL 및 자동 큐 미구현 문구는 당시 상태이며 최신 서버 470개/PG 23개와 운영 한계는 후속 문서를 따른다. 운영 자동 시작/API·화면 연결은 여전히 하지 않았다.

```text
같은 첨부 ID / 원본 manifest·원본 객체 보존
  → 검사 임대 + 별도 후보 객체의 쓰기 의도 먼저 커밋
  → 원본 검사 → 격리된 원본/후보 전체 디코딩·metadata 처리 → 후보 검사
  → 반환 바이트·각 증거의 manifest/해시/정의 상태 재확인
  → 후보 객체 쓰기·파일 동기화 → 저장된 후보 전체 해시 다시 읽어 확인
  → 불변 검사 증거와 ready를 하나의 DB 트랜잭션으로 확정
  → 기존 메시지/기록/피드백/선택 공유 연결
  → 현재 원본 접근 권한 + 후보 manifest로 미리보기·부분 다운로드
```

- `object_key`, 원본 크기·SHA-256·파일명·기존 첨부 ID는 보존한다. `candidate_key`는 원본과 다른 UUID다. 변환 결과가 원본과 같은 바이트여도 별도 객체를 쓴다.
- 준비 모듈의 `prepared` 자체는 승인 상태가 아니다. **양쪽 clean + 전체 디코딩/시간축 증거 + 후보 저장·재조회 + 유효한 작업 임대**를 모두 확인한 뒤에만 내부 `ready`가 된다.
- 기술 보고서의 `mediaAcceptanceReady`는 계속 false다. `ready`는 내부 저장·첨부 사용 상태이지 임상 타당성·익명화·실제 운영 투입 승인을 뜻하지 않는다.
- 공개 상태와 첨부 목록은 실제 제공되는 후보 크기를 표시한다. 객체 경로·해시·검사 원문·임대 토큰은 반환하지 않는다. 묶음 용량 제한은 원본과 후보 중 큰 크기를 사용한다.
- 새 파일의 원 소유자 미리보기와 연결된 파일의 `MediaAccess.open` 모두 같은 `servingFile` 규칙을 쓴다. 후보가 없거나 손상되면 실패하며 원본을 대신 내려주지 않는다.
- 보호자의 조회/철회/재공유·이력 시작점·센터 임상 접근 차단은 기존 원본 연결 정책을 유지한다. 첨부만 보낸 메시지가 치료 기록으로 자동 등록되지 않는다.

## 설정과 스키마

`new MediaUploads(database, privateStore, { preparation })`의 `preparation`에는 명시적으로 구성한 `MediaPreparation`만 넣는다. 기본값 null에서는 격리 상태를 유지한다. `scanner.inspect`만 넣는 옛 생성자 경로와 public `settle(..., { state: 'ready' })`는 더 이상 승인 경로가 아니다. 서버가 생성한 비공개 원본 읽기 함수만 준비 서비스에 전달하며 요청에서 함수·검사 보고서·저장 키를 받지 않는다.

`013-media-preparation-storage.sql`은 001~012의 파일/체크섬을 변경하지 않는 추가형 마이그레이션이다.

- 업로드에 준비 필수 여부·후보 키·제공 크기/해시·증거 참조를 추가한다.
- `cb_media_preparations`는 해당 업로드·임대·처리 버전·원본/후보 키와 양쪽 정확한 manifest·검사 증거를 불변으로 보관한다. 임상 텍스트·사진 바이트·원문 metadata는 넣지 않는다.
- 후보 intent는 기존 `cb_media_objects` 원장을 사용한다. 증거를 확정한 트랜잭션이 `ready`도 확정하지 않으면 지연 제약이 커밋을 거부한다. 현재 객체의 삭제, 준비 필수 flag 해제, 증거/제공 manifest 변경도 거부한다.
- `bound` 원본과 후보 모두 임시 정리로 삭제할 수 없다. 최초 바인딩·선택 공유·수정본 첨부 ID와 수신 범위를 그대로 유지한다.
- 기존 승인 파일은 `preparation_required = false`로 기존 조회를 보존하고, 새 준비 증거가 있는 것처럼 포장하지 않는다. 새 행은 이 값으로 생성할 수 없다. **과거 승인 파일의 재검사/후보 생성·전환은 아직 자동 수행하지 않는다.** 실제 운영 전에 별도 검토·반입 정책이 필요하다. 기존 기록이나 파일을 임의로 변환·폐기하지 않았다.

## 장애·취소·복구

| 상황 | 결과와 회수 방식 |
| --- | --- |
| 준비 서비스 미설정, 손상/잘못된 증거, 검사/IO 장애 | `quarantined` 또는 정확한 탐지의 `rejected`. 후보 intent는 삭제 대기로 전환하고 원본은 유지한다. 내부 오류 원문은 공개 상태에 없다. |
| 후보 쓰기 응답만 성공했지만 실제 파일 없음/손상 | 저장 후 `openVerified` 전체 읽기가 실패하므로 증거/ready를 확정하지 않는다. |
| 후보 저장 뒤 DB 확정 실패 | 부모는 `inspecting`, 후보는 추적된 비공개 객체로 남고 증거는 롤백한다. 임대 종료 후 `cleanup`이 후보를 차단/회수하고 검사 대기로 돌린다. |
| DB 커밋 뒤 응답 유실 | 다른 인스턴스의 `get`이 실제 ready/증거를 확인한다. 같은 첨부 ID를 조회/재사용하고 검사·발신 ID를 새로 만들며 중복 승인/메시지를 만들지 않는다. |
| 임대 종료 후 재검사 | 새 임대·새 후보 키로 작업한다. 이전 후보는 삭제 의도와 `.blocked` fence로 회수하며 이전 작업은 확정할 수 없다. |
| 취소 후 늦은 쓰기/완료 | 원본·후보 모두 삭제 의도를 남긴다. 파일 fence가 재생성을 거부하고 상태/버전/임대 검사도 늦은 완료를 거부한다. |
| 활성 준비 작업 취소/시간 초과 | 단순 Promise.race로 성공/실패를 먼저 반환하지 않는다. 격리 coordinator의 종료·정리 또는 보류 판정까지 기다린다. 반환 후보 메모리는 저장 성공/실패 후 지운다. |
| 권한·철회 변경 중 다운로드 | 저장 후보를 확인한 뒤 현재 원본 권한·상태/버전·제공 키를 다시 검사한다. 이미 전달한 바이트를 회수하는 기능은 아니다. |

정리는 내부 유지보수 호출이며 아직 자동 스케줄러/내구성 있는 작업 대기열은 없다. 예약/증거/객체 원장은 유지한다. 현재 복구는 추적된 intent와 임대에 대한 안전한 회수/재시도이고, 작업을 자동 이어 실행하는 운영 큐의 완성을 뜻하지 않는다.

Linux 로컬 어댑터는 파일 내용뿐 아니라 디렉터리 항목도 fsync한다. 삭제 fence를 동기화한 뒤 파일을 제거한다. **Windows의 Node 경로에는 휴대 가능한 디렉터리 fsync가 없으므로 Windows 시험은 바이트 IO·논리 복구 증거이며 전원 손실 내구성 증거가 아니다.** Windows ACL·운영 디스크/객체 저장소·전원 장애·백업 복원·보안 삭제는 별도 검증이 필요하다.

## 검증과 재현

```powershell
npm run test:server
npm run test:postgres:local
npm run test:media-preparation:local
npm test
npm run check
npm run build
git diff --check
```

- 서버 회귀: 453개 통과(기존 434 + 분리 저장 19), 실패/취소/건너뜀 0. PGlite·실제 임시 디스크·실제 loopback client/protocol과 가상 엔진/디코더를 사용한다. 원본 보존·실제 후보만 제공·바이트 재검증·잘못된 증거·저장 실패·임대/취소/늦은 핸들·응답 유실·SQL 우회·제공 크기 한도를 확인한다.
- 실제 PostgreSQL 18.6: 18개 통과(기존 13 + 준비 저장 5), 두 개의 별도 연결 풀에서 승인/취소 경쟁·원자적 롤백·임대 회수·이전 소유자 차단·증거/양쪽 객체 불변·응답 유실을 검증했다. 새 SQL 증거 fixture는 합성이며 실제 파일/검사 증거가 아니다. 종료 코드 0·일회용 DB/컨테이너 정리를 확인했다.
- 로컬 도메인 단위: 61개 통과. 구문 검사·정적 빌드·tracked whitespace 검사 통과. 화면을 바꾸지 않아 이번 작업에서는 브라우저 검증을 재실행하지 않았다.
- 실제 ClamAV·격리 FFmpeg·Linux IO·PGlite 결합: `npm run test:media-preparation:local`의 18개 통과(기존 12 + 분리 저장 6), 컨트롤러 종료 코드 0·OOM false·자기 컨테이너/정의 볼륨/image tag 정리를 확인했다. 실제 스캔/전체 디코딩과 Linux 파일 저장·후보 제공·쓰기/DB 확정 실패·임대 회수·손상 시 원본 우회 금지·취소 후 늦은 쓰기 차단을 함께 검증했다. 시험 저장소는 tmpfs이고 DB는 PGlite이므로 위 PostgreSQL 여러 연결 시험과 범위를 구분한다. 운영 영구 매체/전원 손실·실물 기기 검증으로 확대하지 않는다.

초기 실패도 통과로 집계하지 않았다. 새 저장 모듈의 응답 유실 시험은 기존 메시지 응답에 없는 `replayed` 필드를 가정해 실패했고, 실제 ID와 DB 메시지/증거 수로 판정하도록 수정했다. 이전 짧은 100ms IO 시험에서는 늘어난 저장 경로가 시간 한도에 걸렸으므로 해당 수신 임대 시험은 그대로 두고 후속 검사는 정상 기본 한도 서비스로 실행했다. 원본/후보 두 객체 정리 수와 현재 코드의 구형 스키마 접근 fixture도 정정했다.

PostgreSQL 초기 실행에서는 18개 본 시험은 통과했으나 바깥 fixture의 예전 13개 완료 문구로 최종 실패했다. full ID·소유 label·image·종료와 같은 로컬 엔진을 확인한 자기 합성 자원만 회수하고 새 UUID 실행에서 최종 0/정리까지 재검증했다. 다른 컨테이너/자료·base image는 유지했다.

결합 컨트롤러에 PGlite를 추가한 첫 실행은 컨트롤러 종료로 실패했고, 종료 진단을 보강한 다음 실행에서 512MiB cgroup의 실제 OOM/137을 확인했다. 신뢰된 **합성 시험 컨트롤러만** 고정 1GiB로 조정한 후 새 실행에서 18개·종료 코드 0·OOM false·정리까지 통과했다. 기본 Linux 컨트롤러·비신뢰 파일 worker·소켓/네트워크/비관리자/읽기 전용 규칙을 완화한 것은 아니다. 임의 더 큰 메모리·swap·명령·host network/port·추가 mount는 검증기가 거부한다.

## 변경 파일과 다음 우선순위

- 저장/제공: `server/media-uploads.mjs`, `media-access.mjs`, `media-bindings.mjs`, `media-serving.mjs`, `private-file-store.mjs`.
- 증거: `server/media-preparation-evidence.mjs`, `media-preparation.mjs`, `migrations/013-media-preparation-storage.sql`.
- 검증: 신규 저장 테스트, SQL/native 합성 helper, PostgreSQL/준비 native harness·Docker allowlist·격리 정책, 기존 업그레이드/첨부 테스트와 문서. 의존성/lock은 변경하지 않았다.

다음 순서는 ① durable queue·실제 프로세스 종료/다중 작업자 재시작·센터별 용량/빈도 제한 ② 원본/후보/증거/backup/fence의 보존·파기와 과거 파일 전환 ③ 국내 인프라·최소 권한 저장/키/로그/지원 경로·메일·관리자/계정 복구·백업 복원 ④ 마지막 API/화면 연결·다른 실물 기기와 통신 단절/재접속 검증이다. 자동 공개 활성화·운영 승인·공급자 선택/유료 생성은 하지 않았다.
