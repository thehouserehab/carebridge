# Carebridge 계정·초대 화면 구현

## 2026-10-08 비밀번호 찾기 화면 체험

로그인 → 체험용 이메일 → 계정 존재 여부와 무관한 공통 안내 → 새 비밀번호/확인 입력 → 완료 안내 → 로그인 복귀를 추가했다. 기존 단순 안내를 실제 조작 가능한 흐름으로 바꿨지만 **인증 기능을 연결한 것은 아니다.** 실제 이메일·비밀번호 대신 합성 입력만 사용한다. 메일 발송, 토큰 발급, 공개 HTTP 호출, 계정·세션·관계 변경은 하지 않는다. [서버 내부 복구](password-recovery.md)와 이 화면의 연결은 API 마지막 단계까지 보류한다.

### 확인 방법과 구현 경계

1. 앱 상단 `로그인 화면` → `비밀번호 찾기`에서 `guardian@example.test` 같은 체험용 주소를 입력한다. 기존 초대 화면과 같은 example.com/org/net/test 도메인 규칙을 재사용한다.
2. `안내 확인 · 체험` → `재설정 화면 체험`에서 서로 같은 12~128자 체험 문구를 두 번 입력한다. 각 표시/숨김 버튼은 독립적으로 동작한다. 실제 계정의 존재를 조회하지 않으며, 등록/미등록을 가정한 두 주소 모두 같은 안내를 보여 준다.
3. 체험 확인란을 선택하고 `입력 확인 · 체험`을 누른다. 완료 후에도 실제 비밀번호·로그인 세션은 그대로다. 자동 로그인하지 않으며 `로그인으로 돌아가기`는 빈 입력 화면을 연다.
4. `만료 안내 체험` → `만료 안내 보기`에서 재요청 경로를 확인한다. 이 버튼은 만료 화면 시연이며 실제 링크 검증이 아니다. 로컬 시연의 요청 후 15분 경계도 재설정 열기와 제출 때 검사한다. 브라우저 시각·메모리 상태는 보안 권한이 아니며, 운영에서는 서버 시각·일회용 토큰·요청 제한을 사용해야 한다.

오류가 나면 같은 입력창과 확인 상태를 유지한다. 성공·취소·Escape·로그인 이동·만료 안내·다른 계정 화면 전환 때에는 표시 중인 `type=text` 비밀번호까지 DOM에서 비운다. 입력을 모델·localStorage·sessionStorage·IndexedDB에 복사하지 않는다. 이는 앱의 DOM/저장·전송 경계 검증이지 브라우저 메모리의 물리적 완전 소거나 비밀번호 관리자 동작의 보장은 아니다. 늦게 도착한 닫기/제출 이벤트가 새로 연 화면을 지우거나 변경하지 않도록 보호했다.

## 기존 계정 연결 화면 추가 2026-10-02

새 계정용 이름·비밀번호 입력과 기존 계정용 센터 연결을 분리했다. 기존 계정 화면에서는 초대받은 이메일, 대상 센터, 이 센터에서의 역할을 먼저 표시한다. 가상 계정 선택 후 전체 이름·이메일을 별도로 보여 주므로 좁은 화면의 native select가 옵션을 줄여 표시해도 확인할 수 있다. 최종 확인을 하지 않거나 이메일/센터/역할이 다르면 저장하지 않는다.

가상 계정 선택은 **인증이 아니다.** 체험 입력은 메모리에만 반영하며 실제 사용자 ID·비밀번호·세션·아동 담당 관계를 만들거나 바꾸지 않는다. fixture의 이름은 가상 계정 식별용 문구다. 실제 연결에서는 센터별 표시명을 다른 센터에서 자동 복사하지 않고 `MemberProfiles`의 본인 설정을 사용해야 한다. 현재 `acceptExisting()`의 `accountId`는 체험용 선택 값이며 운영 API에 그대로 전송하면 안 된다. 운영의 본인 확인은 `Auth.acceptExistingInvitation`의 서버 세션에서만 유도한다.

새 계정 → 기존 계정 → 새 계정으로 전환하면 비밀번호 입력 DOM을 버린다. 기존 계정은 비밀번호를 수집하지 않는다. 종료/만료 초대는 폼을 제공하지 않고 제출 시 현재 상태를 재검사한다. 이미 있는 다른 역할이나 정지 소속을 바꾸거나 재활성화하지 않는다. 기존 가상 사용자 역할·기록·첨부 저장 키는 유지한다. 실제 계정 복구와 시스템 설치는 이번 작업 범위가 아니다.

- `tests/onboarding-browser.mjs`: 로그인 입력 처리, 초대→수락→목록, 취소→재초대→필터, Escape와 포커스 복귀, 390/320px 가로 넘침, 새로고침 초기화, 보호자 메뉴 분리, 기존 대화 진입을 브라우저에서 검증한다.
- 같은 브라우저 테스트에서 API·외부 네트워크 요청 없음, 새 입력이 웹 저장소와 기존 기록에 반영되지 않음을 검사한다.
- 최신 `tests/onboarding-browser.mjs`: 6개 검증 묶음 통과. 기존 계정 경로의 비밀번호 폐기·잘못 선택한 계정/변경된 역할 거부·320/390px·Enter 제출·역할/저장소 비변경을 추가했다. 첫 실행 실패는 역할 전환 전의 세션 UI 상태를 잘못 비교한 테스트 기준점 문제였다. 센터 화면에서 흐름을 시작한 직전 상태와 비교하도록 고쳤으며 데이터 보존 검사는 유지했다.
- `tests/layout-browser.mjs`: 320~1440px 8개 너비의 기존 계정/선택 정보 16조건을 더해 179조건 통과, 넘침/브라우저 오류 0건. 화면을 직접 확인했으며 선택된 전체 이메일의 줄바꿈도 검증했다.
- `npm run test:server` 207개, `npm run check`, `npm run build`, `git diff --check` 통과. 서버 서비스·SQL·인증 HTTP 경로는 이번 단계에서 변경하지 않았다. 브라우저 스킬로 별도 세션의 페이지 로딩·스크린샷·오류·주요 메뉴를 확인했다. 이 결과는 실제 세션 인증·메일·운영 DB·기기 간 연결의 증거가 아니다.
- 스크린샷과 검증 결과는 git에서 제외된 `test-results/onboarding-*`에 생성한다. 브라우저 테스트는 설치된 Playwright 모듈 경로와 격리 브라우저의 CDP 주소를 `PLAYWRIGHT_MODULE`, `CDP_URL`, `APP_URL`로 받는다.
