# 상세 기록·평가·공유본 서버 저장

2026-10-01. 소통 중심 개편안 P1의 서버 내부 저장 단계다. API·브라우저 연결 및 운영 배포는 아직 진행하지 않았다.

## 현재 구현

`Records`는 현재 담당 치료사만 기록을 작성·조회·미리보기·공유하도록 한다. 기본 3항목(활동·반응·다음 계획), 상세 관찰, 최대 20개 평가값, 내부 메모, 보호자용 요약, 가정 활동 안내, 목표·일정 ID, 참고한 대화 ID를 저장한다.

내용을 편집할 때마다 새 수정본을 생성한다. 이전 수정본과 그 측정값·대화 참조는 보존된다. 저장 중에는 세부 행을 추가하고, 트랜잭션을 끝내기 전에 수정본을 확정(`sealed`)한다. 확정 이후 DB에서도 본문 변경·삭제와 측정값·참조의 추가를 거부한다. 미확정 수정본을 커밋하려는 경우에도 실패한다. 정정은 새 수정본으로 남기며, 장기 보존·파기 정책과 관리자 삭제 기능은 아직 구현하지 않았다.

공유에는 저장된 수정본을 사용한다. 공유 요약을 요청 본문에서 새로 받지 않는다. 현재 보호자 목록과 담당 관계 버전까지 미리보기에서 반환하고, 확정할 때 원본 수정본·관계 버전·보호자 목록이 모두 같은지 확인한다. 하나라도 달라지면 다시 확인해야 한다.

공유본에는 제목·요약·날짜·가정 활동 안내와 선택한 첨부 목록만 복사한다. 내부 메모·상세 관찰·평가 원문·참고 대화 목록·비공유 파일은 보호자 응답에 포함하지 않는다. 공유본과 수정본의 연결, 당시 수신자, 대화 카드, 처리 영수증을 같은 트랜잭션에 저장한다. 재공유하면 이전 카드는 기존 정책대로 종료되며 답변은 작성 당시 카드 ID를 유지한다. 공유 철회 후에도 원본 수정본은 보존한다.

## 서비스 계약

| 메서드 | 입력·동작 |
| --- | --- |
| `save(actor, input)` | `conversationId`, `recordId`, `clientId`, `expectedRevision`, `content`, `expectedGoalRevision?`, `expectedAppointmentRevision?`. 신규 작성은 예상 수정본 0이며, 수정은 현재 수정본 번호가 일치해야 한다. 부분 수정이 아니라 정규화된 전체 내용을 저장한다. 목표·일정의 예상 수정본은 작성 중 맥락 변경을 검사한다. |
| `get(actor, input)` | 대화방·기록 ID로 현재 수정본 조회. `revision`을 주면 해당 이전 수정본 조회. |
| `list(actor, input)` | 현재 열람 가능한 기록의 제목·날짜·상태·수정본 번호. `after` 생성 순번과 `limit`(최대 100)으로 페이지 조회. |
| `preview(actor, input)` | 기록 ID로 공유 가능한 저장본과 현재 수신자를 확인한다. `recordRevision`, `relationshipsVersion`, `recipientIds`, 공개할 내용만 반환한다. |
| `publish(actor, input)` | 기록·요청 ID와 미리보기의 `expectedRevision`, `expectedRelationshipsVersion`, `recipientIds`를 확인한 뒤 공유한다. |

저장·공유의 동일 요청 ID 재시도는 기존 영수증을 반환한다. 예전 저장 요청을 재전송해도 최신 수정본을 되돌리지 않는다. 영수증은 당시 처리 결과이며 최신 화면은 별도로 다시 조회해야 한다. 다른 내용·다른 대화방에 같은 요청 ID를 쓰면 충돌로 거부한다. 재시도도 현재 담당 관계와 과거 열람 권한을 통과해야 한다.

빈 초안은 `status: draft`로 저장할 수 있다. 018부터 작성 중인 측정 행은 값 `null`과 미완성 항목·단위·조건을 보존하고, 관찰 상태 미선택/작성 중 가정 활동도 초안에 남긴다. 미완성 목록은 초안 전용 열에 저장하며 확정 측정 테이블에 섞지 않는다. 정식 기록은 실제 작성 내용과 완전한 측정 행이 있어야 하고, 공유에는 정식 기록 상태와 보호자용 요약이 필요하다. 미입력·미관찰·해당 없음은 0으로 바꾸지 않는다. 측정값 0은 보존하지만 무한대·NaN·숫자 강제변환/명시적 관찰 모순은 초안에서도 거부한다. 수치 해석이나 임의 점수·AI 요약은 생성하지 않는다. 도구·항목·단위·조건은 각각 보존하지만 서버의 변화 비교 조회 서비스는 아직 연결하지 않았다. [초안 보존·완성 경계와 검증](record-draft-completion.md)을 참고한다.

009에서 `content.attachments?: [{ id, share? }]`를 추가했다. 최초 연결은 본인의 검사 완료 서버 UUID만 허용하고 `share`는 기본 false다. 새 수정본은 전체 목록을 저장하므로 생략/빈 배열이면 파일이 없지만 옛 수정본·공유본의 파일은 유지한다. 파일만 있는 빈 초안을 정식 기록의 실제 내용으로 판단하지 않는다. 미리보기에는 선택 파일만 반환하고 원본/공유본에서 정확한 수정본을 지정해 파일을 연다. [첨부 연결·접근 계약](media-binding-storage.md)을 참고한다.

## 권한·데이터 연결

- DB의 현재 사용자·센터 소속·아동 담당 관계를 공통 `Conversations.inRoom`에서 확인한다. 보호자는 임상 원본 조회 권한이 없고, 센터 관리자도 원문에 접근하지 못한다.
- 새 기록 생성 시 대화방 순번 하나를 내부 경계로 예약한다. 공개 메시지는 만들지 않는다. 이 경계로 담당자 교체 이전의 미공유 초안도 `from_now` 열람 범위에서 제외한다. 메시지 순번에는 간격이 생길 수 있으므로 순번 차이를 메시지 개수로 계산해서는 안 된다.
- 목표·일정·참고 대화는 같은 센터·아동 대화방에 속해야 한다. 참고 대화는 현재 치료사가 열람할 수 있어야 한다. 일정 하나에 두 개의 현재 기록을 연결할 수 없다.
- `Goals`, `Appointments`의 서버 작성·변경·목록·수정본 보존과 일정 충돌 검사를 구현했다. 새 기록 수정본은 당시 목표/일정 수정본과 `goalSnapshot`, `appointmentSnapshot`을 보존한다. 기존 기록의 알 수 없는 당시 맥락은 null로 남긴다. 화면/API 연결은 후속 작업이며 [목표·일정 서버 계약](care-context-storage.md)을 참고한다.
- 과거 공유본의 수신자 테이블은 공유 당시 확인한 대상의 이력이다. 이후 다른 보호자를 `all` 범위로 연결하면 방의 기존 공유 카드를 볼 수 있는 현재 관계 정책을 유지한다. 수신자 이력이 영구적인 별도 접근 명단을 뜻하지 않는다.
- 기존 요약 전용 공유본은 그대로 보존한다. 원본이 없는 공유본에서 임상 기록을 추측해 만들지 않는다. 같은 ID를 새 임상 원본으로 덮어쓰려 하면 명시적인 이관 경로가 필요하다는 오류를 반환한다.

## 파일과 실행 증거

| 파일 | 변경 |
| --- | --- |
| `server/migrations/005-records.sql` | 목표·일정 참조, 기록·불변 수정본·평가·대화 참조, 공유 연결·수신자·처리 영수증, 수정본 확정 제약 |
| `server/records.mjs` | 입력 검증, 원본 저장·조회·미리보기·확정, 충돌·재시도·권한 처리 |
| `server/conversations.mjs` | 같은 트랜잭션 안에서 저장본과 대화 카드 연결, 공개 가정 활동 표시, 원본 확인을 우회하는 요약 공유 차단 |
| `src/record-fields.js`, `src/domain.js` | 화면의 관찰·평가 정규화와 정식 기록 내용 유무 규칙을 순수 함수로 분리해 서버에서 재사용. 기존 화면 동작은 유지 |
| `server/tests/records.test.mjs` | 기록·공유·권한·복구·DB 제약·이전 스키마 보존 13개 테스트 |
| 기존 서버 테스트 3개 파일 | 005 마이그레이션 적용 목록과 이전 데이터 업그레이드 검증 유지 |

실행 결과:

- `npm run test:server`: 기존 40개와 기록 13개, 총 53개 통과.
- `npm test`: 기존 로컬 검증 23개 통과.
- `npm run check`: JavaScript 구문 검사 통과.
- `tests/communication-browser.mjs`: 독립 브라우저에서 소통·복수 평가·공유·사진/영상·실패 복구·320/390px·키보드 관련 8개 시나리오 통과. 새 서버를 연결한 검증은 아니며, 공통 검증 함수 분리 후 기존 UI의 회귀 검사다.
- 001~004 스키마의 기존 공유 요약·답변을 005 적용 후 보존했고, 원본이 없는 데이터를 새 임상 기록으로 만들지 않았음을 확인했다.

서버 검증은 테스트 전용 인메모리 PGlite에서 수행했다. 실제 PostgreSQL 여러 연결의 잠금 경쟁과 운영 장애 복구 검증은 남아 있다. 서버 모듈이 `src/record-fields.js`를 공유하므로 이후 서버 배포 패키지에도 해당 의존 모듈을 포함해야 한다.

## 남은 작업

피드백 단계 추가: [가정 활동 피드백 서버 저장](activity-feedback-storage.md)에 보호자 수정본·내부 검토·당시 인용/참조 버전 보존을 구현했다. `Records.save`에서 피드백을 참고할 때는 `referenceFeedbackRevisions: [{ messageId, revision }]`으로 확인한 버전이 필요하고, 조회의 `referenceSources`에 당시 버전을 반환한다. 목표·일정 단계에서는 당시 수정본 저장과 `CONTEXT_CHANGED` 검사를 추가했다. 해당 단계의 검증은 서버 80개·로컬 28개였다. 위 53개/23개는 기록 단계 완료 당시 결과이며 최신 파일 단계의 결과는 아래와 같다.

1. [비공개 임시 업로드 기반](media-upload-storage.md)과 [원본 첨부 연결·선택 공유 접근](media-binding-storage.md)을 구현했다. 해당 단계는 서버 122개·로컬 29개가 통과했으며 이후 최신 전체 결과는 [서버 기반 문서](server-foundation.md)를 참고한다. 실제 검사/저장 엔진·파일 장기 보존/파기·전체 용량 통제는 남아 있다. 기존 로컬 사진/영상 기능은 유지되며 새 서버 서비스와 연결되지 않았다.
2. [아동/계정 기본정보·기존 계정의 센터 연결](profiles-provisioning.md)도 구현했다. 국내 운영 환경·메일·최초 관리자/계정 복구·백업 준비는 남아 있다.
3. 마지막으로 API·화면의 서버 연결과 서로 다른 기기의 전체 흐름 검증. 연결 시 `expectedGoalRevision`, 연결 일정의 `expectedAppointmentRevision`을 반드시 전달한다. 기존 내부 호출의 호환 경로는 미전달 시 저장 시점의 최신 맥락을 연결하므로 화면에서 확인한 맥락을 보장하지 않는다.
