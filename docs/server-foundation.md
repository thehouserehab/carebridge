- `MemberProfiles`, `Children`에서 센터별 본인 표시명·아동 등록/운영 프로필·기준일이 있는 선택 연령·분리된 가족 관심사를 저장한다. 가족 관심사는 현재 보호자/치료사에게만 제공한다. `Auth.acceptExistingInvitation`은 본인 세션/이메일·대상 센터/역할·현재 발급자·초대 만료를 확인해 기존 계정의 소속을 연결한다. 정지 소속 복구·역할 교체·아동 자동 연결은 하지 않는다. [기본정보·기존 계정 연결 계약](profiles-provisioning.md)을 참고한다.

**아직 구현하지 않은 항목:** 계정/기존 계정 체험 화면의 실제 인증 연결과 메일 전달, 구성원/아동 기본정보 API·화면 서버 연결, 센터 최초 관리자 CLI의 운영 배치/실제 발급 및 정지 소속 해제의 운영 경로, 계정 복구·다중 기기 세션 관리 화면, 담당 관계·대화·기록·피드백·목표/일정/파일 HTTP API와 화면 연결, 운영 파일 승인·운영 영구 매체/객체 저장 어댑터·durable queue·장기 보관/영구 삭제 정책·과거 승인 파일 재검사·미지원 형식/권리·실제 업로드 상태 UX, 기존 UI의 서버 어댑터, 실시간 전달·재접속 UI, 운영 백업·복원·국내 인프라. 저장 서비스가 있어도 현재 웹앱에서 다른 기기와 대화할 수 있다는 뜻은 아니다. 과거 열람 선택에 관한 센터의 운영 정책도 확인이 필요하다.

## 트랜잭션과 권한 계약

`Conversations`와 `Auth`는 `{ transaction(work) }` 인터페이스를 받는다. 운영에서는 `postgresDatabase(config)`로 node-postgres 연결 풀을 구성한다. 연결 정보는 서버 환경변수로만 주입하며 브라우저와 로그에 노출하지 않는다. HTTPS/TLS, 최소 권한 DB 사용자, 인증서 검증 설정은 실제 호스팅 환경에서 검증해야 한다. 마이그레이션용 DB 계정과 런타임 계정도 운영 설정에서 분리해야 한다.

모든 공개 저장 메서드의 identity는 **인증된 서버 세션이 결정한 내부 `userId`, 선택된 센터 `centerId`**다. role은 호출자가 넘겨도 권한으로 사용하지 않는다. `Auth.authenticate()`가 세션 쿠키를 내부 사용자 ID와 활성 센터 소속으로 변환하지만, 대화 HTTP API는 아직 연결하지 않았다. 따라서 요청 본문·임의 헤더의 userId를 그대로 전달하는 HTTP 래퍼를 만들면 안 된다. SQL 쿼리 권한 검증이며 DB RLS나 완성된 운영 인증 체계라고 부르지 않는다.

인증 경계의 세부 규칙:

- `provisionAccount()`은 내부 호출 전용이며 공개 회원가입 라우트가 아니다. 먼저 센터가 `cb_users`를 승인해야 하며, 센터 소속·역할은 별도 관계 프로비저닝으로 활성화해야 한다.
- 비밀번호는 Node `scrypt`로 해시하고 salt와 비용 파라미터를 함께 저장한다. 비밀번호·세션 원문·로그인 요청 본문은 감사 이벤트에 넣지 않는다.
- 존재하지 않는 이메일도 동일한 비밀번호 검증 경로를 거친다. 잘못된 자격 증명은 하나의 공개 오류로 반환하고, 활성 계정은 5회 실패 후 15분 잠근다.
- 세션 쿠키는 `HttpOnly; SameSite=Lax; Path=/`이며 운영 모드(`NODE_ENV=production` 또는 `SECURE_COOKIES=true`)에서 `Secure`를 강제한다. DB에는 세션 토큰의 SHA-256 해시와 만료·폐기 시각만 남긴다.
- 초대 토큰은 `randomBytes`로 만들고 SHA-256 해시만 저장한다. 만료·수락·철회된 토큰은 다시 사용할 수 없으며, 기존 계정 이메일은 초대 수락으로 덮어쓰지 않는다.
- 로그인·세션 조회·로그아웃·초대 HTTP 경계를 노출한다. 대화 API가 추가될 때에도 세션에서 얻은 `userId`를 사용하고 브라우저가 보내는 role/userId를 신뢰하지 않아야 한다.
- 기존 계정 연결은 새로운 내부 `acceptExistingInvitation`을 사용한다. 본인 세션과 초대를 함께 확인하며 비밀번호·이메일·계정 ID·세션을 바꾸지 않는다. 실제 수락 기록을 쓰는 시점의 만료도 검사한다. 새로운 HTTP 경로는 추가하지 않았다.

새 임상 기록의 공유는 `Records.publish`에서 저장된 수정본과 현재 수신자를 검증한 뒤 `publishInRoom`으로 연결한다. 수정본과 공유본의 외래 키 연결·당시 수신자·선택 첨부 목록·대화 카드·처리 영수증이 함께 커밋된다. 기존 요약 전용 자료는 원본이나 첨부 연결을 만들어 내지 않는다. 어떤 내부 도우미도 검증 없이 HTTP 공유 API로 노출하면 안 된다.

하나의 대화 행을 잠근 상태에서 권한 조회·변경·순서 부여를 완료한다. 대화방별 저장 순서를 커밋 순서와 맞춰 재접속 커서가 늦게 커밋된 메시지를 건너뛰지 않게 한다. 처음에는 같은 방의 조회도 짧게 직렬 처리한다. 많은 동시 사용자를 위한 성능 보장은 없으며 부하 측정 후 일관성 계약을 유지하며 개선할 수 있다.

참여자의 `first_sequence`는 기본값 없이 명시해야 한다. 관계 서비스는 전체 이력(`all`), 연결 이후(`from_now`), 현재 범위 유지(`preserve`)를 명시적으로 받고, 신규/재연결의 `preserve`를 거부한다. 임상 저장은 **대화 행 → 현재 사용자/소속 검증 → 참여 관계 행** 순서로 잠근다. 일정 저장·담당 관계 교체는 그 앞에 **센터 일정 잠금**을 추가해 다른 아동과의 자원 충돌을 검사한다. 조회를 포함한 일정 서비스도 센터 일정 잠금 안에서 일관된 목록 버전을 읽는다. 직접 SQL 유지보수도 자원 변경 시 센터 우선 순서를 따라야 한다. 연결 해제 시 과거 메시지 보존을 위해 관계를 비활성화한다. 직접 ID 조회·답변·인용·읽음에도 같은 열람 시점을 적용한다. 서비스가 센터의 과거 열람 동의·인수인계 정책을 대신 결정하지는 않는다.

순번 커서는 신규 메시지를 찾기 위한 값이며 공유 철회와 내부 검토 변경을 나타내지 못한다. 따라서 별도 `revision`을 제공한다. 메시지·읽음·공유·검토·참여 범위가 달라지면 revision이 증가한다. 클라이언트가 이전 revision으로 요청하면 `resetRequired: true`를 반환한다. 향후 클라이언트는 기존 투영 내용을 교체 조회하고 권한 거부·로그아웃 때 캐시를 지워야 한다. 서버 변경 이벤트/폴링과 브라우저 캐시 삭제는 아직 구현하지 않았다.

설계 참고: [node-postgres 트랜잭션](https://node-postgres.com/features/transactions), [PostgreSQL 명시적 잠금](https://www.postgresql.org/docs/current/explicit-locking.html), [PGlite API](https://pglite.dev/docs/api). 한 연결에서 전체 트랜잭션을 실행하며, SQL 입력값은 파라미터로 바인딩한다.

## 전체 개편안 완료 감사와 다음 작업

2026-10-07 최신 [전체 완료표](communication-acceptance.md)에서 모든 P0 요구·사람/실물 관측·P1 실제 연결·조건부 P2를 분리했다. 사용자는 **센터·보호자의 실제 자료 베타를 로컬 E 드라이브로 진행**, 사업화 후 유료 데이터센터를 검토하기로 결정했다. [전용 E 파일 IO/NTFS 디렉터리 준비](local-beta-storage.md)를 확인했지만 운영 DB·계정·키·독립 백업·외부 접속/서비스 활성화는 아직 아니다. 아래 공급자 미정 문구는 이전 클라우드 검토 당시 상태이며, 현재는 유료 공급자 선택을 사업화까지 보류한다. API 마지막 제약과 실제 베타 보호/복구 요구는 유지한다.

직전 후속은 [015 센터 자원 제한](media-resource-limits.md)이다. 센터 전체의 보수적 용량 예약·빈도·대기량 정책과 명시적 설정/중지를 추가했다. 운영 값을 선택하지 않았으며 미설정 신규 할당은 거부한다.

2026-10-06 직전 후속은 [016 보류 검사 검토·재개](media-work-reviews.md)다. 현재 센터 관리자의 명시적 복구 사유/확인 한 건으로 추가 검사 한 번을 부여하며 누적 횟수는 유지한다. 영수증/재개 원자성·중복 접수·현재 원 소유자/열람 범위·최대 추가 3건/누적 8회·SQL 우회 차단과 임상 내용 없는 운영 조회를 구현했다. 재개는 파일 승인이 아니며 전체 검사/후보 저장을 다시 수행한다. 001~015/기존 원본·증거·큐 필드를 보존하고 API/화면/운영 자동 시작/배포는 하지 않았다. 구성요소별 과거 숫자/미구현 기록과 현재 판정은 구분한다.

최신 구현은 [작업자 종료·상태·복구 경계](media-worker-lifecycle.md)다. 검사/정산 후 격리 회수를 확인하고 중단 요청과 오류가 겹쳐도 정상 종료로 숨기지 않는다. 임상/식별정보 없는 process-local snapshot과 전용 프로세스의 opt-in SIGTERM/SIGINT 처리를 추가했다. 서버 518개·실제 PostgreSQL/자식 신호 35개·native 파일 준비 결합 18개·로컬 61개를 통과했다. SQL/권한/원본·UI·API·배포는 유지하며 실제 운영 supervisor·영속 heartbeat/경보·자동 시작/재시작은 아직 아니다.

후속 [보존·백업·복원 준비 검토](recovery-readiness.md)에서 DB/원본·후보/fence/권한/키를 같은 복원 묶음으로 다루는 범위와 BR-01~10 검증 기준을 정리했다. 이는 설계·결정 단계이며 운영 backup/restore 구현이나 실제 복원 성공이 아니다. 공급자/월 예산, 기존 데모의 보존/이관 범위와 보관/파기·RPO/RTO가 미정이다. 기존 데이터/SQL·권한·서비스를 바꾸거나 유료 자원을 만들지 않았다.

최신 후속은 [정지형 합성 DB·첨부 복원](recovery-native-verification.md)이다. 실제 PG 18.6 dump/restore·새 파일 경로에서 구조화 임상/공유 이력·전 DB 지문과 실제 권한·함수/제약/trigger, 원본/후보 PNG·삭제 fence를 확인했다. native 9개와 권한/CHECK/NOT NULL 약화 역검증, 신규 암호화 계약 19개 포함 서버 538개를 통과했다. 운영 CLI/스케줄러·기존 자료 이관·세션/삭제/원장 cutover·별도 cluster role·영구 매체/키/국내 통제 및 마지막 API 연결은 미완료다.
