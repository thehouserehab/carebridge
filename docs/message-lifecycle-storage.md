# 일반 메시지 수정·삭제 — 서버 저장 경계

2026-10-08. 사용자 선택인 **‘카카오톡과 같은 방식’**을 기존 PostgreSQL 내부 서비스에 이어서 반영했다. 로컬 화면은 [이전 단계](message-lifecycle.md)에 있다. **새 HTTP API·운영 DB 전환·기기 간 전달·배포를 완료한 것은 아니다.** 실제 자료 수집과 외부 접속은 독립 백업 준비 전까지 계속 보류한다.

## 2026-10-08 서버 표시 계약 후속

로컬 화면에는 있지만 서버 조회에 없던 **첨부 요약·상대 읽음·일반 소식 반영 확인**을 연결했다. 수정 전 새 실제 서비스/PGlite 시험에서 사진만 보낸 원문은 `body:''`로 보존됐으나 답변의 `quote.preview`가 `undefined`여서 실패했다. 수정 후 같은 시험은 `사진 1장`으로 통과한다. 발신·수정·삭제 정책과 SQL 001~021·권한 v5는 변경하지 않았다.

## 저장 구조와 동시성

기존 `cb_messages`는 이미 발신 원문과 파일 목록을 변경할 수 없는 구조다. 이를 풀지 않고 **신규 `020-message-lifecycle.sql`만 추가**했다. 기존 001–019 파일은 이번에 수정하지 않았다.

- `cb_message_text_heads` / `cb_message_text_revisions`: 현재 버전 포인터와 추가 전용 원문 이력. 기존 본문은 최초 버전으로 새 보조 테이블에만 복사한다.
- `cb_message_reply_versions`: 답변이 선택한 원문 버전. 기존 답변은 최초 버전으로 연결한다.
- `cb_message_hides`: 사용자별 숨김. 원문/다른 사용자의 상태를 삭제하지 않는다.
- `cb_message_change_requests`: 본문 없는 요청 해시·작업·결과 버전 영수증. 같은 요청 재시도는 한 번만 반영한다.
- `cb_record_text_sources`: 이미 봉인된 임상 참고의 메시지 버전. 기존 임상 내용/참고 ID/파일 목록을 다시 작성하지 않는다.

DB 시계·방 잠금·현재 담당/계정·과거 열람 경계·버전 확인·이력/포인터·감사 사건·영수증을 같은 트랜잭션으로 처리한다. 연결이 끊기거나 감사/영수증 저장이 실패하면 전체 롤백한다. 오래된 화면의 수정/삭제는 충돌로 거부하며 삭제 후 예전 수정 영수증 재시도로 본문을 되살리지 않는다. 관계 해제 후에는 영수증을 알고 있어도 접근할 수 없다.

버전 이력·숨김·인용·임상 참고·영수증은 SQL 변경/삭제가 차단되고 현재 포인터도 순차 증가만 허용된다. 이력만 추가하고 포인터를 누락하는 경우와 임상 참고 버전 누락은 커밋 시 거부한다.

### 최소 DB 권한

권한 정책을 **v4 / 검토된 61테이블·50함수**로 갱신했다. 앱은 신규 보조 테이블 SELECT/INSERT 및 포인터의 `current_revision` 열 UPDATE만 가진다. 이력 UPDATE/DELETE/TRUNCATE, 트리거 함수의 직접 실행 권한은 주지 않았다. 작업자/초기 계정 발급 역할은 새 대화 보조 테이블에 접근하지 않으며 백업 역할은 SELECT만 가진다. 앱의 기존 감사 기록 권한은 **INSERT-only**로 유지했다.

이것은 DB 역할의 권한 분리다. 사용자/센터별 RLS 격리나 운영 서비스 계정·OS 격리를 완료했다는 의미는 아니다. 사용자 권한은 여전히 인증된 서버 신원과 내부 서비스의 현재 관계 확인을 거쳐야 한다.

## 사진·영상과 임상 보존

전체 삭제 또는 본인 숨김 후에는 원래 메시지를 통한 파일 다운로드를 허용하지 않는다. 파일 UUID나 업로드 소유 여부를 우회 권한으로 쓰지 않는다. 파일을 연 다음에도 현재 권한을 다시 확인하며, 그 사이 삭제되면 핸들을 닫고 스트림을 반환하지 않는다.

이미 임상 기록에 고정한 참고 파일에는 별도의 내부 `record-reference` 앵커를 사용한다. **현재 권한과 과거 열람 범위를 충족한 치료사**가 해당 기록의 해당 버전에서 실제로 참고한 파일만 읽을 수 있다. 보호자는 이 경로에 접근하지 못한다. 대화 삭제가 임상 원문/파일의 영구 파기를 의미하지 않는 이유다.

같은 기록의 현재 버전에 남아 있는 참고는 이후 저장에서도 당시 원문을 유지한다. 참고를 제거한 뒤 오래된 버전의 숨김/삭제된 소식을 다시 추가하는 우회는 허용하지 않는다. 공유 미리보기/보호자 발행본에는 비공개 참고 본문이나 내부 메모를 넣지 않는다.

### 실제 E 결과와 재검증

최종 실행 `4940f62e-d66b-4133-bdb8-e5ffcdfc4327`의 기계 결과 (로컬 검증 산출물: `test-results/database-privileges-results.json`)는 `passed:true`, `scenarioCount:40`, `failure:null`이다. 원본/복원 클러스터 모두 중단됐고, 자식2개의 실제 종료 및 최종 실행의 합성 자격증명·TLS 키 정리를 확인했다. 비공개 진단 루트는 `E:/CarebridgeBeta\private\checks\postgres-check-4940f62e-d66b-4133-bdb8-e5ffcdfc4327`이며 운영 서버로 시작하지 않는다.

신규 실제 메시지 사례6은 동시 수정 한 승자·동일 수정 재시도 한 영수증/감사·수정 대 전체 삭제 한 승자·임상 저장 대 수정의 선택 버전 보존·다른 연결의 본인 숨김/페이지 초기화·**자기 시험 연결만 종료**한 뒤 원자적 롤백/같은 요청 재시도를 확인했다. 임상 보존과 새 보조 테이블은 이후 별도 클러스터의 전체 테이블 지문·권한/함수/트리거 복원·재시작 검사에도 포함됐다. E 검사에서 작업자 scanner/decoder는 합성 상대이며 이번에는 실제 ClamAV/FFmpeg 전체를 다시 실행한 것이 아니다.

재검증 명령은 다음과 같다. `--powershell`에는 설치된 `pwsh.exe`의 실제 절대경로를 사용해야 한다. 명령은 새 합성 검사 클러스터만 만들며 실제 자료나 운영 서비스를 활성화하지 않는다.

```powershell
npm run test:database-privileges:e-drive -- --base E:/CarebridgeBeta --powershell "<pwsh.exe 절대경로>" --confirm-synthetic-e-drive
```

전체 서버 검사 이후 시험용 감사 관측 경로를 바꾼 세 파일은 별도 `node --check`와 위 최종 실제 E 실행으로 확인했다. 제품 서비스/마이그레이션/권한 계약의 최종 코드는 서버737 전체 결과와 동일하다.

최종 산출물 감사에서도 이전 공개 소스 SHA-256 `3ecf393417a9dc833d2c428f3fa23d90dbc4cb16310a4c15fd04968e3382746f`의 **33개 파일 모두 변경 없음·소스/dist 바이트 일치**를 확인했다. dist의 추가 파일은 빌드 메타데이터뿐이다. 변경 문서5개는 엄격 UTF-8·로컬 파일 링크147개, `git diff --check`를 통과했다. 최종 E 실행의 원본/복원 `postmaster.pid` 부재와 TLS 디렉터리 제거도 재확인했다. 새 브라우저 화면 검사나 운영 배포의 증거는 아니다.

### 중간 실패와 수정

첫 전체 서버 실행은 기존 테스트 두 경계에서 실패했다. 활동 피드백 통합 검사의 일반 답변 참고 기대값에 새 버전/본문/첨부 투영을 반영했다. 과거014 업그레이드 검사는 새020 투영을 요구하는 현재 메시지 서비스를 014 스키마에 실행하지 않고 당시 SQL/파일 결합 fixture로 작성하도록 수정했다. 추가한 버전 기대값 이름을 한 차례 잘못 쓴 집중 실패도 `version`으로 바로잡았으며 최종 전체737에 포함됐다. 기존 자료 불변 비교나 권한 제한을 제거하지 않았다.

첫 E 역할 실행 `70cbfa14-bf3f-4616-8ba6-07d5bfc8cee6`은 27개까지 확인 후 새 메시지 검사에서 멈췄다. 시험 코드에 앱의 INSERT-only 감사 테이블을 읽는 경로가 있어, 권한을 확대하지 않고 **명시적 시험용 소유자 READ ONLY 관측 경로**로 분리했다. 원 실행의 일반화된 오류만으로 SQLSTATE까지 확인했다고 주장하지 않는다. 해당 실행은 전체 통과나 복원 증거가 아니며 소스 클러스터 중단은 확인됐다. 실패 진단 경로의 합성 자료/합성 TLS fixture는 비공개 E 검사 경로에 남아 있다.

## 남은 위험과 다음 순서

1. 운영 보존 기간·정식 파기/법적 삭제·백업 속 삭제 반영 정책을 확정해야 한다. 현재 삭제는 대화 열람 제한이며 원문/파일의 물리 파기가 아니다.
2. 독립 백업 매체·운영 키 복구·권한/삭제 원장 대조와 실제 복구 절차가 필요하다. 같은 E 디스크의 복원 검사는 독립 백업이 아니다.
3. 운영 Windows 서비스/별도 계정·감독/경보, 실제 사용자/실물 기기의 검증과 P0 사람 관찰은 아직이다.
4. 위 비API 준비 이후에만 세션 기반 API와 UI 어댑터를 연결한다. 내부 서비스의 레거시 v1 호환 입력을 그대로 공개 API로 노출하지 않고 선택 버전·요청 ID·삭제 확인을 명시적으로 고정해야 한다.

P104 및 전체 개편 목표는 계속 진행 중이다. 이번 변경을 인증된 실제 사용자 채팅·다른 기기로 전달되는 베타 서비스로 표시하지 않는다.
