# 사진·영상의 비공개 업로드 기반

2026-10-02. 소통 개편 P1의 파일 처리 중 **연결 전 임시 업로드**를 구현했다. 이 문서는 008 단계의 계약이며 이후 009의 [원본 연결·공유 접근](media-binding-storage.md)을 추가했다. 전체 서버 첨부 기능이 완료된 것은 아니다. API·화면 연결·배포는 하지 않았으며, 기존 브라우저 사진/영상과 저장 키는 유지한다.

## 현재 상태와 다음 연결

2026-10-05 최신 [분리 저장·불변 증거·원자적 사용 가능 전환](media-preparation-storage.md)은 원본/후보 검사 결합을 실제 비공개 파일 저장과 `MediaUploads.inspect`에 연결한다. 명시적 `preparation: MediaPreparation`만 새 파일을 처리하며 기본 미설정 시 격리한다. 원본/첨부 ID·권한/공유 이력을 유지하고 새 파일은 후보만 제공한다. 저장 실패·임대 회수·취소 후 늦은 작업도 검증했다. **아래 scanner.inspect 계약은 008의 과거 기록이며 현재 새 파일 승인 경로로 사용할 수 없다.** durable queue·운영 저장/국내 통제·보존/파기·기기 검증은 남아 있고 API/화면은 마지막이다.

2026-10-05 [MP4·WebM 후보 처리](video-metadata-processing.md)의 구조 계약 24개·native 19개를 추가했다. 압축 영상/음성·회전·타이밍·위치 보존과 컨테이너 설명/촬영 시각 감소를 확인했지만 원본/후보 객체 저장·manifest·`inspect`에 연결한 것은 아니다. 익명화가 아니며 아래 008/009 상태와 기본 미설정 검사기를 유지한다.

이미지 후속으로 [공유용 메타데이터 처리](image-metadata-processing.md) v2를 추가했다. 원본 불변의 별도 후보 바이트·방향/프레임·지원 ICC RGB/회색 v2/v4 수치/고지를 보존하고 독립 색 비교·실제 픽셀/재생/변조 대조 27개를 검증했다. copyright/프로필 생성 날짜의 보존 예외가 있으며 익명화가 아니다. 이 구성요소를 본 업로드의 `inspect`, 객체 저장/manifest 또는 파일 승인에 연결한 것은 아니다. 영상·미지원 ICC/기기 표시·검사 결합·원본/변환본 수명·운영 준비는 계속 필요하다. 아래 008 단계의 원본 저장 계약/정책은 유지한다.

`MediaUploads`는 실제 바이트를 스트림으로 비공개 저장소에 기록하고 DB에 소유자·센터/아동·형식·용량·내용 해시·상태·처리 버전을 남긴다. `PrivateFileStore`는 로컬 파일 어댑터다. 유료 자원이나 외부 저장소를 만들지 않았다. 클라우드 어댑터가 없으며 국내 운영 저장소를 구성한 것도 아니다.

현재 단계에서 사용 가능한 동작은 임시 업로드 예약, 바이트 수신, 검사 요청, 업로더 본인의 검사 완료 파일 미리보기, 취소, 만료/실패 객체 정리다. 현재 참여자라도 다른 사람의 연결 전 파일을 볼 수 없다. 센터 관리자는 임상 파일 업로드/조회에 접근하지 못한다.

이후 009에서 검사 완료 파일을 대화 메시지·기록 수정본·피드백 수정본·선택한 공유본에 원자적으로 연결했다. 해당 서비스는 ID만 있는 첨부 목록을 받으며 원본의 현재 권한으로 파일에 접근한다. 연결된 `bound` 파일은 임시 만료/취소/정리에서 제외하고 원 소유자 미리보기 대신 `MediaAccess`로 연다. 실제 검사/저장 엔진과 보존/파기 정책은 남아 있다. 화면/API 연결은 이 저장 계층과 운영 준비 뒤의 마지막 단계다.

## 상태와 실패 복구

```text
예약 대기 → 수신 중 → 검사 대기 → 검사 중 → 사용 가능
               ↓          ↑          ↓
            재시도 대기    └─ 검사 실패/미설정
               또는             또는 거부
              거부

취소/임시 보관 만료 → 삭제 대기 → 실제 객체 삭제 → 삭제 완료
```

- 수신 중에는 실제 크기·전체 SHA-256·선두 형식 시그니처를 확인한다. 선언된 용량보다 커지면 즉시 스트림을 중단한다. 메모리에 파일 전체를 모으지 않는다.
- 크기·해시·형식 불일치는 거부된다. 스트림/저장 장애는 같은 예약 ID의 재시도 대기로 돌아간다. 요청 해시에는 정규화된 파일명·형식·크기·내용 해시가 포함된다.
- 검사 전에 파일 전체 해시를 다시 확인한다. 형식 시그니처는 형식 힌트일 뿐, 정상 디코딩이나 악성 파일 검사 완료를 뜻하지 않는다.
- 실제 검사기/디코더가 없거나 실패/시간 초과/불완전한 결과를 반환하면 검사 대기에 머문다. 검사를 생략하는 기본 승인 경로는 없다.
- 상태 변경은 예상 버전, 임시 작업 토큰, 임대 만료를 확인한다. 오래된 작업의 완료로 새 업로드를 덮어쓰지 않는다. 만료된 수신 작업은 새 객체 키로 재시도한다.
- 파일 바이트와 DB는 같은 트랜잭션에 묶을 수 없다. 바이트 쓰기 **전** 객체 추적 행을 저장하고, 바이트 쓰기 **후** 상태를 확정한다. 두 단계 사이 장애 시 실제 객체가 추적 행 없이 남지 않으며, 임대 복구/정리로 회수한다. DB 확정 실패는 성공 응답으로 반환하지 않는다.
- DB 삭제 의도를 먼저 남기고 실제 객체를 지운다. 삭제 실패/응답 유실은 추적 행을 유지해 재시도한다. 실제 파일이 없는 경우의 삭제도 성공으로 처리한다.
- 로컬 어댑터는 삭제 키에 작은 `.blocked` 차단 파일을 남긴다. 취소되기 전에 작업 토큰을 얻었던 프로세스가 뒤늦게 시작해도 객체를 다시 생성할 수 없다. 다른 저장 어댑터도 같은 삭제 후 재생성 방지 계약이 필요하다. 차단 파일/추적 행의 장기 보존 정리는 아직 구현하지 않았다.

## 입력·검사 정책

허용 형식은 기존과 같은 JPG·PNG·WebP·GIF·MP4·WebM이다. 사진 10MiB, 영상 50MiB를 넘을 수 없다. 경로 구분자·제어 문자·빈 파일명과 잘못된 SHA-256을 거부하며 파일명을 객체 경로로 사용하지 않는다.

업로드 준비 영역은 동일 센터/아동/소유자당 최대 24개·300MiB다. 여러 작성 중 화면을 위한 **임시 영역** 제한이며 기존 기록/메시지의 첨부 6개·합계 100MiB 제한을 바꾼 것이 아니다. 009의 연결 서비스와 DB에서도 후자의 묶음 제한을 검사한다. 연결된 파일은 준비 영역에서 제외하며 만료됐지만 아직 정리되지 않은 미연결 객체는 한도에 포함한다. 전체 센터/계정/인프라 용량 할당과 요청 빈도 제한은 운영 단계에서 추가해야 한다.

임시 예약의 기본 유효 시간은 24시간, 작업 임대는 5분, 스트림/검사 제한은 2분이다. 내부 구성으로 조절하며 클라이언트 요청 본문에서 변경하지 못한다. 이 24시간은 **아직 원본에 연결하지 않은 임시 파일**에만 적용한다. 치료 기록·공유본·연결된 첨부의 보존 기간을 결정한 것이 아니다. 실제 정리는 내부 `cleanup` 실행이 필요하며 자동 스케줄러는 아직 없다.

008 초기 단계는 서버 주입 `scanner.inspect`의 아래 결과를 검증했다. 현재 013에서는 이 단독 어댑터를 승인 경로로 거부한다. 아래 shape는 과거 증거와 새 준비 결과의 제한된 내부 요약용이며 요청에서 검사 결과를 받지 않는다.

- `verdict`: `clean / rejected`.
- `engine`, `engineVersion`: 식별용 제한 문자열. 외부 검사기의 오류 원문·자유 설명·파일명은 DB 감사/응답에 넣지 않는다.
- `policyVersion`: `carebridge-media-v1`.
- `clean`의 `media`: 확인한 MIME·양의 정수 가로/세로(각 8,192 이하·4천만 픽셀 이하). 영상은 양의 유한한 진행 시간(600초 이하)도 필요하다.

이 검사는 **어댑터 결과의 유효성**을 확인하는 계약이지 검사 엔진 자체가 안전하다는 증거가 아니다. 현재 전체 안티멀웨어·디코더 어댑터는 없고 테스트에만 가상 검사기를 주입했다. 이후 [로컬 ClamAV 통신 계층](media-scanning.md)을 구현하고 2026-10-04 [실제 엔진 13개 시나리오](clamav-native-verification.md)를 합성 환경에서 시험했다. 해당 클라이언트는 `inspect`가 없고 디코딩/업로드 승인에 연결하지 않으므로 기본값은 계속 검사 대기다. 일부 파일 수/크기·정의 갱신·취소는 검증했지만 모든 압축 폭탄·손상·다중 프레임·코덱·장애/운영 한도까지 확인하지 않았다. EXIF/GPS·영상 메타데이터 제거, 변환본/썸네일과 원본 보존 정책도 아직 구현하지 않았다. 실제 아동/건강 자료를 넣어도 된다고 판단하지 않는다.

## 내부 서비스 계약

모든 사용자 메서드의 `actor`는 인증된 서버 세션의 `{ centerId, userId }`다. 현재 사용자·센터 소속·아동 담당 관계를 DB에서 다시 검사한다. 역할 주장이나 다른 사용자의 업로드 ID로 접근할 수 없다. 임시 업로드의 생성 순번도 과거 열람 시작점에 포함해 `from_now` 재연결로 옛 임시 파일을 되찾지 못하게 한다.

| 메서드 | 계약 |
| --- | --- |
| `reserve(actor, input)` | `conversationId`, `clientId`, `file: { name, type, size, sha256 }`. 서버가 UUID를 발급한다. 같은 요청은 현재 상태를 반환하며 삭제된 예약을 되살리지 않는다. 다른 방/내용에 ID를 재사용하면 충돌한다. |
| `get(actor, input)` | `conversationId`, `uploadId`. 현재 관계를 가진 원 소유자만 상태를 조회한다. |
| `receive(actor, input, stream)` | `conversationId`, `uploadId`, `expectedVersion`, Node Readable. 실제 바이트 검증을 통과하면 검사 대기로 이동한다. 실패 코드와 재시도/거부 상태를 반환한다. |
| `inspect(actor, input, { signal? })` | 같은 ID·예상 버전. 명시적 전체 준비 서비스·별도 후보 저장/전체 재검증·불변 증거 확정 뒤에만 사용 가능 상태다. 미설정/실패 시 격리하며 public settle로 승인할 수 없다. |
| `open(actor, input)` | `conversationId`, `uploadId`, 선택 `range: { start, end? }`. 원 소유자의 유효한 사용 가능 임시 파일만 스트림으로 반환한다. 단일 바이트 범위와 전체 해시를 검사하고 IO 후 권한/상태를 다시 확인한다. |
| `cancel(actor, input)` | ID·예상 버전. 삭제 의도를 기록하며 동일 취소 재시도는 안정적이다. 연결된 `bound` 파일은 `FILE_IN_USE`로 거부한다. 임상 첨부의 영구 삭제 메서드가 아니다. |
| `cleanup({ limit? })` | 사용자 입력을 받는 공개 기능이 아닌 내부 유지보수 메서드. 최대 100개씩 만료 의도·객체 삭제·완료 확정을 처리한다. 제거/실패/완료 개수만 반환하며 임상 내용을 읽지 않는다. |

상태 응답에는 ID·파일명·형식·크기·상태·버전·제한된 실패 코드·만료만 포함한다. 객체 키·경로·해시·작업 토큰·검사 원문은 없다. `open`은 서버 내부 Readable을 반환할 뿐 URL을 발급하지 않는다. HTTP 연동에서는 세션·Origin/CSRF·제한 범위·빈도 제한, `Cache-Control: private, no-store`·`X-Content-Type-Options: nosniff`와 안전한 파일명 헤더를 적용해야 한다. 현재 HTTP 다운로드 경로는 없다. 이미 전송한 바이트/다운로드를 권한 해제로 회수할 수는 없다.

## 저장·데이터 안전 경계

`PrivateFileStore`는 명시된 절대 경로의 전용 폴더만 사용하고 프로젝트/공개 폴더·드라이브 루트·사용자 홈/임시 루트 자체는 거부한다. 상위 경로의 심볼릭 링크/Windows junction과 객체의 하드 링크를 거부한다. 객체는 임의 UUID 경로로 `O_EXCL` 생성하고 덮어쓰지 않는다. 스트림/파일 핸들은 성공·실패 모두 닫는다.

POSIX 생성 권한은 디렉터리 0700·파일 0600이다. **Windows ACL을 자동 구성하거나 검증하지는 않는다.** 별도 서비스 계정, 해당 계정만 쓸 수 있는 폴더, 디스크 암호화·백업/로그/지원 접근 통제는 운영에서 설정·검증해야 한다. 같은 권한의 악성 프로세스 또는 관리자까지 막는 보안 경계라고 주장하지 않는다. 디렉터리 변조와 전원/디스크 장애, 다중 프로세스·다중 호스트 정리 작업은 별도 검증이 필요하다.

008은 001~007을 수정하지 않는 추가형 마이그레이션이다. 기존 임상 내용/첨부 ID를 가져오거나 파일을 만들어 내지 않는다. 수정 불가 매니페스트·명시적 상태 전환·내용 없는 상태 이력·객체 추적을 DB 제약으로 검사한다. 임시 파일 삭제는 원본 행/상태 영수증을 물리 삭제하지 않으므로 파일명/내용 해시 등 메타데이터의 별도 보존·최소화/파기 정책이 남아 있다. 물리 파일 제거는 보안 삭제 또는 백업 파기를 보장하지 않는다.

- `npm test`: 29개 통과(기존 28개 + 시그니처 규칙 1개).
- `npm run check`, `npm run build`: 통과. 기존 로컬 UI·첨부 저장 구조를 다시 작성하지 않았다.
- 크기/해시/시그니처 위조·스트림 중단·검사 없음/거부/잘못된 결과/시간 초과·원 소유자/관계 권한·범위 읽기·저장 변조·예약/바이트 할당량을 확인했다.
- 이벤트 저장 실패의 DB 롤백, 바이트 기록 후 확정 실패의 추적 보존, 임대 재시도/옛 완료 거부, 삭제 장애/응답 유실 재시도·삭제 전후 생성 경쟁을 확인했다.
- 실제 임시 폴더의 쓰기/읽기/삭제를 실행했다. 경로/junction·덮어쓰기·내용 변조를 검사했으며 008 반영 후 기존 목표 수정본이 그대로 유지됐다. 테스트 폴더만 절대 경로·범위를 확인한 뒤 정리한다.
- 최초 테스트에서 `autoClose:false` 쓰기 스트림이 파일 핸들을 붙잡아 종료를 막았다. 쓰기를 별도 Writable로 바꾸고 명시적 닫기를 유지해 수정했다. 전체 102개 실행은 핸들 GC 경고나 정지 없이 끝났다. 첫 테스트에 시간 제한을 두어 해당 회귀가 무기한 대기로 숨지 않게 했다.

위 102개/29개는 008 단계 당시 결과다. 이후 [첨부 원본 연결·공유 접근](media-binding-storage.md)과 [기본정보·기존 계정 연결](profiles-provisioning.md)을 추가했다. 최신 전체 결과는 [서버 기반 문서](server-foundation.md)를 참고한다. 연결 파일은 과거 이력 보존을 위해 임시 정리에서 제외한다.

위 008 단계 서버 DB 시험은 단일 연결 인메모리 PGlite였다. 이후 2026-10-04 실제 PostgreSQL 여러 연결 8개·ClamAV 합성 13개·[FFmpeg 디코더 38개](media-decoder-verification.md)를 별도 실행했다. 두 검사 모듈은 파일 승인에 통합하지 않았고 metadata 제거·운영 객체 저장소·기기 간 파일 전송 시험은 하지 않았다. 브라우저 검사 결과를 서버 첨부 전송 완료 증거로 사용하지 않는다. API/화면 연결, 전체 검사 어댑터·운영 파일당 격리·다양한 실제 파일/최악 자원 조건·장기 보존/파기 정책·운영 서비스 계정/암호화·백업·국내 통제까지 남아 있으므로 P1/전체 개편안은 계속 진행 중이다.

파일별 실행 후속으로 [별도 최소 디코더 작업 28개](decoder-job-isolation.md)를 검증했다. 파일당 다른 오프라인 컨테이너·stdin·tmpfs·종료/소유권 정리 경로를 마련했지만 현재 transport는 Windows 합성 시험용이다. 운영 Linux transport·durable queue/장애 회수·metadata 제거·전체 검사 통합·국내 운영 준비는 계속 필요하다. `MediaUploads`의 기본 검사기와 `inspect` 결과 계약을 바꾸거나 실제 업로드를 승인하지 않았다.

그다음 [실행 원장](decoder-job-journal.md)을 추가했다. opaque 실행 단계/영수증의 DB 저장·전역 한도·lease/generation 복구 기반이며 업로드/파일 접근 권한이나 대기열이 아니다. 임시 업로드의 기존 검사 임대·상태·취소·파일 원본은 그대로다. 실제 파일 검사 통합·원장과 실제 worker의 운영 장애 시험은 여전히 필요하다.

별도 [Linux 후속](linux-decoder-runtime.md)은 명시적 로컬 adapter·PostgreSQL 원장·실제 per-file container의 8개를 결합해, 실제 SIGKILL·자연 lease 만료·새 인스턴스 회수를 검증했다. 이 실행 경로를 `MediaUploads.inspect`나 파일 승인 서비스에 연결한 것은 아니다. metadata/변환본·안티멀웨어 결합·durable 업로드 queue·운영 배치/전체 장애 행렬·국내 운영·기기 간 전송은 계속 남아 있다.
