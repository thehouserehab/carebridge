# 아동 기본정보 편집 — 로컬 UI와 공통 입력 계약

2026-10-02. 센터의 `아동 → 기본정보 수정`과 신규 아동 등록을 정리했다. 실제 API·서버 계정·메일·기기 간 동기화·배포를 연결하지 않은 로컬 프로토타입 단계다. 실제 아동/건강 자료는 입력하지 않는다.

## 지금 확인할 수 있는 동작

1. 사용자 역할을 센터로 바꾸고 아동을 선택한다.
2. `기본정보 수정`에서 가상 이름·연령·연령 기준일을 입력한다. 이름은 필수, 연령은 선택이다.
3. 연령을 입력하면 기준일도 입력한다. 실제 0세는 `0`, 미입력은 두 칸 모두 빈 값이다.
4. 저장 후 아이 정보에서 기준일을 함께 확인한다. 치료사·보호자는 자신에게 연결된 아동의 정보를 읽기만 한다.
5. 보호자의 가족 관심사는 기존 별도 화면에서 수정한다. 센터의 기본정보 폼·아동 조회에는 관심사 내용이 없다.

저장 실패나 다른 탭의 수정 충돌에서는 입력을 유지하고 기존 저장값을 덮어쓰지 않는다. 다른 탭의 최신값을 확인한 후 다시 수정해야 한다. 기본정보 수정은 담당 관계·가족 관심사·기록·대화·공유본·첨부 ID를 변경하지 않는다. 이미 공유한 기록을 새 이름의 임상 수정본으로 자동 재작성하지 않는다.

## 연령과 이전 데이터

| 저장 상태 | 표시·처리 |
| --- | --- |
| `age: null, ageAsOf: null` | 연령 미입력. 빈 문자열을 숫자 0으로 변환하지 않는다. |
| `age: 0, ageAsOf: YYYY-MM-DD` | 실제 0세와 입력한 기준일을 표시한다. |
| 기존 정수 연령, `ageAsOf` 속성 없음 | 기준일 미확인. 이름만 수정하면 기존 연령과 속성 부재를 그대로 유지한다. |
| 새로 확인/변경한 연령 | 0~26 정수와 유효한 기준일을 함께 저장한다. 둘 모두 비우면 미입력으로 해제한다. |

기준일은 생년월일이 아니다. 연령은 자동으로 증가하지 않으며 과거 연령에 오늘 날짜를 붙이거나 생년월일을 역산하지 않는다. 읽기/새로고침 시 기존 아동 데이터를 일괄 재작성하지 않는다. 날짜가 없는 기존 연령의 이름만 수정하는 호환 경로는 **로컬 데이터에만** 적용한다. 서버의 신규 저장 계약은 계속 연령/기준일 쌍을 요구한다.

저장 키·schema 3·미디어 DB/파일 ID·기존 schema 2 백업 전환은 유지한다. 새 null 연령/기준일 쌍은 현재 버전에서 읽지만 과거 빌드는 null 연령을 유효하지 않은 데이터로 판단할 수 있다. 이전 빌드로 되돌릴 때 사이트 데이터를 초기화하거나 삭제하지 말고, 먼저 원문과 첨부 참조를 안전하게 확보해 버전 호환성을 확인해야 한다. 새로운 전체 백업/복원 기능을 구현한 것은 아니다.

## 공통 검증과 권한 경계

- `src/profile-fields.js`: 이름 1~30자, 잘못된 유니코드/제어문자·알 수 없는 임상/인증 필드 거부, 정수 연령·실제 달력 날짜·연령/기준일 쌍 검증. 이름의 바깥쪽 공백만 정리하며 줄바꿈/탭은 공백 정리 전에 거부한다. 기존 서버보다 이름 앞뒤의 줄바꿈/탭 거부를 엄격하게 했다.
- `childProfileFormValues`: HTML 폼 경계에서만 정수 문자열을 숫자로 변환한다. 공백·지수·소수·부분 숫자·숫자가 아닌 타입을 허용하지 않는다. 공통/서버 내용 검증은 숫자를 강제 변환하지 않는다.
- 로컬 쓰기: 기기 시계의 Asia/Seoul 날짜를 UX 검증에 사용한다. 이것이 운영 시간의 증명은 아니다.
- 서버 쓰기: `server/profiles.mjs`에서 공통 검증을 재사용하되 미래 기준일은 기존 DB 시계로 확인한다. 입력 오류는 기존 `INVALID_INPUT`으로 변환한다. 권한·트랜잭션·독립 프로필 버전·불변 영수증·SQL·인증 HTTP 경로는 유지한다.
- 별도 서버 실행 패키지는 공통 `src/profile-fields.js`도 포함해야 한다. 해당 모듈에는 자격 증명이나 임상 데이터가 없다.

현재 센터/치료사/보호자 전환은 **가상 역할의 화면 구분**이지 실제 접근 보안이 아니다. 브라우저 개발 도구에서 로컬 데이터를 읽을 수 있다. 서버 계약은 [기본정보·기존 계정 연결](profiles-provisioning.md)을 따른다.

신규 등록의 기존 P0 가상 치료사 선택은 유지했다. 로컬 등록은 선택한 가상 치료사를 연결하지만 보호자를 자동 연결하지 않는다. **운영 서버의 `Children.register`는 계정/담당 관계를 만들지 않는다.** 실제 연결 때 이 차이를 없애고 `Relationships.replace`에서 현재 구성원·열람 범위를 별도로 확인해야 한다. 체험용 선택값을 운영 권한으로 사용하면 안 된다.

## 변경 파일

- `src/profile-fields.js`, `src/profile-ui.js`: 공통 규칙·연령 표시·재사용 폼.
- `src/app.js`, `src/domain.js`: 센터 편집 진입/저장, 신규 등록의 빈 연령, 역할별 조회, 기존 연령 호환·수정 범위 보호.
- `server/profiles.mjs`: 중복 아동 내용 검증을 공통 모듈로 대체.
- `tests/profiles.test.mjs`, `tests/profiles-browser.mjs`: 내용/폼/상태/보존/역할과 실제 브라우저 저장·충돌 검증.
- `tests/domain.test.mjs`, `tests/browser.mjs`: 기존 신규 등록 fixture에 명시적인 기준일 추가.
- `tests/layout-browser.mjs`: 8개 너비에서 기본정보 수정/신규 등록 16조건 추가.
- `server/tests/profiles.test.mjs`: 이름 앞뒤 제어문자 거부 회귀 검사 추가. 오류·보존 검사를 완화하지 않았다.

브라우저 시험은 독립 Chromium 컨텍스트와 합성 자료만 사용하며 사용자의 저장소를 지우지 않는다. 실행 시 `PLAYWRIGHT_MODULE`, `CDP_URL`, `APP_URL`을 지정한다. 새 브라우저 시험의 초기 두 실패는 실제 닫기 버튼 이름과 텍스트의 중복 매칭을 잘못 지정한 테스트 선택자였다. 실제 접근성 이름/정확한 텍스트로 고쳤으며 제품 규칙이나 보존 검사는 완화하지 않았다.

서버 전체 시험의 첫 실행에서 `center-bootstrap.test.mjs` 파일 수준의 프로세스 실패가 1회 있었다. 세부 원인은 출력에서 확인하지 못했다. 해당 파일 단독 18개와 수정하지 않은 전체 재실행 207개는 통과했지만 원인을 확정한 것은 아니다. 재발하면 프로세스 진단 출력을 보존해 조사해야 하며 시험 안정성 확인은 남아 있다.
