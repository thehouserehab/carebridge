# 아동별 담당 관계·과거 열람 범위

## 2026-10-08 가정 활동·다음 기록 맥락의 과거 열람 누락 수정

원 개편안의 공유 범위와 ‘대화에서 다음 기록으로’ 흐름을 다시 대조하면서 두 화면의 우회 노출을 확인했다. 공통 권한 로직은 이미 이전 자료를 거부했지만, 가정 활동 목록과 새 기록의 이전 반영 메모가 원본 저장소를 직접 조회했다. 합성 자료로 이전 자료 1건씩을 준비해 기본 범위로 해제·재연결하면, 권한 조회는 각각 0건인데 화면용 원본 조회는 각각 1건을 반환했다. 이전의 관계/대화 검사만으로 이 두 진입점까지 검증됐다고 볼 수 없었다.

### 수정과 유지한 정책

- `src/app.js`의 `activitiesView()`는 **권한이 허용된 공유본과 현재 공유 중인 ID의 교집합**만 표시한다. 보호자와 치료사 모두 연결 전 활동의 제목·안내·빈도·유의사항을 우회 열람할 수 없다. 치료사의 공유 이력 조회는 별도로 유지하고, 활동 목록에 이전 버전·철회한 활동을 다시 넣지 않는다.
- 같은 파일의 `recordForm()`은 `canReadMessage()`를 통해 현재 관계와 과거 열람 경계를 확인한 메시지의 반영 메모만 가져온다. 별도 과거 공개 승인 전에는 이전 메모를 새 기록 작성창에서 노출하지 않는다.
- 일반 소식 숨김/전체 삭제와 이미 작성된 치료사 임상 메모의 보존은 다른 규칙이다. 열람 권한이 있는 치료사의 기존 메모는 원문이 대화에서 숨겨지거나 삭제 표시돼도 유지한다. 원문/공유본/기록/첨부를 지우거나 별도 과거 확인을 생략하지 않았다.
- 제품 변경은 `src/app.js`의 조회 경로뿐이다. 공통 권한의 정의, 서버 코드·SQL·세션·인증·API·파일 저장·배포는 변경하지 않았다. 검증 스킬의 ‘실제 진입점→조회 경계→표시/저장’ 기준으로 수정 전 실패와 수정 후 결과를 분리했다.

## 2026-10-08 사용자 결정과 로컬 화면 반영

사용자의 ‘1’은 **신규·재연결자는 연결 이후부터, 과거 공개는 별도 확인**으로 반영했다. 일반 메시지는 이후 별도로 답한 **‘카카오톡과 같은 방식’**이 선택된 방향이다. 메시지 수정 불가·운영자 삭제만 허용하는 이전 권고안을 선택한 것으로 해석하지 않는다.

관계 변경 화면은 다음 원칙을 기본값으로 사용한다.

- 신규·해제 후 재연결: 변경이 확정된 시점 이후의 소식과 새 내부 기록만 열람한다. 폼을 연 뒤 연결 전에 도착한 소식도 제외한다.
- 현재 연결 유지: 기존 범위를 유지한다. ‘기본 범위 유지’ 선택이 과거 전체 공개를 뜻하지 않는다.
- 선택한 참여자의 과거 공개: ‘과거도 추가 공개’를 선택하고 별도 확인 항목을 체크해야 저장된다. 일반 관계 변경 확인만으로는 확대할 수 없다.
- 재연결·실제 과거 확대 때 해당 참여자의 읽음만 초기화한다. 이미 전체 공개된 관계의 같은 선택을 다시 저장할 때는 읽음을 유지한다.

공통 로컬 조회 규칙을 홈·대화·공유본·기록에 적용했다. 열람 범위 밖 메시지의 직접 조회/읽음/답변/임상 참고, 이전 기록 수정·공유·철회, 이전 공유본 피드백도 거부한다. 기존 참여자가 이전 메시지에 답한 **새 독립 소식**은 새 참여자에게 보이되 이전 원문의 작성자·본문·첨부는 인용에 노출하지 않는다. 이전 공유본에 늦게 도착한 피드백으로 과거 내용이 우회 노출되는 것도 막는다. 원본 메시지·기록·공유본·파일 ID와 파일 자체는 삭제하지 않는다.

로컬 schema 3에 선택적인 `historyAccess`와 기록의 `createdRevision`을 추가했다. 기존 자료에 이 값이 없으면 기존 범위를 유지하며, 기존 기록의 생성 revision은 논리적으로 0으로 취급한다. 기존 자료를 일괄 재작성하지 않는다. **로컬 역할 선택은 인증이 아니다.** 같은 브라우저의 원본 저장소·이전 앱 버전·개발자 도구를 보안 경계로 통제한 것이 아니므로 실제 자료나 서버 신원/권한 반입에 사용하지 않는다.

서버 내부 `Relationships.replace()`에도 `pastHistoryConfirmed` 확인을 추가했다. 신규/재연결 `all` 또는 현재보다 과거가 넓어지는 `all`은 정확히 `true`여야 한다. 문자열 확인값은 거부한다. 기존 명령 영수증 재조회는 관계를 재적용하지 않으므로 연결 해제 뒤 옛 요청을 재시도해도 권한을 복구하지 않는다. API·SQL 마이그레이션·DB 권한·의존성·운영 서비스·배포는 변경하지 않았다.

### 관계 단계 당시의 다음 작업: 카카오톡형 일반 메시지

사용자 방향은 일반 메시지의 작성자 수정·삭제다. 카카오 [공식 서비스 소개](https://www.kakaocorp.com/page/service/service/KakaoTalk)에서 수정·삭제 및 ‘수정됨’ 표시를 확인했고, [공식 배포자 Mac 릴리스 기록](https://apps.apple.com/kr/app/kakaotalk/id869223134?mt=12)에서 삭제 시간 확대 안내를 확인했다. 이 근거로 모든 플랫폼의 세부 시간 제한/첨부 동작까지 동일하다고 단정하지 않는다.

**이 관계 단계 당시에는 메시지 수정·삭제를 아직 구현하지 않았다.** 이후 [메시지 후속](message-lifecycle.md)에서 작성자 권한, 나에게만/전체 삭제, 수정 표시·충돌·재시도, 당시 인용·임상 참고와 첨부 보존을 로컬에 반영했다. 치료 기록·당시 공유본은 일반 메시지와 함께 조용히 덮어쓰거나 삭제하지 않는다. 서버 구현과 원본 보존·삭제 요청 처리·보존 기간의 운영 기준은 남아 있다. API는 계속 마지막이다.

## 아래는 최초 서버 구현 당시 기록

2026-10-01. 개편안 P1의 서버 내부 서비스이며, API·화면 연결은 마지막 단계로 남긴다.

## 구현 범위

`server/relationships.mjs`의 `Relationships`가 아동 대화방의 담당 치료사와 보호자 연결을 관리한다. 검증된 서버 세션의 사용자 ID·센터 ID를 받아 DB의 현재 관리자 권한을 확인한다. 요청에 넘긴 역할을 신뢰하지 않는다. 센터는 참여 관계만 조회하며 메시지·임상 메모·공유 요약은 받지 않는다.

담당 치료사 교체, 보호자 추가/연결 해제, 과거 열람 범위 변경을 하나의 트랜잭션으로 적용한다. 이전 참여자 행은 비활성화하고 메시지·답변·공유본·작성자 참조는 보존한다. 연결 해제된 사용자의 다음 서버 조회·전송·읽음 요청은 차단된다. 이미 내려받은 데이터의 회수나 브라우저 캐시 삭제는 향후 클라이언트 연결에서 구현해야 한다.

## 호출 계약

| 메서드 | 입력 및 결과 |
| --- | --- |
| `get(actor, { conversationId })` | `conversationId`, `childId`, 관계 전용 `version`, 참여자별 ID·역할·활성 여부·첫 열람 순번을 반환한다. |
| `replace(actor, input)` | 활성 참여자 전체 목록을 교체한다. `conversationId`, `clientId`, `expectedVersion`, `therapist`, `guardians`, `historyConfirmed: true`가 필요하다. |

`therapist`는 `{ userId, history }` 또는 `null`, `guardians`는 같은 형식의 배열이다. `null`/빈 배열은 해당 역할의 연결을 모두 해제한다. 사용자는 같은 센터의 활성 구성원이어야 하며, 센터 역할은 대화 참여자로 지정할 수 없다. 서비스가 계정이나 센터 소속을 새로 만들지는 않는다.

| `history` | 적용 범위 |
| --- | --- |
| `all` | 순번 1부터 열람한다. 기존 공유본의 철회·재공유 표시 규칙은 계속 적용한다. |
| `from_now` | 관계 변경 트랜잭션에서 확정한 마지막 메시지의 다음 순번부터 열람한다. 폼을 연 뒤 연결 전에 도착한 소식도 제외한다. |
| `preserve` | 현재 활성 관계의 열람 범위를 유지한다. 신규 연결이나 해제 후 재연결에는 사용할 수 없다. |

열람 옵션과 확인을 생략하면 실패한다. 2026-10-08부터 과거 범위를 실제 확대하는 `all`에는 별도의 `pastHistoryConfirmed: true`도 필요하다. 서버의 선택지 제공이 센터의 동의·인수인계·보존 정책을 확정한 것은 아니다. 운영 화면은 선택한 범위를 당사자·센터 정책에 맞게 확인해야 하며, `all`을 기본값으로 자동 제출해서는 안 된다. 임상 기록·피드백의 저장 서비스도 이 열람 시작 순번을 확인한다. 최신 공동 목표/운영 일정과 이전 수정본의 구분은 [목표·일정 서버 계약](care-context-storage.md)을 참고한다.

## 충돌·재시도·감사

- `relationships_version`은 관계가 바뀔 때만 증가한다. 메시지·읽음 갱신 때문에 관계 편집이 불필요하게 충돌하지 않는다. 오래된 관계 화면의 변경은 `RELATIONSHIP_CONFLICT`로 거부한다.
- 같은 센터·관리자·`clientId`의 동일 요청은 기존 처리 영수증만 반환한다. 이후 다른 관계 변경이 있었어도 옛 요청을 다시 적용하지 않는다. 다른 요청 내용이나 대화방에 같은 ID를 사용하면 `IDEMPOTENCY_CONFLICT`다. 재시도도 현재 관리자 권한이 있어야 한다.
- 영수증의 `appliedVersion`은 해당 요청 당시 버전이다. 화면의 최신 상태가 필요하면 다시 `get`해야 한다.
- 연결 해제 뒤 재진입하거나 과거 열람을 확대하면 해당 사용자의 읽음 커서를 초기화한다. 새로 보이는 대화를 이미 읽은 것으로 처리하지 않는다. 다른 참여자의 읽음 상태는 유지한다.
- 관계 변경은 기존 대화 `revision`도 증가시킨다. 예전 조회 결과의 연속 페이지 요청은 재조회가 필요하다는 응답을 받는다.
- 관계 변경의 DB 잠금은 센터 일정 → 대화방 → 사용자/소속 → 참여 관계 순서다. 새 담당 치료사와 다른 아동의 일정이 겹치면 `SCHEDULE_CONFLICT`로 전체 변경을 거부한다. 변경 결과·명령 영수증·변경 전후 활성 상태와 열람 순번의 감사 행을 함께 커밋하며, 실패 시 관계·읽음 커서·버전·영수증 모두 롤백한다. 관계 조회에는 센터 일정 잠금이 필요하지 않다.
- 감사 행에는 ID·역할·열람 순번만 남기며 메시지 본문, 이메일, 비밀번호, 토큰, 자유 서술 메모는 넣지 않는다. 해당 식별자 역시 운영에서 접근 통제해야 할 데이터다.

## 파일 및 검증

- `server/migrations/004-relationships.sql`: 관계 버전과 내용 없는 요청·변경 감사 테이블. 기존 적용 마이그레이션을 수정하지 않는 추가 마이그레이션이다.
- `server/relationships.mjs`: 관리자 관계 조회·원자적 교체·명시적 열람·재시도.
- `server/conversations.mjs`: 관계 변경과 같은 순서로 대화방 잠금을 확보한 뒤 현재 참여 권한을 재확인한다.
- `server/tests/relationships.test.mjs`: 권한·해제·교체·열람 범위·읽음·충돌·재시도·롤백·이전 스키마 업그레이드 11개 테스트.
- `server/tests/auth.test.mjs`, `server/tests/conversations.test.mjs`: 새 마이그레이션 목록을 검증하고 기존 인증·대화 회귀를 유지한다.

`npm run test:server`의 관계 검증 11개가 통과했다. 이후 기록 서비스 등을 포함한 최신 전체 결과는 [서버 기반 문서](server-foundation.md)에 정리한다. DB는 테스트에서만 생성한 인메모리 PGlite이며 실제 고객 DB 또는 환경변수 `DATABASE_URL`을 사용하지 않는다. 이전 001~003 스키마에 가상 메시지를 저장한 뒤 후속 마이그레이션을 적용해 메시지·기존 권한·대화 revision의 보존과 재실행을 확인했다.

PGlite는 단일 연결로 실행하므로 실제 PostgreSQL의 여러 연결 잠금 경쟁을 검증한 것은 아니다. 운영 전 담당 변경과 발신의 동시 실행, 관리자 권한 해제 경쟁, 커밋 응답 유실·재시도, 브라우저 캐시 제거를 실환경에 가까운 조건에서 확인해야 한다. 화면의 로컬 관계 관리에는 아직 서버 선택지가 연결되지 않았다.

기록·평가·가정 활동·피드백·목표/일정·첨부 원본 연결과 [아동/계정 기본정보·기존 계정 센터 연결](profiles-provisioning.md)을 구현했다. 계정의 센터 연결이나 새 아동 등록만으로 참여/과거 열람 권한을 만들지 않는다. 해당 구성원을 여기의 명시적 관계 설정으로 연결해야 한다. 다음은 실제 파일 엔진·국내 운영 환경 준비이며 이후 API와 기기 간 흐름을 연결한다.
