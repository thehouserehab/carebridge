# Carebridge 데이터 보존·백업·복원 준비 검토

2026-10-08 외부 파일 후속: [원본/복원본의 바이트와 삭제 차단 표식 대조](recovery-state-comparison.md#2026-10-08-외부-파일삭제-차단-표식-후속)를 기존 DB SHARE 잠금 안에 선택적으로 결합했다. 새 합성 E27은 PNG/fence의 변조·누락·최신 취소 차이 감지 및 검사 무변경/격리 유지까지 확인했다. 준비 후보/증명의 실제 엔진 결합, writer 중단·키/ACL·독립 백업·최종 전환은 별도이며 **BR-06~10/전체 운영 완료로 바꾸지 않는다**. 실제 아동 자료/외부 접속 보류와 API 마지막 원칙을 유지한다. 아래 숫자는 각 이전 단계의 기록이다.

최신 [DPAPI 기반 실제 DB/TLS 연결](windows-database-service.md)은 합성 E 30·서버 625·로컬 87 통과. 시험 TLS 키는 두 cluster 종료 후, 자격증명은 연결 pool 종료 후 자기 파일만 정리했으며 운영 백업으로 남기지 않았다. 실제 OS/서비스·키 회수/독립 매체·최신 권한/삭제 cutover는 미완료이고 BR-08/09·실제 자료 전환 판정은 바꾸지 않는다.

최신 [Windows DB 서비스 자격증명 보관](windows-database-credential-store.md)은 복구 키와 별도 목적/경로의 CurrentUser DPAPI 내부 구성요소다. 가상 E 15·기존 키 최종 회귀 13·서버 611·로컬 87 통과, 운영 secrets 파일 0개. 일시 키 회귀 실패/이전 PG 중단 원인은 미확정이다. 실제 DB 인증·OS 격리·프로필 상실 복구·독립 매체가 아니며 BR-08/09·실제 자료 전환을 완료로 바꾸지 않는다.

2026-10-06. 개편안 P1의 실제 저장/재접속과 기존 기록·첨부 보존을 위한 후속 설계다. **운영 백업 도구·스케줄러·운영 복원 실행·서버 이관은 아직 구현/활성화하지 않았다.** 실제 사용자 DB나 파일을 덤프·복사·삭제하지 않았고 운영 공급자·예산·보관 기한을 확정하지 않았다. 이후 [정지형 합성 DB·첨부 복원](recovery-native-verification.md)의 암호화 모듈·실제 PG/파일 시험을 구현했다. 운영 게이트 전체 완료와 구분한다.

## 1. 현재 상태와 실제 확인 근거

2026-10-07 결정 갱신: 사용자는 실제 센터/보호자 베타의 저장 기반으로 [로컬 E 드라이브](local-beta-storage.md)를 선택했다. 유료 공급자/월 예산 선택은 사업화까지 보류하며 기존 요청을 반복하지 않는다. 새 private 경로의 합성 IO·NTFS 접근 제한은 확인했지만 DB/첨부 일관된 운영 사본·키/최신 삭제 대조·RPO/RTO·복구 책임은 미확정/미완료다. 같은 E의 recovery 디렉터리만으로 독립 백업을 충족하지 않는다. 실제 자료는 마지막 계정/권한/API와 이 복구 준비 후 사용한다.

독립 매체 질문에 사용자가 **아직 별도 매체 없음**으로 답했다. 독립 백업 게이트는 미충족이며 실제 아동 자료 운영 전환을 보류한다. 유료 백업을 임의 생성하거나 같은 E 사본을 완료 근거로 대체하지 않는다. 이 상태는 비API/합성 준비까지 중단하라는 요청은 아니다.

이후 [E Windows PostgreSQL 지속 저장·복원](windows-e-postgres-verification.md) 9개를 확인했다. 원본/대상의 실제 E PGDATA·독립 정상 종료 재시작·별도 신규 cluster의 가상 DB/PNG/fence 복원 근거다. operating role/secret 회수·기존 동일 cluster 격리 모듈의 별도 cluster 적용·최신 삭제 대조·키 복구·전원 손실·독립 매체·운영 cutover는 완료하지 않았다. 합성 시험의 키는 폐기하므로 남은 사본을 운영 백업이라고 하지 않는다.

최신 후속 [복원 대상의 계정·작업 격리](recovery-quarantine.md)는 017을 추가해 오래된 세션·초대·사용자/작업 쓰기를 닫는 실제 합성 증거를 마련했다. BR-06~07의 방어 일부이며 최신 권한/삭제/불확실 엔진 대조·격리 해제·운영 전환은 미완료다. 아래 001~016/518개는 최초 검토 당시 기반이고 현재 복원/격리 native 14개·서버 회귀 547개와 구분한다.

## 3. DB 방법과 파일 일관성

`pg_dump`는 DB 내부의 일관된 snapshot을 만들며 cluster-wide role/tablespace까지 담지는 않는다. custom format은 `pg_restore`로 다룬다. 압축 archive를 암호화된 사본으로 간주하지 않는다. 운영 role/grant 복구는 앱 권한과 분리해 검토한다. [PostgreSQL SQL dump](https://www.postgresql.org/docs/18/backup-dump.html), [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html)

논리 dump는 WAL 기반 연속 복구에 쓰는 물리 백업이 아니다. 더 짧은 데이터 손실 허용치가 필요하면 base backup/WAL 또는 공급자의 검증된 PITR을 별도로 선택한다. 수치·주기·비용을 아직 정하지 않았다. [PostgreSQL PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)

Carebridge의 `.blob`/`.blocked`는 PostgreSQL 바깥의 파일이다. DB snapshot과 파일의 시점/버전이 일치하도록 별도 조합이 필요하다. 첫 합성 복원 시험은 복잡한 online writer 경쟁을 숨기지 않고 다음 **명시적 정지형 경로**로 설계한다.

1. 전용 합성 환경과 생성 영수증을 확보한다. 실제 사용자/운영 DB·기존 폴더를 시험 대상으로 채택하지 않는다.
2. 신규 쓰기/업로드를 차단하고 웹 writer·검사 작업자·유지보수의 종료와 active IO/임대/격리 작업 상태를 확인한다. `worker.status` 한 개나 lease 시간 초과만으로 모든 프로세스 종료를 추정하지 않는다. 불명확하면 묶음을 확정하지 않는다.
3. DB와 해당 시점의 비공개 객체/삭제 차단 정보를 함께 보존한다. 검사 중 부분 파일을 임의로 ready로 고치지 않는다. snapshot 묶음의 version/객체 inventory·체크섬·시점을 남기되 실패/부분 묶음에는 완료 표시를 붙이지 않는다.
4. 키와 사본의 접근을 분리하고 암호화/변조 검증·디렉터리 권한·원격 전달 목적지를 확인한다. 평문 임시 사본, SQL stdout, token/URL/원문 오류 로그를 만들지 않는 실행 경로가 필요하다.
5. 새 격리 DB/비공개 경로로 복원·검증한다. 검증 실패는 실패로 남긴다. 기존 운영 환경을 덮어쓰거나 `--clean`/일괄 폴더 삭제로 시험을 시작하지 않는다.
6. 검증 및 최신 권한/삭제 대조 후 별도 cutover 승인을 받는다. 합성 사본을 실제 운영으로 승격하지 않는다.

online backup이나 영구 스냅샷/객체 versioning 경로는 별도 동시성 시험 뒤 선택한다. 파일 쓰기/정리가 DB 트랜잭션 밖에서도 실행되므로 DB 잠금이나 dump 성공만으로 전체 파일 일관성을 선언하지 않는다.

## 4. 복원 이후 반드시 닫아 둘 경계

아래 위험은 현재 코드와 snapshot 복구 특성에서 도출한 설계 판단이다. 자동 복구 기능이 이미 있다는 의미는 아니다.

- **계정/권한 rollback:** 세션의 revoked_at, 계정 비밀번호/잠금, 소속/참여 해제, 공유 철회가 백업 이후 변경됐을 수 있다. 현재 진실과 비교할 수 없다면 공개/API·로그인·메일을 열지 않는다. 보존본은 유지하고 서비스용 복구본의 세션/초대 종료 및 최신 정지/권한/철회 대조를 승인된 절차로 처리해야 한다. 실제 계정 복구나 무조건 정지 해제를 구현하지 않았다.
- **삭제 자료 부활:** 오래된 backup의 파일이 현재 삭제 의도와 충돌할 수 있다. 운영 삭제/철회 기록과 fence의 별도 최신 대조가 필요하다. 복원했다고 파일 제공이 승인되는 것이 아니다. bound 원본·후보와 불변 이력의 운영 파기 경로는 현재 없으며 이를 영구 보관 정책으로 확정하지 않는다.
- **작업자 재실행:** 이전 engine/container/job ID·누적 횟수·영수증을 새 서비스의 실행 승인으로 취급하지 않는다. 이전 프로세스와 엔진 상태를 확인하지 못하면 검사 자동 시작을 금지한다. DB generation이 과거로 되돌아간 상태의 fence 효과도 새 cutover 시험으로 검증해야 한다.
- **과거 파일 승인의 혼동:** pre-013 파일은 새로운 준비 증거를 만들지 않고 기존 manifest/ID 그대로 보존한다. 반입·재검사·후보 전환은 별도 승인 경로다. 손상 후보를 건강한 원본으로 대신 제공하지 않는다.
- **dump 자체의 신뢰:** 복원은 dump 안의 코드를 실행할 수 있다. 승인된 자체 사본의 출처·무결성·복원 role을 확인하며 출처 불명 파일을 운영 DB에 직접 실행하지 않는다. [pg_restore 보안 경고](https://www.postgresql.org/docs/18/app-pgrestore.html)

## 5. 후속 구현의 검증 게이트

현재 아래 **운영 게이트 전체는 미완료**다. [합성 복원 후속](recovery-native-verification.md)은 BR-01~05 일부의 실제 증거이며 BR-06~10과 운영 role/매체/키/책임 검증을 대신하지 않는다. 기존 일반 회귀/임대 복구 테스트를 실제 backup/restore 통과로 재집계하지 않는다.

| 게이트 | 완료를 입증해야 할 결과 |
| --- | --- |
| BR-01 대상/권한 보호 | 전용 생성 DB/경로·영수증만 사용. 운영/기존 대상·symlink·권한 불일치·잘못된 archive 출처 거부. 앱 센터 역할로 임상 전체 backup을 얻지 못함. |
| BR-02 실제 DB 복원 | 실제 PG 18.6의 승인된 dump 도구로 사본을 만들고 새 DB에 복원. 001~016 이력/체크섬·제약/trigger·최소 role/grant 재현 확인. |
| BR-03 실제 파일 복원 | 원본/후보/삭제 fence를 별도 비공개 경로에 복원. 모든 제공 대상의 전체 크기/해시와 source/candidate/proof/binding ID 연결 일치. 누락/변조/잘못된 후보는 실패. |
| BR-04 공유/임상 보존 | 당시 답변 참조·재공유/철회 안내·독립 메시지·기본 3항목·복수 평가의 0/null/날짜/단위/조건·legacy 원문과 첨부 ID 보존. 보호자는 내부 메모/평가 원문을 못 봄. |
| BR-05 중간 실패 | dump/파일 복사/암호화/manifest/복원 실패와 응답 유실에서 완성 표시·자동 cutover 없음. 기존 원본·운영 대상 보존. 같은 실행 ID의 중복/충돌 처리. |
| BR-06 권한/삭제 cutover | 백업 이후 정지·비밀번호 변경·세션/초대 철회·참여 해제·공유/파일 삭제 대조. 정보가 부족하면 fail closed. 종료된 세션과 삭제 후보가 복원만으로 다시 유효해지지 않음. |
| BR-07 작업자/원장 cutover | receiving/inspecting/running/blocked·불확실 생성/회수 사례와 engine 교체. 이전 작업/임대/generation/후보의 뒤늦은 정산 거부. 자동 승인/원본 fallback/횟수 reset 없음. |
| BR-08 키·매체·권한 | 키 분리 보관/회수, 변조 검증, 최소 OS/DB/backup 권한, 영구 매체의 실제 재시작/장애 증거. tmpfs/메모리 결과만으로 통과하지 않음. |
| BR-09 RPO/RTO·운영 | 합의한 허용 손실 시간/복구 시간과 실제 측정, 사본 주기/경보/보관/파기·최신 삭제 대조가 예산/운영 담당자 범위에서 실행됨. 숫자 미정이면 운영 완료 아님. |
| BR-10 사용자 흐름 | 마지막 API·화면 연결 후 권한 있는 서로 다른 기기의 홈 → 대화 → 기록 → 공유, 사진/영상, 통신 단절/재접속과 모바일/키보드 완주. |

RPO는 허용 가능한 데이터 손실 시간, RTO는 서비스 복구까지 허용하는 시간이다. ‘매일 백업’만 정하는 대신 실제 회복 가능한 DB+파일 시점과 운영 중단 시간을 함께 합의한다.

## 6. 결정과 실행 우선순위

1. **확정 범위와 남은 접근/사본 결정:** 사용자는 E 드라이브에서 센터·보호자의 실제 자료 베타, 사업화 후 유료 데이터센터 검토로 정했다. 독립 백업 매체는 아직 없으므로 실제 운영 전환을 보류한다. 센터 밖/내부 접속 범위와 독립 매체·키 회수 책임을 먼저 확정한다. 유료 공급자/월 예산은 지금 재확인하거나 자원을 생성하지 않는다. ‘국내 region’만으로 전체 국내 통제를 완료로 판정하지 않는다.
2. **기존 브라우저 자료:** 데모로 보존만 할지 승인된 서버 이관이 필요한지. 이관이 필요하면 사용자·센터·아동/첨부 귀속을 새 실제 계정에 명시적으로 매핑한다. 가상 역할/ID를 운영 권한으로 재사용하지 않는다. 원본을 자동 삭제하지 않는다.
3. **운영 보존/파기·복구 책임:** 원본/후보/이력/세션/감사/사본/삭제 차단 정보별 기한, 삭제 요청과 사본의 관계, 승인자/실행자·키 회수 담당, RPO/RTO. 법적 기한을 이 문서에서 임의로 지정하지 않는다.
4. **합성 복원 구현·실제 검증:** BR-01~07의 전용 일회용 경로부터 구현한다. 같은 format/원래 trigger를 다루며 그 목적만을 위해 제약이나 auth를 완화하지 않는다. 성공 후 선택한 운영 매체/키 경로의 BR-08~09를 확인한다.
5. **마지막 API·현재 UI 연결·실물 기기:** BR-10과 원 개편안의 6개 사용자 시나리오, 사람의 작성 시간/보호자 요약 이해도 확인. 그전까지 P0가 실제 서버 소통처럼 표시되지 않게 유지한다.

이번 변경 파일은 이 문서와 README/서버 기반의 후속 상태 링크다. 코드·SQL·권한·저장 데이터·API·화면·운영 환경·의존성·GitHub/Vercel 배포는 변경하지 않았다. `npm test`를 다시 실행해 로컬 61개(기존 형식 원문 백업·ID/평가·파일 보존·실패 처리 포함)가 모두 통과했고 `git diff --check`도 통과했다. 신규 문서의 내부 파일/링크·텍스트 형식을 별도로 확인했다. 서버/native/브라우저/실물 기기와 신규 backup/restore는 이번 문서 단계에서 실행한 것으로 주장하지 않는다.

2026-10-07 후속 [Windows CurrentUser 복구 키 보관](windows-recovery-key-store.md)은 BR-08의 **일부 구성요소 증거**다. 가상 키 영구 암호문·독립 프로세스 재읽기/기존 묶음 인증과 실패 거부 13개를 확인했다. 독립 백업·프로필 상실 후 키 회수·전용 OS/최소 DB 권한·운영 매체 재부팅/정전은 미확인이다. 운영 키/실제 서비스는 만들지 않았으며 BR-08/09를 완료로 바꾸지 않는다.

2026-10-07 최신 [E DB 권한 v2·다섯 역할 분리](database-worker-privileges.md)도 BR-08의 일부 증거다. worker의 SQL 최소 권한/앱 원장·승인 증거 생성 거부, 읽기 전용 dump와 별도 cluster의 새 자격증명/객체 ACL·명시적 DB 접속 ACL·전체 파일 7개 복원/재시작을 확인했다(23개, 일반 E 9·서버 585·로컬 87). 준비 대역의 SQL/E 시험이며 실제 native 검사/운영 프로세스 증거는 아니다. 실제 운영 자격증명/OS 계정·최신 권한/삭제/원장 대조·격리 해제·독립 매체/키 회수는 미완료다. 기존 동일 cluster 격리 모듈을 이번 별도 cluster에 적용하지 않았으며 BR-08/09·전체 목표를 완료로 판정하지 않는다. 종전 v1 19개/576개는 [역사적 보고서](database-privilege-separation.md)에 보존한다.

같은 날 후속 [실제 DB 연결 가드·작업자 조립](database-service-admission.md)은 v2 권한을 유지하며 실제 로그인/DB/OID·권한의 매 트랜잭션 검사와 별도 worker 원장을 연결했다. 가상 scanner/decoder 통신을 사용한 SQL/E/전체 파일 복원·재시작 25개, 일반 E 9·서버 599·로컬 87 통과. 중간 종료 1회는 원인 미확정으로 보존했고 최종 새 실행은 정상 종료했다. 자격증명 보관·실제 native 엔진/운영 서비스·독립 백업/키 회수·최신 권한/삭제 cutover는 아직 아니며 BR-08/09 및 전체 완료 판정은 바꾸지 않는다.
