# 가정 활동 피드백 서버 저장

## 2026-10-08 피드백 수정 이후의 당시 인용·임상 참고 보존

보호자가 활동 피드백 F1을 F2로 수정해도, F1에 달린 기존 답변과 F1을 선택한 치료 기록은 당시 내용을 유지하도록 보완했다. 수정 전 로컬의 과거 답변이 F2로 바뀌는 경우와 서버의 기존 F1 참고 기록 재저장이 `REFERENCE_CHANGED`로 막히는 경우를 각각 재현했다. 아래의 2026-10-01 구현과 구분되는 후속 수정이며, API 연결·배포·실제 계정 전환은 아니다.

### 동작과 보호 경계

- 로컬 피드백에 선택적 `history`를 추가했다. 기존 데이터는 수정본 1로 읽고, 성공하는 편집에서만 이전 내용·첨부 목록·비공개 검토 상태를 복사해 보존한다. 저장 키와 스키마 번호는 유지하며 이전 형식의 공백·긴 원문을 읽기 과정에서 정규화하지 않는다.
- 대화 카드의 ID·최초 시각·순번을 유지한다. 현재 카드는 F2, 과거 답변 인용은 F1과 변경 안내를 표시한다. 인용의 첨부 요약도 F1에 속한 목록을 사용하고 파일명·파일 ID·내부 확인 메모는 인용에 넣지 않는다.
- 치료사가 선택한 참고본에는 당시 반응·활동 날짜·수행 상태·어려움·첨부 목록을 보존한다. 기존 기록의 계획을 수정해도 참고본이 최신 내용으로 교체되지 않는다. 기존 ID-only 참고본은 원본이 처음 바뀌기 전에 당시 사용 가능한 내용으로 고정한다. 임상 본문·공유본·실제 파일 바이트는 자동 수정하지 않는다.
- 로컬 폼은 편집·검토·새 답변·새 참고 선택 시 확인한 버전을 전달한다. 명시된 버전이 달라지면 저장하지 않는다. 기존 참고본은 버전 생략 또는 저장된 버전만 허용하고 다른 버전을 명시하면 거부한다. 이전 로컬 호출과의 호환성을 위해 일부 명령의 버전 생략은 여전히 허용하므로, 이를 서버 수준의 필수 버전 계약으로 간주하지 않는다.
- 서버 `Records.save`는 **같은 기록의 현재 수정본에 이미 있는** 피드백 ID/수정본만 유지한다. 기존 참고본도 버전 명시는 필수다. 새 기록·다른 기록·제거 후 재추가는 최신 피드백 버전을 다시 확인해야 하며, 다른 기록의 예전 참고본을 빌려 사용할 수 없다.
- 신규·재연결자의 과거 열람 제한, 활성 계정/역할/담당 관계 및 공유 철회 검사를 유지한다. 보호자 조회는 현재 피드백의 명시된 필드만 반환하고 `history`, 내부 메모·확인 시각은 반환하지 않는다. 공유 기록에도 참고본·내부 계획을 자동 포함하지 않는다.
- 읽음과 임상 검토는 별개다. 수정 후 현재 피드백은 미확인으로 돌아가고 과거 수정본의 검토 메모는 비공개 이력에 남는다. 과거 검토를 현재 수정본 검토로 표시하지 않는다.

## 구현한 흐름

현재 공유 중인 가정 활동 → 연결된 보호자의 수행 상태·아이 반응·어려움 → 대화 카드 1개 → 치료사의 공개 답변 또는 내부 확인 → 다음 회기 기록의 원문 참조.

- `done / partial / skipped`, 활동 날짜, 반응(필수 1,000자 이내), 어려움(선택 1,000자 이내)을 저장한다. 기존 로컬 화면과 순수 검증 함수를 공유한다.
- 보호자는 본인이 작성한 피드백만 수정한다. 수정본은 새 행으로 보존하고 대화 카드의 ID·최초 시각·순번은 바꾸지 않는다. 같은 피드백을 수정했다고 카드나 안 읽은 개수를 늘리지 않는다.
- 읽음과 치료사 검토를 분리한다. 검토는 특정 피드백 수정본에 붙는다. 보호자가 수정하면 최신 수정본은 다시 미확인 상태가 되고, 이전 수정본의 확인 메모는 보존된다.
- 공개 답변은 일반 대화 메시지다. 내부 확인 메모·검토 버전·검토 시각은 치료사에게만 조회된다. 보호자에게는 확인 여부만 제공한다.
- 답변 인용과 기록 참조에는 피드백의 당시 수정본 번호를 저장한다. 이후 편집해도 과거 인용·참조 내용은 달라지지 않는다. 일반 대화가 임상 기록에 자동 복사되지는 않는다.
- 화면에서 확인한 뒤 저장하기 전에 피드백이 바뀌면 답변 또는 기록 저장을 거부한다. 사용자가 최신 내용을 확인한 뒤 새 버전으로 재시도해야 한다.

## 서비스 계약

`ActivityFeedback`는 검증된 서버 세션의 `{ centerId, userId }`를 받는 내부 서비스다. 브라우저가 주장하는 사용자 ID·역할로 호출하면 안 된다. 공개 HTTP 경로는 추가하지 않았다.

| 메서드 | 입력·동작 |
| --- | --- |
| `save(actor, input)` | `conversationId`, `feedbackId`, `sourceMessageId`(가정 활동을 담은 공유 카드), `clientId`, `expectedRevision`, `content: { date, result, reaction, difficulty?, attachments?: [{ id }] }`. 신규 0, 수정은 현재 수정본 번호를 명시한다. |
| `get(actor, input)` | `conversationId`, `feedbackId`. 공통 대화 카드 형식으로 최신 피드백 조회. 치료사만 `revision`을 주어 이전 수정본을 조회할 수 있다. |
| `review(actor, input)` | `conversationId`, `feedbackId`, `clientId`, `expectedRevision`, `expectedReviewVersion`, `note`(필수 2,000자 이내). 현재 담당 치료사만 특정 최신 수정본의 검토를 저장한다. 첫 확인은 검토 버전 0. 메모 수정도 이전 메모를 덮어쓰지 않는다. |

저장·검토 응답은 `{ feedbackId, revision, reviewVersion, messageId, operation, replayed }` 영수증이다. 영수증은 처리 당시 결과이며 최신 카드는 `get`/`Conversations.list`로 다시 조회한다. 같은 요청 ID·같은 내용의 재시도는 기존 영수증만 돌려주며, 오래된 재시도로 최신 수정본을 되돌리지 않는다. 다른 내용·다른 방에 같은 피드백 요청 ID를 사용하면 거부한다. 재시도도 현재 계정·센터·담당 관계와 과거 열람 범위를 통과해야 한다.

다른 서비스의 추가 계약:

- `Conversations.sendText`: 피드백에 답할 때는 `replyTo`와 함께 화면에서 확인한 `expectedReplyRevision`이 필수다. 일반 메시지·공유 카드에 답할 때는 이 필드를 보내지 않는다. 오래된 피드백이면 `FEEDBACK_CONFLICT`다.
- `Records.save`: `referenceMessageIds` 중 피드백 카드마다 `content.referenceFeedbackRevisions: [{ messageId, revision }]`으로 확인한 버전을 보낸다. 누락은 `INVALID_INPUT`, 버전 변경은 `REFERENCE_CHANGED`다. 일반 메시지에 피드백 버전을 붙일 수 없다.
- `Records.get`: 기존 `referenceMessageIds`를 유지하고 `referenceSources`를 추가한다. 피드백 항목은 `messageId`, `feedbackId`, `feedbackRevision`을 반환한다. 임상 원본과 함께 치료사에게만 보인다.

## 권한·공유 이력·복구

현재 사용자/소속/관계와 과거 열람 범위는 `Conversations.inRoom`을 재사용한다. 대화방 → 사용자/소속 → 참여 관계 순서로 잠그고 버전 확인·원본 수정본·카드·요청 영수증·내용 없는 감사 이벤트를 함께 저장한다. 일정·담당 관계 변경은 이 순서 앞에 센터 일정 잠금을 추가하지만 피드백은 센터 잠금을 요구하지 않는다. 센터 관리자는 임상 피드백을 조회하지 못한다.

피드백은 원래 공유본에 고정된다. 재공유로 새 활동 카드가 생겨도 예전 피드백을 새 카드로 옮기지 않는다. 종료된 공유본은 보호자에게 피드백과 인용 내용까지 숨긴다. 이미 보낸 독립 답변 본문은 삭제하지 않으며, 치료사는 원본과 내부 검토를 계속 조회한다. 종료된 활동에 새 피드백·편집·공개 답변을 받을 수 없다. 이전에 성공한 동일 요청의 재시도는 기존 결과만 반환한다.

`from_now` 관계로 새로 연결된 사람은 연결 이전 활동에서 유래한 피드백을 볼 수 없다. 피드백 자체의 발신 순번이 연결 이후여도 같다. 직접 조회·목록·안 읽은 개수·인용·읽음·검토·기록 참조에 같은 경계를 적용한다. 해당 피드백을 인용한 이후의 독립 메시지는 열람할 수 있으나 인용 부분은 가린다.

DB에서는 피드백 수정본·검토 메모의 덮어쓰기/삭제, 원래 공유본/작성자의 변경, 카드 중복, 카드 없는 피드백 커밋, 버전 없는 피드백 인용·참조를 거부한다. 같은 센터·방의 원본에만 연결되도록 복합 외래 키를 둔다. 006은 추가형 마이그레이션이며 기존 001~005 SQL은 변경하지 않았다.

## 검증과 남은 한계

- `npm run test:server`: 66개 통과(기존 53개 + 피드백 13개).
- `npm test`: 25개 통과(기존 23개 + 공통 내용 검증 2개).
- `npm run check`, `npm run build`, `git diff --check`: 통과.
- 권한 위조·비활성 계정·작성자 변경·다른 아동 연결·열람 범위·수정 충돌·중복 재시도·메모 비노출·철회·재공유·기록/인용의 당시 버전을 검증했다.
- 영수증 작성 직전 장애를 주입해 신규 카드/수정/검토 전체와 대화 순번·revision·감사 이벤트가 복구되는지 확인했다. 같은 요청으로 다시 시도하면 한 번만 반영된다.
- 005의 기존 임상 수정본을 006 적용 후 그대로 보존했다. 이전 공유 요약·답변의 001~004 업그레이드 테스트도 함께 통과했다.
- `agent-browser` 및 개발 서버 검증 스킬에 따라 DB 미연결 데모 서버의 화면 로딩·스크린샷·주요 요소·콘솔 오류를 확인했다. `tests/browser.mjs` 14개와 `tests/communication-browser.mjs` 8개 시나리오를 별도 브라우저 컨텍스트에서 통과했다. 보호자 피드백 입력/검토, 사진·영상, 재시도, 320/390px 및 키보드 접근을 포함한다. 사용자 브라우저 저장소에는 테스트 내용을 쓰지 않았다.
- 소통 브라우저 테스트 첫 실행에서는 자동 생성 WebM의 미리보기 실패로 영상 요소 대기가 만료됐다. 재실행은 코드 변경 없이 재생까지 통과했다. 첫 실패의 원인은 확정하지 못했으며 브라우저/미디어 fixture의 비결정성 가능성을 후속 확인 대상으로 남긴다. 영상 검사를 생략하거나 성공 기준을 완화하지 않았다.

검증 경계: 기존 로컬 화면 → 로컬 저장 흐름은 위 브라우저 테스트, 새 서버 서비스 → 테스트 DB → 역할별 응답은 서버 테스트로 각각 확인했다. 화면 → 새 피드백 API → 운영 DB 경로는 의도적으로 아직 없으므로 전체 서버 연동 검증 완료가 아니다. 외부 네트워크 서비스·실제 계정·임상 자료를 사용하지 않았다.

서버 검증은 실제 운영 DB가 아닌 인메모리 PGlite다. PostgreSQL 여러 연결의 잠금 경쟁·커밋 응답 유실·네트워크 장애 복구는 별도 검증이 필요하다. 서버 배포 패키지는 공통 규칙인 `src/record-fields.js`와 `src/feedback-fields.js`를 포함해야 한다.

009에서 사진·영상의 [피드백 수정본 연결·공유 접근](media-binding-storage.md)을 추가했다. 보호자 작성자는 본인의 검사 완료 서버 UUID만 선택하며 카드의 현재 수정본 파일을 공유한다. 같은 피드백의 새 수정본은 기존 연결 파일을 재사용할 수 있고, 이전 목록은 치료사 이력으로 남긴다. 종료된 활동의 파일은 원 업로더도 보호자 권한으로 열 수 없다. `attachments` 생략/빈 배열은 새 수정본의 파일 제거이며 과거 바이트를 지우지 않는다. 실제 검사/저장 엔진·장기 보존/파기 정책과 삭제 실행 경로는 미완성이다. 로컬 첨부 기능은 변경하지 않았으며 실제 아동·건강 데이터 투입 또는 운영 준비 완료로 해석하면 안 된다.
