# 센터별 파일 자원 제한

작성일: 2026-10-06. 서버 내부 저장 계층의 후속 작업이며 API·화면 연결·운영 배포가 아니다.

## 해결한 문제와 현재 상태

기존 제한은 사용자/대화방별 임시 업로드 24개·300MiB, 첨부 원본별 6개·100MiB, 검사 5회, 디코더 엔진별 동시성이다. 다른 아이 방·사용자를 이용하면 센터 전체의 파일 용량·요청 빈도·검사 대기량은 제한하지 못했다.

`015-media-resource-limits.sql`과 `MediaResourcePolicy`가 다음 센터 단위 한도를 추가한다. 운영 값은 선택하지 않았다. 신규/기존 센터의 정책은 기본 `revision: 0`, 미설정·신규 예약 중지다. 합성 시험에서만 명시적인 시험 정책을 설정한다.

| 설정 | 의미 |
| --- | --- |
| `storageBytes` | 원본·공유 후보·삭제 대기 객체와 준비 슬롯의 보수적인 용량 예약 합계 |
| `pendingUploads` | pending/receiving/quarantined/inspecting 전체 개수. 만료·5회 보류도 명시적 정리 전에는 포함 |
| `uploadsPerWindow`, `windowMilliseconds` | DB 시각 기준 이동 구간의 새 예약 개수. 사용자·아이 방에 관계없이 센터 전체에 적용 |
| `acceptingUploads` | 신규 예약만 일시 중지. 기존 영수증 재조회·수신·검사·권한 있는 파일 열람·취소/정리는 중지하지 않음 |

미설정/중지·용량·빈도·대기량 오류는 외부에 DB 원문을 보내지 않는 서비스 코드로 바꾼다. 실제 HTTP 오류 연결은 마지막 API 단계다. 기존 사용자/방별 한도와 첨부별 제한도 그대로 유지한다.

## 용량은 실측 사용량이 아니라 예약 상한

서로 다른 준비 형식에서 후보가 원본보다 커질 수 있으므로 원본 크기만 합산하지 않는다. 각 객체는 이미지 10MiB, 영상 50MiB 상한으로 계산한다. 준비 중이거나 ready인 새 업로드는 최소 두 슬롯을 예약한다. 즉 작은 이미지도 원본/후보 합계 20MiB, 영상은 100MiB를 예약할 수 있다. **실제 파일 크기·청구 용량·AWS 월 비용으로 표시하면 안 된다.**

객체가 더 많으면 `max(실제 미삭제 객체 수, 필요한 최소 슬롯 수)`를 계산한다. 이전 수신/검사 시도의 객체도 포함한다. 실패 후보는 delete_pending이 되어도 계속 계산하며, 새 후보가 추가 슬롯을 요구하면 파일 IO 전에 거부한다. 자기 삭제 확인 후 같은 업로드 ID·다른 후보 키로 다시 시도한다. 실패 후보를 폐기하는 정리 자체는 한도 때문에 막히지 않는다.

취소는 쓰지 않은 준비 슬롯만 반환한다. 이미 저장된 원본/후보는 실제 `remove` 성공과 ledger `deleted` 확정 후에 반환한다. 삭제 오류·응답 유실은 보수적으로 용량을 계속 보유하며 다음 정리에서 재확인한다. bound 파일과 검사 증거/기존 원본은 이 한도 때문에 삭제하지 않는다. 기존 자료를 줄여 한도에 맞추거나 기존 승인 파일을 재승인하지 않는다.

예약 합계는 DB/백업/격리 엔진 임시 메모리·디스크/파일시스템 fence와 메타데이터의 실제 사용량을 모두 측정하는 수치가 아니다. 저장 장치 별도 여유 공간·모니터링·보존 정책이 필요하다. 상한 방식은 과소 계산을 막지만 작은 파일에 과도하게 보수적이다. 향후 실측 용량을 도입하려면 검증된 객체의 크기·예약/해제 원자성·장애 복구 계약을 유지해야 한다.

## 권한·변경·잠금

- `MediaResourcePolicy.get(actor)`는 현재 활성 센터 관리자만 숫자 설정·예약 합계·대기량을 조회한다. 파일/아동/사용자/대화 ID, 이름·해시·임상 원문·검사 원문은 반환하지 않는다.
- `configure(actor, input)`은 서버에서 검증된 관리자 주체와 `expectedRevision`을 요구한다. 요청의 role로 권한을 얻지 않는다. 정지된 관리자·치료사·보호자·다른 센터 관리자는 거부한다.
- 용량/대기량을 현재 보유량 아래로 줄이면 정책·수정 번호·변경 이벤트를 함께 롤백한다. 사용량을 지워 맞추지 않는다. 중지는 기존 한도를 유지한 채 `acceptingUploads: false`로 한다.
- 정책 스냅샷/시각/수정 번호는 불변 이벤트로 보존한다. 이 이벤트는 설정 값의 변경 이력이며 운영 감사의 행위자 식별·승인/요금제 권한·경보 체계를 모두 완성한 것은 아니다. 운영 API 노출 전 허용 한도와 관리자 위임 범위를 확정해야 한다.
- 별도 센터 media 정책 행이 mutex다. `cb_centers`나 센터 일정 잠금을 업로드의 방 잠금 이후에 얻지 않으므로 일정/관계의 센터 → 방 순서와 섞지 않는다.
- 새 업로드/객체 할당은 정책 행을 커밋까지 잠근다. deferred 제약은 새 객체와 예약 슬롯의 일시 중복 대신 최종 트랜잭션 상태를 검사한다. 단조 감소인 객체 삭제는 객체 행을 잠근 뒤 정책 mutex를 요청하지 않아 정리 잠금 순환을 만들지 않는다.
- 동일 `clientId`·같은 내용의 권한 있는 재시도는 기존 영수증을 반환해 새 용량·대기량·요청을 소비하지 않는다. 새 예약 실패는 방 순번·ID·이벤트를 롤백하며 같은 발신 ID로 재시도할 수 있다.
- 시간은 DB가 설정한다. 취소/만료/삭제된 예약도 이동 구간 안에서는 빈도에 포함한다. 소유자 권한이 사라지면 이전 성공 영수증도 기존 정책처럼 반환하지 않는다.

작업 큐는 정책 미설정 또는 추가 검사 슬롯이 없는 센터의 작업을 건너뛴다. 다른 센터가 진행할 수 있고 검사 횟수도 소비하지 않는다. 이 조회는 스냅샷 힌트일 뿐이며 실제 선점 때 현재 권한과 DB 제약으로 다시 검사한다. 그 사이 용량이 소진되면 선점/임대/큐 횟수/객체 의도를 롤백한 뒤 idle로 돌아간다. weighted fairness·센터별 CPU 시간 배분·악용 방지 전체를 구현한 것은 아니다.

## 기존 자료와 검증

001~014 SQL/체크섬을 수정하지 않는다. 015는 기존 manifest·객체·준비 증거·메시지·큐를 그대로 두고 미설정 정책을 추가한다. 기존 자료를 조회하거나 정리할 수 있지만 새 업로드/검사 객체 할당에는 정책 설정이 필요하다. migration을 운영 DB에 적용한 것은 아니다.

## 남은 우선순위

1. [016 명시적 보류 검토·재개](media-work-reviews.md)는 내부 서비스로 구현했다. 운영 supervision·복구 절차/위임 정책은 남아 있다. 횟수 초기화나 검사 우회로 승인하지 않는다. 위 482/28/18개는 015 당시 증거이며 최신 전체 검증은 016 문서를 따른다.
2. 원본/후보/증거/백업/fence 보존·파기, 과거 파일 전환, 운영 영구 매체와 복원 검증.
3. 국내 공급자·키/로그/지원·메일/계정 복구·운영 권한/요금제 한도·실제 자원 값 확정.
4. 마지막 API·화면 서버 연결, 다른 실물 기기 전송·재접속 및 사용자 이해도 확인.
