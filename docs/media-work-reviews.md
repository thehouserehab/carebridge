# 검사 보류 작업의 명시적 검토·재개

작성·검증: 2026-10-06. 개편안의 사진·영상 전달을 위한 서버 내부 후속이다. **재개는 파일 승인·공유가 아니다.** API·화면 연결은 마지막 단계로 유지하며, 운영 계정·DB·파일·자동 서비스·배포를 변경하지 않았다.

## 현재 상태와 변경 이유

기존 [014 검사 큐](media-work-queue.md)는 5회 실패하면 자동·수동 검사를 모두 보류한다. 장애가 해결되어도 횟수를 초기화하거나 원본을 재업로드하지 않고 명시적으로 재검사할 경로가 필요했다. [015 자원 제한](media-resource-limits.md)과 원본/후보 분리 저장·현재 참여 권한·후보만 제공하는 정책은 그대로 유지한다.

신규 `MediaWorkReviews` 내부 서비스는 현재 센터 관리자가 보류 상태를 조회하고, 복구 사유와 재검사 확인을 명시한 한 건을 재개한다. 파일 이름·형식·크기·해시·객체 키·원본/후보 바이트·아동/소유자 정보·대화/치료 내용을 반환하지 않는다. 센터 관리자에게 임상 대화나 파일 열람 권한을 추가하지 않았다.

## 상태와 안전 규칙

자동 검사 최대 5회 → `blocked` → 명시적 검토 영수증과 추가 1회 권한을 같은 트랜잭션으로 저장 → `retry` → 전체 검사 재실행 → `completed` 또는 다시 `blocked`.

- 누적 `attempts`를 0으로 돌리지 않는다. 한 검토에 검사 **한 번만** 추가하며, 파일당 평생 검토는 기술적 안전 상한 **3건**, 누적 시도는 최대 **8회**다. 이 수치는 이번 구현의 무한 재시도 방지 경계이며 운영 서비스 수준·요금제·관리자 위임 정책이 확정되었다는 뜻이 아니다. 운영 노출 전 실제 복구 절차와 함께 검토해야 한다.
- 사유는 `ENGINE_RESTORED`, `STORAGE_RESTORED`, `CONFIGURATION_CORRECTED`만 받는다. 자유 텍스트·파일 내용·진단 로그·임상 판단을 입력받지 않는다. 사유 선택은 관리자의 선언이지 실제 엔진 상태나 안전성의 증거가 아니다.
- 검토 당시 업로드 버전·누적 횟수와 `confirmReinspection:true`가 필요하다. 변경된 상태는 충돌/불필요한 요청으로 처리한다.
- 관리자의 현재 계정·센터 역할과 원 소유자의 현재 계정·센터 소속·해당 방 참여·과거 열람 시작 순번을 검사한다. 호출자가 제출한 역할은 권한이 아니다. 만료·취소·완료·악성 판정·연결 해제·과거 열람 범위 축소를 되돌리지 않는다.
- 원 업로드 ID·객체·manifest·만료 시각·업로드 버전은 재개 요청 자체로 변경하지 않는다. 원본을 다른 사용자의 소유로 바꾸거나 후보를 재사용하지 않는다.
- 자원 정책은 명시적으로 설정되어 있어야 한다. 신규 업로드 중지는 기존 보류 검토를 막지 않지만, 실제 다음 선점의 용량/권한/기한 검사는 정상 큐 경로에서 다시 수행한다. `canResume`는 운영 상태의 현재 힌트이며 즉시 실행·용량 확보·파일 승인 보증이 아니다.
- 다음 검사에서 원본 전체 해시/크기·ClamAV, 별도 파일 worker의 전체 디코딩/metadata 처리/후보 디코딩, 후보 ClamAV, 별도 후보 저장/해시 재조회·불변 증거를 모두 다시 요구한다. 후보 손상·미저장·원본 읽기 실패를 관리자 요청으로 우회하지 않는다.

## 중복·실패·권한 해제 처리

같은 센터·관리자·`clientId`와 같은 입력은 불변 검토 영수증을 반환한다. 다른 입력은 `IDEMPOTENCY_CONFLICT`다. 이미 검사가 끝나거나 취소/만료된 뒤의 같은 요청 재전송은 **과거 요청을 접수했다는 확인**일 뿐, 현재 작업 상태를 바꾸거나 추가 검사권을 발급하지 않는다. 이 과거 영수증 조회에도 관리자의 현재 권한이 필요하다.

검토 영수증 삽입과 큐의 추가 횟수/재개 전환은 함께 커밋한다. 한쪽 실패 시 둘 다 롤백한다. DB 커밋 응답을 잃으면 새 연결이 같은 요청을 재전송해 저장된 영수증을 확인하며, 성공/실패를 추측하거나 자동으로 새 ID를 만들지 않는다. 서로 다른 요청이 같은 보류 작업을 동시에 재개해도 한 건만 반영된다.

방 → 현재 관리자 → 업로드/큐 → 현재 원 소유자 → 전용 자원 정책 순서로 검사한다. 관계 변경은 같은 방 잠금 순서를 사용한다. 별도 PostgreSQL 연결에서 실제 계정 행 잠금에 대기하는 것을 관찰하고, 소유자 해제 커밋 후 재개가 거부되는 사례를 검증한다. 감사 행에는 불변 관리자 내부 ID·고정 사유·검토 전 버전/횟수·검토 순번·DB 시각을 남긴다. 센터 자원 설정의 행위자 감사·전사 운영 감사 전체가 완료된 것은 아니다.

## 조회와 SQL 경계

`list`는 자기 센터의 보류 작업만 opaque 대화/업로드 ID, 상태, 횟수, 버전, 고정 실패 코드, 만료/재개 가능 여부로 보여준다. 기본 50건·최대 100건이며 대화/업로드 ID의 키셋 커서를 사용한다. 이는 **변하는 운영 현황**으로, 여러 페이지가 동일한 고정 스냅샷이라는 보장은 없다. 작업이 바뀌면 첫 페이지부터 갱신해야 한다. `get`과 `resume`은 센터 관리자의 현재 방 관리 권한도 확인한다.

추가형 `016-media-work-reviews.sql`은 001~015 SQL/체크섬을 바꾸지 않는다. 기존 큐의 모든 필드/상태·원본·증거·메시지를 유지하고 추가 검토 횟수 0/최근 검토 없음만 더한다. 기존 보류를 자동 재개하거나 정책을 자동 설정하지 않는다. SQL에서도 횟수 초기화·조작된 추가 권한·영수증 단독 커밋·영수증 수정/삭제·현재 권한 없는 검토·미설정 정책을 거부한다. 운영 마이그레이션을 실제 적용하지 않았다.

주요 안전 오류는 `MEDIA_REVIEW_CONFLICT`, `MEDIA_REVIEW_NOT_REQUIRED`, `MEDIA_REVIEW_LIMIT`, `MEDIA_OWNER_UNAVAILABLE`, `MEDIA_RESOURCES_UNCONFIGURED`, `UPLOAD_EXPIRED`다. 이후 HTTP 경계는 내부 DB/엔진 오류를 공개 응답이나 로그에 그대로 직렬화하지 않아야 한다. 본 서비스에는 HTTP 경로·운영 CLI·자동 실행을 추가하지 않았다.
