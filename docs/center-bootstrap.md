# 최초 센터 관리자 생성: 운영자 전용 절차

2026-10-02. P1의 실제 계정·초대 흐름에 필요한 최초 관리자 생성 기반이다. **내부 저장 서비스와 운영자 CLI를 구현했으며 실제 운영 센터/계정을 생성하거나 배포하지 않았다.** 브라우저 UI·저장 키·파일·로그인/초대 HTTP 경로는 그대로다. API와 화면의 서버 연결은 마지막 단계로 유지한다.

## 해결한 문제와 범위

초대 발급에는 활성 센터 관리자 계정이 필요하지만 최초 관리자가 없는 새 설치에서 이를 만드는 절차가 없었다. `Auth.bootstrapNewCenter()`는 운영자가 승인한 **새 센터와 신규 관리자 계정**만 생성한다. 기존 센터 인수·추가 관리자·기존 계정 승격·비밀번호 재설정·정지 해제 기능으로 사용하지 않는다.

센터, 활성 사용자, 이메일/기존 scrypt 해시 형식의 계정, `center` 소속, 생성 영수증을 하나의 트랜잭션으로 저장한다. 아동·프로필·임상 기록·대화 참여자·초대·세션은 자동 생성하지 않는다. 생성 후 일반 로그인과 기존 관리자 초대 서비스를 사용할 수 있지만 실제 메일/운영 UI 연결은 아직 없다.

암호 정책과 로그인·세션 동작은 기존 `Auth`를 재사용한다. 별도 기본 비밀번호, 임시 평문 비밀번호 파일, 관리자 세션 우회 또는 공개 회원가입 경로는 없다. 운영자 도구에도 이메일·비밀번호·DB URL을 인자로 받는 옵션을 제공하지 않는다.

## 권한·한 번만 생성·재시도 계약

입력은 `operationId`(v4 UUID), `centerId`, 동일한 `confirmNewCenter`, `email`, `password`다. 호출자 지정 `role`·`userId`·`force` 등의 추가 필드를 거부한다. 관리자 내부 사용자 ID는 서버가 새로 발급한다.

운영 DB 계정이 `cb_center_bootstraps`에 INSERT할 수 있는지 실제 DB 권한으로 확인한다. 일반 앱 런타임 DB 계정은 이 권한을 가져서는 안 되며 같은 영수증 재조회도 일반 계정에서는 거부한다. 브라우저의 `center` 역할이나 일반 세션을 전달하는 것으로 운영자 권한을 얻을 수 없다. 새 메서드는 인증 HTTP 라우터에 연결하지 않았다.

| 상황 | 동작 |
| --- | --- |
| 새 센터 + 새 이메일 + 새 작업 ID | 다섯 종류의 저장 행이 함께 커밋된다. |
| 같은 작업/센터/이메일/비밀번호 재시도 | 기존 계정과 활성 관리자 상태를 확인하고 같은 영수증만 반환한다. hash·로그인 실패/잠금·권한·세션은 바꾸지 않는다. |
| 같은 작업 ID의 다른 대상/자격 증명 | `BOOTSTRAP_CONFLICT`. 비밀번호 변경 요청으로 처리하지 않는다. |
| 기존 센터 또는 다른 ID로 같은 센터 생성 | 비어 있는 기존 센터도 `BOOTSTRAP_EXISTS`. 기존 데이터와 관리자 권한을 덮어쓰지 않는다. |
| 이미 계정이 있는 이메일 | `BOOTSTRAP_ACCOUNT_EXISTS`. 계정 승격·재활성화·새 센터 연결을 하지 않는다. |
| 완료 후 관리자/소속 정지·역할 변경·자격 증명 삭제 | `BOOTSTRAP_CLOSED`. 재시도로 복구하지 않는다. |
| 일반 앱 DB 계정 | `BOOTSTRAP_FORBIDDEN`. 생성/완료 재시도를 거부한다. |
| 저장 도중 실패 | 전체 롤백. 같은 작업 ID로 재시도 가능. |
| 커밋 응답 유실 | 성공이라고 추측하지 않는다. 같은 ID와 자격 증명으로 영수증을 확인한다. |

희소한 운영 작업끼리는 전용 advisory transaction lock으로 직렬화한다. 실제 PostgreSQL 여러 연결에서의 잠금 경쟁은 아직 검증하지 않았다. 앱 DB 계정·마이그레이션 계정·운영자 계정의 분리와 실제 권한 설정은 운영 환경에서 확인해야 한다. 앱에 DB 소유자/슈퍼유저를 쓰거나 모든 테이블에 일괄 권한을 부여하면 이 권한 분리가 무력화된다.

현재 프로젝트의 공통 저장 스키마 `public`을 대상으로 권한을 확인하고 트랜잭션/영수증 검사 함수의 `search_path`를 고정한다. 연결의 검색 경로에 같은 이름의 테이블을 먼저 넣어도 다른 영수증의 INSERT 권한을 관리자 생성 권한으로 인정하거나 잘못된 스키마에 생성 결과를 기록하지 않는다. 사용자 지정 스키마 배포는 지원/검증한 것이 아니다.

## 운영자 CLI 사용

이 명령은 코드만 준비된 상태다. 실제 대상 DB 승인, 스키마 적용, 분리된 운영자 계정, TLS/인증서와 백업 확인 뒤에만 실행한다. 이 작업에서 실제 DB에 실행하지 않았다.

저장소 루트에서 `node server/bootstrap-center.mjs --help`로 안내를 확인한다. 최초 실행은 다음과 같다.

```powershell
node server/bootstrap-center.mjs
```

새 센터 ID와 작업 ID를 먼저 표시한다. 이 두 **불투명한 내부 ID**를 작업 증적으로 보존한다. 이후 DB URL, 이메일, 비밀번호, 비밀번호 확인, `CREATE NEW CENTER` 최종 확인을 입력한다. 모든 입력은 숨김이며 비밀값은 출력·로그·파일에 남기지 않는다. 실제 비밀번호/DB URL을 채팅에 보내거나 명령 인자로 넣지 않는다.

응답 유실/결과 불명 시 같은 두 ID로 실행한다. 아래 값은 플레이스홀더이며 실제 출력 ID로 교체한다. 같은 이메일·비밀번호를 다시 확인하고 영수증만 조회한다.

```powershell
node server/bootstrap-center.mjs --center-id "<opaque-center-id>" --operation-id "<operation-uuid>"
```

파이프·리다이렉션, 별도 비밀 입력 파일, `DATABASE_URL` 등 환경변수의 자동 DB 선택은 지원하지 않는다. CLI는 스키마를 자동 생성/마이그레이션하지 않는다. 사용자가 숨김으로 입력하고 승인한 대상에만 접속한다. 입력 대기·실행 중 강제 종료로 결과가 불명확하면 새 ID를 발급해 다시 생성하지 말고 같은 ID로 확인한다.

DB는 기본 인증서 검증 TLS다. URL의 모든 쿼리/fragment를 거부해 `sslmode` 등의 인증서 검증 우회를 막는다. node-postgres는 연결 문자열의 SSL 옵션으로 직접 설정한 `ssl` 객체를 덮어쓸 수 있으므로 이를 허용하지 않는다. [공식 SSL 문서](https://node-postgres.com/features/ssl)를 참고한다. 사설 CA는 승인된 신뢰 저장소 구성이 필요하며 인증서 검증을 끄는 원격 옵션은 없다.

`--local-test`는 리터럴 `127.0.0.1` 또는 `::1`의 **별도 로컬 시험 DB**에만 비TLS 접속을 허용한다. `localhost`/원격 주소에서는 거부한다. 운영 DB에 사용하지 않는다. 실제 DB의 국내 위치·접근·로그·지원 경로까지 이 도구가 판정하는 것은 아니다.

입력은 raw mode로 echo를 끄고, 다음 숨김 질문 사이에도 echo가 켜지지 않게 유지한다. Backspace/줄 지우기·Ctrl-C/D·UTF-8 분할 입력, 취소·시간 초과·오류 뒤 터미널 복원을 처리한다. 제어/escape 문자와 여러 줄 붙여넣기는 거부한다. [Node TTY 문서](https://nodejs.org/api/tty.html)에 근거한 방식이다. OS의 화면 녹화/키로거·메모리 dump·강제 종료까지 차단하는 기능은 아니며 JavaScript 문자열의 안전한 메모리 삭제도 보증하지 않는다. 신뢰할 수 있는 개인 운영 터미널에서만 실행한다.

## 스키마·감사·운영 조건

011은 기존 001~010 파일을 수정하지 않는 추가형 마이그레이션이다. `cb_center_bootstraps`에는 작업 ID·센터 ID·관리자 내부 ID·시각만 저장하며 이메일·비밀번호·토큰·임상 내용은 없다. 중복 센터/작업 ID, 유효한 활성 관리자 계정 여부와 영수증 불변성을 DB가 검사한다. 영수증을 지워 기존 설치를 다시 초기화하는 경로를 만들지 않는다.

PUBLIC 권한을 제거했으며 별도 승인된 운영자 역할에만 SELECT/INSERT 및 필요한 센터/사용자/계정/소속 저장 권한을 부여해야 한다. 런타임 역할에는 영수증 INSERT 권한을 주지 않는다. 모든 인증/DB bind parameter·dump·운영 터미널 녹화가 개인정보를 남길 수 있으므로 운영 DB 로그/백업/지원 접근도 통제한다. DB 관리자/동일 권한의 악성 프로세스에 대한 보안 경계라고 주장하지 않는다.

기존 센터 인수·관리자 추가·계정 복구는 신원/권한 확인과 별도 감사 정책이 필요하므로 의도적으로 구현하지 않았다. 실제 메일 발송·계정 복구·MFA/유출 비밀번호 확인, 요청 빈도 제한·Origin/CSRF·운영 TLS·여러 기기의 세션 폐기 검증은 남아 있다. 현재 인증 기반이 운영 투입을 허용하는 완성된 인증 체계라는 의미는 아니다.

## 변경 파일·검증

- `server/migrations/011-center-bootstrap.sql`: 운영자 전용 생성 영수증·활성 관리자 검사·불변/권한 제약.
- `server/auth.mjs`: 기존 credential 규칙을 재사용하는 새 센터 생성·권한·중복/재시도. 기존 로그인/초대/세션 경로는 유지.
- `server/bootstrap-center.mjs`, `server/operator-terminal.mjs`: 숨김 대화형 입력·대상/TLS 확인·명시적 승인·비밀값 없는 결과/실패.
- `server/tests/center-bootstrap.test.mjs` 18개, `server/tests/bootstrap-cli.test.mjs` 20개: 원자적 생성·실패/커밋 응답 유실·기존 데이터/계정·권한/검색 경로·HTTP 비노출·터미널/CLI 계약.
- 기존 서버 테스트 9개 파일: 011 이후에도 이전 업그레이드 데이터 보존을 검사하도록 기대 목록만 추가.
- README·서버 기반·계정 UI·기본정보 문서: 현재 상태/실행 절차/남은 경계 정리.

`npm run test:server`는 207개(기존 169개 + 38개), 실패/취소/건너뜀 0. `npm test` 31개, `npm run check`, `npm run build`, `git diff --check` 통과. 새 파일의 줄 끝 공백도 없고 `dist/`에 운영자/서버 코드·문서가 포함되지 않음을 확인했다. 최초 업그레이드 시험에서 가상 프로필 fixture의 필수 revision 누락을 수정했으며 제품 제약을 완화하지 않았다.

시험은 단일 연결 인메모리 PGlite와 합성 값이다. 실제 PostgreSQL의 여러 연결·TLS·역할 배포를 검증하지 않았다. CLI 단위 시험의 입력/DB는 대역이다. 추가로 실제 Windows PTY에서 합성 입력이 출력에 나타나지 않는지 확인했고, 최종 생성 확인을 거부해 DB 접속/계정 생성 없이 종료했다. 실제 운영 생성·계정 복구·메일·파일 엔진·백업/복원·국내 통제·기기 간 소통은 미완료다. UI를 변경하지 않아 이번 단계에서 브라우저 검사를 다시 실행하지 않았다.
