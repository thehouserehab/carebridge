## 2026-10-10 현재 스키마의 비공개 반영 메모와 재시작 검증

기존 E 성공 실행은 스키마022의 일반 소식 반영 메모 영수증 도입 전 소스였다. 이번에는 **새 UUID의 가상 DB만** 생성하여 현재 전체 마이그레이션·권한 v6 적용/검증을 통과한 뒤 실제 runtime 계정으로 메모를 저장했다. 기존 E 세션을 업그레이드하거나 키를 채택하지 않았다. 스키마/권한 적용 근거는 준비 단계의 필수 검증·고정 소스 지문과 실제 C05 처리 성공이며, 모든 테이블의 모든 작업을 새로 검사했다는 뜻은 아니다.

## 달라진 점

기존 native 실행기는 검증 후 자동 종료했다. `dev:synthetic-e`는 같은 인증·권한·PostgreSQL·DPAPI·TLS·미디어 검사 서비스를 재사용하여 사용자가 터미널에서 준비하고 Ctrl+C로 종료하는 **새 가상 세션**을 제공한다. 기존 4173 프로토타입과 4180 메모리 실행기는 변경하지 않는다.

- 치료사·보호자 가상 계정과 가상 아동 2명, 목표·오늘의 일정만 생성한다. 기록·공유본·피드백·첨부는 사용자 화면에서 작성한다.
- PostgreSQL은 E 드라이브의 새로운 UUID 하위 경로에 저장한다. 기존 데이터베이스를 채택하거나 덮어쓰지 않는다.
- 실제 검사기 상태와 별도 worker의 DB 권한 확인, API 준비가 완료되어야 접속 주소를 표시한다.
- 세션 계정은 `.test` 주소와 임의 비밀번호이며 직접 사용하는 터미널에만 한 번 표시한다. 파일·URL·시험 보고서에는 자격증명을 기록하지 않는다.
- `127.0.0.1`만 사용한다. 같은 PC의 일반 창과 별도 프로필/시크릿 창은 서로 다른 로그인 상태로 접속할 수 있다. 다른 PC·휴대전화는 접속할 수 없다.

## 실행

준비된 PostgreSQL 18.6-5, PowerShell 7, Docker Desktop Linux 엔진 및 기존 검사 이미지가 필요하다. 설치·전역 설정 변경은 이 명령이 수행하지 않는다. 일반 PowerShell 터미널에서 프로젝트 디렉터리를 열고 실행한다.

```powershell
npm run dev:synthetic-e -- --base E:/CarebridgeBeta --powershell "C:/Users/USER\.cache\codex-runtimes\codex-primary-runtime\dependencies\native\powershell\pwsh.exe" --confirm-synthetic-e-drive
```

준비에는 몇 분이 걸릴 수 있다. 표시된 루프백 주소를 열고 각각 가상 치료사·가상 보호자로 로그인한다. 출력 리디렉션이나 파이프에서는 실행하지 않으며, 비밀번호가 나타나는 화면을 공유하지 않는다.

권장 체험: 치료사 홈 일정의 기록하기 → 수행·반응·다음 계획 작성 → 공유 요약/가정 활동 작성 → 미리보기에서 받는 보호자와 공개 내용 확인 → 공유 → 보호자 홈에서 활동 경험 남기기 → 치료사 대화에서 확인. 사진·영상은 대화에서 가상 파일만 선택하고 실제 준비 완료 이후 전송한다. 업로드만으로 상대에게 공유되지 않는다.

## 종료·보존·제한

실행 중 API만 정상 재시작하려면 같은 터미널에 `r`을 입력하고 Enter를 누른다. 이전 API의 실제 exit 0·close·입출력 종료가 확인되어야 다음 API를 띄운다. 재시작 중에는 준비 완료 주소를 표시하지 않으며, 완료 후 출력된 새 주소에서 처음 안내한 가상 계정으로 다시 로그인한다. 비밀번호는 다시 표시하거나 파일에 저장하지 않는다. 정상 재시작은 한 세션에서 최대 10회이며 한도 거부는 현재 정상 API를 종료하지 않는다.

이 동작은 **동일 실행기가 소유한 API만** 재시작한다. DB·검사 작업자·파일·TLS/DPAPI 키는 그대로 유지하며 다른 E 폴더나 이전 키를 채택하지 않는다. 자동 장애 재시작·작업자/DB/PC 재시작·종료한 세션 재개가 아니다. API 재시작 실패나 작업자 장애는 기존 전체 종료 절차로 연결된다. 재시작 중 Ctrl+C도 같은 소유 자원의 실제 종료를 기다린다. 저장된 자료의 재열람과 미전송 UI 초안의 복원은 구분하며, 후자는 이번 재시작 기능으로 보장하지 않는다.

Ctrl+C는 API → 실제 worker 종료 → DB 연결/프로세스 종료 → 검사 자원 → 이번 실행의 키·잠금 순서로 정리를 요청한다. 시작 중 Ctrl+C도 같은 소유 자원의 종료를 기다린다. 시간 경과나 stop 응답만으로 종료를 확정하지 않는다. 진행 중 검사 환경 준비 명령이 끝날 때까지 기다릴 수 있다.

종료가 불확실하거나 파일 소유권/내용이 달라지면 관련 자원과 잠금을 보존한다. 같은 터미널에서 종료를 재확인할 수 있지만, 영구적인 소유권 불확실성은 자동으로 해제하지 않는다. 다른 실행기의 잠금을 삭제하거나 Docker 전체 정리를 실행하면 안 된다.

**이 버전은 종료 후 같은 세션 재개를 지원하지 않는다.** 실행 중 새로고침·재접속 시에는 E 저장 자료가 유지된다. 정상 종료 후 가상 DB·업로드 진단 자료는 E에 남지만 이번 자격증명/TLS 키는 정리되며, 다음 실행은 새 계정과 새 자료로 시작한다. 따라서 상시 서비스·백업/복원 완성으로 취급하지 않는다. 자동 삭제나 장기 보존 정책도 아직 없다.

사진·영상 예약량은 세션당 120 MiB, 대기 업로드 4건, 시간당 8건이다. 실제 파일 크기와 별개로 처리 중 이미지 20 MiB/영상 100 MiB의 상한을 예약하므로 반복 체험은 제한에 걸릴 수 있다. 이는 시험 안전 한도이며 실제 서비스 요금제나 운영 용량 계획이 아니다.

### 첫 통합 실행의 실패와 입력 구분

`synthetic-e-session-36101910-3319-4185-adc7-3db503203efb.json`은 실패 증거로 보존한다. 기록·공유·피드백·PNG 흐름은 통과했지만 WebM 입력이 180초 안에 준비 완료되지 않았다. 브라우저 오류/외부 요청은 없었고, API/worker 각각 실제 exit 0·pipe 종료, PostgreSQL 종료, 키·잠금·검사 자원 정리가 확인됐다. 성공으로 집계하지 않는다.

기존 브라우저 재생용 WebM 1,101바이트를 순수 메타데이터 변환기에 넣어 `SCAN_UNAVAILABLE`, 요소 `0x75a1`을 재현했다. VP8 자체가 아니라 해당 입력의 추가 블록이 현 허용 정책 밖이다. 첫 native 실행의 최초 실패 단계까지 특정한 것은 아니며, 변환 이전 디코더 검사도 별도 경계다. 브라우저에서 재생된다는 사실은 준비 정책 통과를 보장하지 않는다.

허용 목록이나 검사 결과를 바꾸지 않았다. 대신 이 입력의 미지원 회귀를 추가하고, 실제 격리 시험 생성기로 새 H.264 MP4 원본을 한 번 생성했다. `tests/native-video-fixture.mjs`는 무음 32×24/2초/4프레임 패턴의 **미처리 원본** 2,439바이트와 SHA-256을 고정한다. 이전 승인 후보나 승인 DB를 재사용하지 않으며 매번 UI 업로드 후 전체 검사를 거친다.

검사 미완료 코드가 있는 격리 파일에는 전송 불가와 취소/다른 지원 파일 선택 안내를 표시한다. 기존 재시도·승인·전송·API 규칙은 유지한다. 다음 native 보고서부터는 경로·파일 내용 없이 고정 업로드 상태와 실패 코드의 변화를 최대 24건 기록하여 일반 대기와 검사 실패를 구분한다.

### 기존 확장 native 회귀의 후속 실패

위 최종 신규 세션 성공 직후, 별도 직렬 실행한 기존 `windows-postgres-check.mjs --verify-native-media`는 **실패**했다. run `2b92e616-abf8-4fef-a0a1-dab58ed1f7ce`, 실제 exit **1**, 기존 전체 55개 중 상위 완료 항목 **13개**에서 중단됐다. 전체 로그 `test-results/synthetic-e-existing-native-20261009.log`와 브라우저 `test-results/native-prepared-2b92e616-abf8-4fef-a0a1-dab58ed1f7ce/results.json`을 보존한다. 이전 단계의 55/55 성공은 이번 코드의 재검증 성공으로 인용하지 않는다.

- phase 609의 네 번째 worker는 `db-open begin → failed`만 관측됐다. 작업자 준비·큐 처리에 도달하지 않아 브라우저 사진은 격리 상태에서 180초 후 실패했다. 앞의 세 작업자는 DB 연결·종료 단계를 통과했고, API 로그인·업로드는 동작했다. 공통 PG 설정 전체 오류로 단정할 근거는 없지만, 이번 공통 수명 코드 추출과의 관련성도 확정적으로 배제하지 못했다.
- 기존 실행기의 `started`는 bootstrap 전송 완료이며 실제 DB 준비 완료가 아니다. 따라서 작업자 실패와 별개로 브라우저가 대기했다. 신규 `dev:synthetic-e`는 별도 실제 admission을 확인한 뒤 API를 연다.
- API는 stop·exit 0·pipe 종료가 관측됐지만 `closeObserved:false`와 관측 시간 초과로 정상 정리를 입증하지 못했다. 이는 DB 연결 실패와 별도 문제다. 실패 후 observer가 종료 판정을 내리며 리스너를 해제할 수 있어, 이후 실제 close 이벤트가 없었다고 단정하지 않는다.
- 두 실행의 해당 라벨을 읽기 전용으로 조회한 결과 검사 컨테이너·이미지·볼륨은 모두 0개였고, 해당 PG의 `postmaster.pid`도 없었다. 신규 최종 세션은 키·자격증명·잠금까지 정리됐다. 실패한 기존 실행은 `postgres-check-2b92e616-abf8-4fef-a0a1-dab58ed1f7ce/tls`와 `credential-check-2b92e616-abf8-4fef-a0a1-dab58ed1f7ce`를 보존했다. 가상 자료 전용 파일이며 자동 삭제하거나 재사용하지 않았다.

현재 보고서에는 DB 열기 실패의 세부 원인이 없다. 자격증명·경로·SQL·원문 오류를 노출하지 않는 고정 단계 진단으로 자격증명 로드, TLS/접속, 권한 검증을 구분하고, 종료 관측 경계도 별도 재현해야 한다. 성공 결과만 얻기 위한 반복 실행이나 검사·종료 기준 완화는 하지 않았다. **새 가상 흐름 성공과 별개로 전체 native 회귀는 미해결 상태다.**

## 남은 작업

기록·피드백 첨부와 같은 실행 내 API 재시작/재로그인 검증은 후속 단계에서 연결했다. 2026-10-10 원 개편안 대조 기준의 다음 핵심 간극은 **완전 종료 후 같은 가상 세션 재개**다. 새 세션에 한해 Windows 계정으로 보호한 연결 자격증명·TLS 키를 보존할지 사용자 선택을 받은 뒤 설계·구현한다. 현재의 종료 시 키 삭제 정책은 바꾸지 않았으며 기존 가상 폴더/키 채택이나 잠금 삭제로 복구를 대신하지 않는다. 장기 실행·DB/worker 장애 복구도 별도 미완료다. 본인 비밀번호 변경 화면 같은 인접 기능을 먼저 추가하지 않는다. 초기 콘텐츠 관측 실패의 세부 원인과 이전 Windows 간헐 오류의 전체 원인은 아직 미확정이다.

여러 실물 기기·사람 사용성, 운영 보존·파기·복구와 독립 백업은 남아 있다. 별도 백업 매체가 없으므로 실제 아동 자료 수집과 외부 접속은 계속 보류한다. 공개 배포는 하지 않았으며 원 개편안 전체/P1 완료를 의미하지 않는다.
