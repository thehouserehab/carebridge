# 검사 완료 첨부의 원본 연결·공유 접근

2026-10-05 후속: [013 분리 저장](media-preparation-storage.md)에서 기존 첨부/원본 ID와 권한·공유·철회 이력을 유지하고 새 승인 파일은 저장된 후보로만 제공한다. 실제 제공 크기를 첨부 목록에 표시하고 묶음 제한은 원본/후보 중 큰 용량을 적용한다. 원본과 후보 모두 bound 정리 보호 대상이다. 아래 009 당시 검사 미연결 기록과 최신 결합/저장 결과를 구분한다. API·국내 운영·실물 기기 전송은 아직 없다.

2026-10-02. P1의 서버 내부 파일 연결 단계다. [비공개 임시 업로드](media-upload-storage.md)의 검사 완료 파일을 대화·기록·피드백에 연결했다. **API·화면 연결, 실제 검사 엔진, 국내 운영 저장소, 기기 간 전송은 아직 없다.** 현재 웹앱은 기존 localStorage/IndexedDB 데모를 계속 사용한다. 배포·유료 자원 생성·기존 로컬 파일 삭제는 하지 않았다.

## 구현 범위와 공유 규칙

| 연결 위치 | 저장·열람 규칙 |
| --- | --- |
| 직접 대화 | 본문 없이 사진/영상만 보낼 수 있다. 해당 메시지를 열람할 수 있는 현재 방 참여자에게 전달한다. 첨부 목록과 내용은 확정 후 변경하지 않는다. |
| 치료 기록 | 수정본별 첨부 목록을 보존한다. 기본 비공유이며 파일마다 `share: true`를 선택해야 공유 미리보기와 공유본에 포함된다. 임상 원본·비공유 파일은 현재 담당 치료사만 조회한다. |
| 공유 카드 | 확정한 기록 수정본의 선택 첨부만 복사한다. 기록 수정만으로 과거 공유본의 파일이 바뀌지 않는다. 재공유하면 새 목록으로 새 카드를 만들고 이전 보호자 접근은 닫힌다. |
| 활동 피드백 | 보호자 작성자의 수정본별 목록을 보존한다. 수정해도 카드 하나를 유지하며 현재 목록만 보호자에게 보여준다. 치료사는 이전 수정본의 파일을 명시적으로 조회할 수 있다. |
| 철회·종료 | 공유 카드와 그 활동에서 유래한 피드백 파일은 보호자에게 숨긴다. 파일 업로더 본인도 소유권으로 우회할 수 없다. 치료사 이력과 이미 보낸 독립 대화의 파일은 유지한다. |

센터 운영 역할에는 임상 대화나 파일 열람 권한이 없다. 현재 사용자·센터 소속·담당 관계와 과거 열람 범위를 공통 대화 서비스에서 검사한다. 파일 UUID·작성자 역할 주장·업로드 소유권만으로 연결된 파일을 열지 못한다.

하나의 업로드는 대화 메시지, 기록, 피드백 중 **하나의 원본**에만 연결된다. 같은 기록/피드백의 새 수정본은 기존 연결 파일을 재사용할 수 있지만 다른 메시지·기록·피드백으로 옮길 수 없다. 대화를 기록에 참고해도 첨부를 복사하거나 별도의 열람 권한을 자동 부여하지 않는다. 원문 링크로 확인한다. 실제 운영에서 파일 재사용·내보내기가 필요하면 별도의 명시적 정책과 서비스를 설계해야 한다.

담당 치료사 교체 시 `all` 범위의 새 치료사는 기존 기록 파일을 다음 수정본에 유지할 수 있다. `from_now` 범위는 옛 기록 ID를 사용해 파일을 직접 열 수 없게 한다. 대화 첨부의 열람 시점은 **메시지의 순번**으로, 기록 파일은 **기록 생성 경계**로 판단한다. 다른 참여자가 파일을 언제 임시 업로드했는지만으로 새 메시지를 숨기거나 옛 메시지를 공개하지 않는다.

## 내부 계약

입력의 `actor`는 인증된 서버 세션의 `{ centerId, userId }`여야 한다. 임의 HTTP 본문·헤더의 사용자 ID를 그대로 전달하면 안 된다. 다음은 내부 메서드이며 새로운 HTTP 경로가 아니다.

- `Conversations.sendText`의 `attachments?: [{ id }]`: 서버 발급 UUID만 받는다. 본문은 최대 2,000자이며 본문 또는 파일이 필요하다. 파일명·형식·용량·공유 여부를 요청에서 받지 않는다.
- `Records.save`의 `content.attachments?: [{ id, share? }]`: `share` 기본값은 false다. 저장은 부분 패치가 아닌 **전체 내용**이며 첨부를 생략/빈 목록으로 보내면 새 수정본에는 파일이 없다. 이전 수정본·공유본의 파일은 삭제하지 않는다. 빈 초안에는 파일을 넣을 수 있지만 파일만으로 정식 기록의 실제 작성 내용을 충족하지는 않는다.
- `ActivityFeedback.save`의 `content.attachments?: [{ id }]`: 기존 날짜·수행 상태·반응 등 내용 규칙을 유지하며 전체 목록을 새 수정본에 저장한다. 첨부를 제거한 수정본을 저장해도 과거 이력은 유지한다.
- 조회·미리보기·대화 카드는 DB의 불변 매니페스트에서 `{ id, name, type, size, share }`를 반환한다. 객체 경로·키·해시·검사 원문·작업 토큰·공개 URL은 반환하지 않는다.
- 기존 요청의 첨부 생략과 빈 배열은 같은 정규화 결과다. 예전 첨부 없는 요청 해시를 바꾸지 않으며 같은 ID 재시도는 중복 저장하지 않는다. 파일 선택/순서/공유 여부가 다른 요청은 다른 내용이다.

목록은 최대 6개·중복 불가·합계 100MiB다. 파일별 사진 10MiB, 영상 50MiB 제한은 업로드 매니페스트에서 유지한다. 서버 서비스와 DB 제약이 모두 묶음 제한을 검사한다. 최초 연결에는 같은 방에서 현재 작성자가 소유한, 유효 기간 내 `ready` 파일만 허용한다. 검사 대기·거부·취소·만료된 파일과 다른 방/작성자의 임시 파일은 연결하지 못한다.

### 연결된 파일 열기

`MediaAccess(database, privateStore).open(actor, input)`:

```js
// 메시지/공유 카드/현재 피드백 카드의 파일
{ conversationId, uploadId,
  source: { kind: 'message', messageId },
  range: { start, end } } // range 선택, 단일 바이트 범위

// 담당 치료사의 기록 수정본 파일
{ conversationId, uploadId,
  source: { kind: 'record', recordId, revision } } // revision 생략 시 현재
```

치료사만 피드백 메시지의 `source.feedbackRevision`으로 이전 수정본을 선택할 수 있다. 보호자에게는 이 매개변수를 허용하지 않는다. 메시지의 인용 대상은 그 답변 메시지에 파일 열람 권한을 자동 부여하지 않는다.

서비스는 요청한 원본/수정본의 실제 첨부 목록을 검사하고 저장 파일 전체 SHA-256을 재확인한다. 디스크 IO 이후 현재 관계·공유 철회·파일 상태를 다시 검사한 뒤 `{ stream, attachment, range, total }`을 반환한다. 재검사 실패 시 열린 핸들을 닫고 바이트 스트림을 반환하지 않는다. 이미 전달한 바이트나 다운로드를 회수할 수는 없으며, 스트림 반환 후 진행 중 권한 변경을 실시간으로 중단하는 기능도 없다.

`MediaUploads.open`은 연결 전 파일의 원 소유자 미리보기 전용이다. `bound` 파일에는 이를 사용할 수 없다. 반드시 위의 원본 기반 접근을 사용한다. HTTP 연결 단계에서는 세션·Origin/CSRF·요청/바이트 빈도 제한·취소/타임아웃, `private, no-store`, `nosniff`, 안전한 파일명 헤더와 로그 최소화를 구현해야 한다. 현재 다운로드 URL이나 공용 정적 파일 경로는 없다.

## 원자적 저장과 DB 보존

추가형 `009-media-bindings.sql`은 기존 001~008 SQL과 임상 내용·파일 바이트를 변경하지 않는다. 옛 메시지/피드백/공유본에는 비어 있고 확정된 첨부 목록을 부여한다. 알 수 없는 과거 파일 연결을 추측해 만들지 않는다.

- 파일 매니페스트에 단일 원본을 연결하고 `ready → bound`로 전환한다. 불변 매니페스트·검사 증명·활성 객체·내용 없는 상태 이력을 유지한다.
- 메시지/기록/피드백/공유본별 타입이 있는 첨부 테이블을 사용한다. 동일 센터·아동·원본·수정본 외래 키와 중복/순서 제약을 둔다.
- 공유 첨부의 외래 키는 **정확한 기록 수정본의 `share = true` 항목**을 요구한다. 서비스 로직을 우회해 비공유 파일이나 다른 버전의 파일을 공유 테이블에 넣어도 DB가 거부한다.
- 새 원본과 첨부 목록을 같은 트랜잭션에서 만든 뒤 목록을 확정한다. 커밋 이후 목록 삽입·수정·삭제를 막고 미확정 목록/실제 참조 없는 `bound` 행의 커밋도 거부한다.
- 원본 저장·공유 카드·첨부 연결·상태 이력·요청 영수증·감사 이벤트가 함께 커밋된다. 실패 시 파일은 이전 `ready` 상태로 돌아가며 기존 바이트를 유지해 동일 요청으로 다시 저장할 수 있다. 공유 실패 시 이전 공유본과 파일 접근도 유지된다.
- 연결 파일은 임시 영역의 24시간 만료/취소/정리 대상과 임시 할당량에서 제외한다. `MediaUploads.get`에서 `expiresAt: null`, `expired: false`로 표시하고 취소는 `FILE_IN_USE`로 거부한다. DB도 연결된 객체의 삭제 상태 전환을 막는다.

이 보존은 과거 기록을 임시 파일 정리가 실수로 지우지 않도록 하는 규칙이지 법적 보관 기간을 정한 것이 아니다. 연결 파일의 영구 삭제·센터 전체 할당량·메타데이터 최소화·백업 파기는 아직 구현하지 않았다. 정책 확정 전에 자동 파기를 추가하지 않는다.

## 변경 파일·검증

주요 변경은 `server/migrations/009-media-bindings.sql`, `server/media-bindings.mjs`, `server/media-access.mjs`, 기존 `media-uploads.mjs`, `conversations.mjs`, `records.mjs`, `activity-feedback.mjs`다. `server/tests/media-bindings.test.mjs`의 20개 시나리오와 기존 서버 테스트 7개 파일의 업그레이드/입력 검증을 갱신했다. 브라우저 UI·저장 키·기존 파일과 기존 인증 HTTP 경계는 바꾸지 않았다.

- `npm run test:server`: 122개(기존 102개 + 연결/접근 20개), 실패/취소/건너뜀 0.
- `npm test`: 기존 로컬 29개 통과.
- `npm run check`, `npm run build`, `git diff --check`: 통과.
- 직접 대화·기록 선택 공유·피드백 수정본의 실제 임시 파일 읽기, 범위 조회, 원 소유자 우회 차단, 센터/다른 방/관계 접근, 철회/재공유/독립 답변 보존, IO 후 재검사를 검증했다.
- 최대 6개·선택 순서·정확히 100MiB와 1바이트 초과, SQL의 합계 제한과 공유 부분집합 외래 키를 검증했다. 합계 용량 테스트는 **메타데이터 전용 가상 승인 fixture**를 사용하며 100MiB 실제 영상 쓰기·디코딩을 했다는 증거가 아니다.
- 원본/영수증 실패의 전체 롤백과 동일 요청 재시도, 만료된 미연결 파일의 연결 거부, 연결 파일 만료 제외, 과거 요청 해시/업로드 바이트·ID 보존, 009 재실행을 검증했다.

검증은 가상 데이터·인메모리 단일 연결 PGlite·임시 디스크다. 실제 PostgreSQL 다중 연결 경쟁/네트워크 장애, 실제 안티멀웨어·디코더, EXIF/GPS 제거·영상 메타데이터 정책, Windows ACL·암호화·운영 백업/복구, 국내 통제, 여러 기기 전송을 검증하지 않았다. 검사기는 테스트용이며 운영 기본값은 계속 **검사 대기**다. 실제 아동·건강 자료를 넣어도 된다고 판정하지 않는다.

위 122개/29개는 009 첨부 단계 당시 결과다. 이후 [기본정보·기존 계정 연결](profiles-provisioning.md)을 추가했다. 최신 전체 검증은 [서버 기반 문서](server-foundation.md)를 참고한다. 다음은 실제 파일 엔진/운영·보존 정책 준비이며 마지막에 API·화면 서버 연결·기기 간 전체 흐름을 검증한다. 개편안 전체/P1은 계속 진행 중이다.
