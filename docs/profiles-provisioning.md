# 아동·구성원 기본정보와 기존 계정의 센터 연결

2026-10-02. 소통 개편 P1의 서버 내부 기본정보·프로비저닝 단계다. 아동을 식별하고 참여자를 표시할 최소 정보와 기존 계정의 초대 수락을 구현했다. **현재 브라우저는 로컬 데모 저장소를 계속 사용한다.** API·화면 서버 연결·실제 메일·배포·유료 자원 생성은 하지 않았고 기존 기록/사진/영상/저장 키를 변경하지 않았다.

## 현재 구현과 정보 분리

| 정보 | 작성·조회 범위 | 수집·보존 원칙 |
| --- | --- | --- |
| 구성원 표시 이름 | 본인이 자기 센터의 이름을 설정/해제. 관리자는 해당 센터의 활성 구성원 목록을 조회. 아동의 현재 참여자끼리는 해당 방 참여자 이름만 조회 | 센터별 이름을 분리한다. 로그인 이메일·비밀번호·세션·다른 센터 소속은 명단에 없다. 표시명은 법적 신원 확인이나 권한이 아니다. |
| 아동 표시명·연령 | 센터 관리자가 등록/수정. 센터 또는 현재 담당 치료사/보호자만 조회 | 표시명 30자 이내. 연령은 선택이며 0~26 정수와 `ageAsOf` 기준일을 함께 저장한다. 미입력은 null, 실제 0은 0이다. 미래 기준일·없는 날짜는 거부한다. |
| 가족 관심사 | 연결된 보호자가 작성/수정/해제. 현재 보호자·담당 치료사만 조회 | 1,000자 이내의 현재 공동 관심사다. 센터의 아동 상세/목록에는 조회하거나 포함하지 않는다. 진단·자동 치료 계획·임상 기록으로 변환하지 않는다. |
| 변경 영수증 | 각 작업의 현재 권한을 확인한 뒤 재시도 처리 | ID·종류·요청 해시·처리 버전·변경 여부·시각만 남긴다. 이름·관심사 원문·이메일·토큰·비밀번호 사본은 없다. |

연령은 **입력한 기준일의 값**이다. 생년월일을 추측하거나 시간이 지났다는 이유로 자동 증가시키지 않는다. [로컬 아동 기본정보 편집](profile-ui.md)은 기준일을 함께 표시하며 실제 서버 연결은 남아 있다. 현재는 정확한 생년월일·주민번호·학교/학번·전화번호·진단·아바타 사진 등을 새로 수집하지 않는다.

프로필은 수정본 전체를 계속 보관하는 임상 기록과 달리 **현재값만** 저장한다. 표시 이름은 null, 가족 관심사는 빈 문자열로 해제할 수 있다. 원문 사본을 이력에 추가하지 않는다. 변경 요청 해시/식별자 역시 통제 대상이며, DB/백업의 보존·파기/암호화 정책은 별도로 남아 있다. 현재값 제거가 백업이나 이미 열람한 자료의 완전한 파기를 뜻하지 않는다.

기존 사용자/아동에 프로필이 없으면 이름·연령은 null, 버전은 0, 관심사는 빈 값이다. 이메일·ID·옛 자유 텍스트·데모 이름에서 프로필을 만들지 않는다. 기존 메시지의 작성자 ID와 아동/기록/첨부 연결도 바꾸지 않는다.

## 내부 기본정보 계약

`MemberProfiles`, `Children`의 actor는 인증된 서버 세션으로 확인한 `{ centerId, userId }`다. 브라우저가 제출한 사용자·역할을 신뢰하지 않는다. 센터별 현재 사용자·소속/역할·아동 참여 관계를 확인한다.

| 메서드 | 입력·동작 |
| --- | --- |
| `MemberProfiles.getSelf(actor)` | 본인의 해당 센터 표시명·현재 역할·버전·수정 시각. 인증 정보와 분리한다. |
| `saveSelf(actor, input)` | `clientId`, `expectedRevision`, `displayName`(1~30자 또는 null). 다른 사용자 ID/이메일/역할을 지정할 수 없다. |
| `listMembers(actor, input?)` | 관리자만 활성 사용자·소속의 ID/역할/표시명/버전/수정 시각을 조회. `after` 사용자 ID, `limit` 기본 50·최대 100. |
| `Children.register(actor, input)` | 관리자만 `childId`, `conversationId`, `clientId`, `content: { name, age?, ageAsOf? }`로 아동·아동별 방·운영 프로필을 함께 등록한다. |
| `get(actor, { conversationId })` | 센터 또는 현재 방 참여자가 운영 프로필과 활성 참여자 표시명을 조회한다. 보호자·치료사만 `familyPlan` 현재값/버전을 받는다. |
| `list(actor, input?)` | 관리자는 센터의 아동, 치료사/보호자는 현재 연결된 아동의 운영 프로필만 조회한다. `after` 아동 ID, `limit` 기본 50·최대 100. |
| `save(actor, input)` | 관리자만 `conversationId`, `clientId`, `expectedRevision`, `content` 전체를 저장한다. 연령/기준일 생략은 null로 변경한다. 가족 관심사를 함께 지정할 수 없다. |
| `saveFamilyPlan(actor, input)` | 현재 보호자만 `conversationId`, `clientId`, `expectedRevision`, `concern`을 저장한다. 빈 값으로 해제할 수 있다. 다른 보호자 수정도 현재 버전 확인이 필요하다. |

목록은 `{ members 또는 children, nextCursor, hasMore }`다. 전체 센터 구성원을 보호자에게 검색 가능하게 만들지 않는다. 아동 목록에는 가족 관심사가 없다. 값은 서버의 리터럴 문자열이며 화면 연결 때 반드시 기존 이스케이프 도우미로 렌더링해야 한다.

세 저장 대상의 버전은 각각 독립적이다. 이전 화면의 수정은 `PROFILE_CONFLICT`, 같은 요청 ID의 다른 내용/다른 대상은 `IDEMPOTENCY_CONFLICT`다. 변화 없는 저장은 버전을 올리지 않는다. 성공했던 요청을 재전송하면 당시 버전의 영수증만 반환하고 이후 현재값을 되돌리지 않는다. 최신 정보는 다시 조회한다. 재시도도 현재 권한을 통과해야 한다.

아동 표시명/연령·가족 관심사 변경은 대화 revision을 올려 예전 투영을 다시 조회하도록 한다. 구성원 이름은 별도의 센터별 프로필 버전을 제공한다. 이름 변경 시 모든 과거 메시지의 작성자 이름을 스냅샷으로 복사하거나 방을 전부 수정하지 않는다. API/캐시 연결 단계에서 참여자 프로필도 함께 다시 조회해야 한다.

새 아동 등록은 **계정/담당 관계/과거 열람 권한을 생성하지 않는다.** 이후 `Relationships.replace`로 활성 구성원과 `all / from_now` 범위를 명시적으로 연결한다. `from_now` 참여자에게 최신 공동 기본정보/가족 관심사는 보이지만 이전 대화·임상 원본·첨부 이력은 기존 열람 경계로 계속 차단된다. 가족 관심사의 이전 버전 조회 기능은 없다.

## 기존 계정의 센터 초대 수락

`Auth.acceptExistingInvitation(sessionValue, { token, centerId, role })`를 내부 메서드로 추가했다. **새 HTTP 경로는 없으며**, 마지막 API 단계에서 HttpOnly 쿠키의 세션 토큰을 전달해야 한다. 요청 본문/임의 헤더의 사용자 ID·이메일을 세션 대신 사용하면 안 된다.

수락 조건:

1. 대상이 명시적으로 확인한 센터·역할이 초대의 값과 같아야 한다. 초대 역할은 치료사/보호자만 허용한다.
2. 로그인 세션·사용자는 활성/유효해야 하고 계정의 실제 이메일이 초대 이메일과 같아야 한다. 초대 ID·이메일만 아는 것으로 연결할 수 없다.
3. 신규 수락에는 초대가 미수락·미철회·미만료여야 하고 발급자도 지금 해당 센터의 활성 관리자여야 한다. 이 발급자 재검증은 기존 새 계정 수락에도 적용했다.
4. 대상 센터의 소속이 없으면 초대 역할로 만든다. 같은 역할의 활성 소속이면 중복 없이 수락한다. 다른 역할이나 정지된 소속은 `INVITATION_MEMBERSHIP_UNAVAILABLE`로 거부하며 변경/복구하지 않는다.
5. 실제 수락 기록을 쓰는 시점에도 초대/세션의 만료 시각을 다시 확인한다. 잠금 대기 중 만료됐으면 소속 생성·수락·감사를 전부 롤백한다.

응답은 `{ user, invitation: { id, centerId, role }, linked: true, replayed }`다. `linked`는 **지금 활성 연결을 확인했다는 뜻**이지 새 소속 행을 매번 만들었다는 뜻이 아니다. 이메일·비밀번호 해시·내부 사용자 ID를 바꾸거나 세션 토큰을 반환/회전/연장하지 않는다. 다른 센터 소속도 유지한다. 새 계정용 `acceptInvitation`은 여전히 기존 계정을 덮어쓰지 않는다.

성공한 초대를 같은 인증된 계정이 다시 처리하면 현재 소속·세션을 확인한 뒤 재시도 결과를 반환한다. 이미 완료된 초대의 시간 만료는 이 읽기 전용 재시도를 막지 않지만, 철회·다른 계정·정지/역할 변경은 허용하지 않는다. 과거 요청을 재시도해 정지된 소속을 다시 만들지 않는다. 완료 재시도에는 초대 발급자의 현재 권한으로 새 권한을 부여하는 동작이 없다.

새 소속·초대 수락·내용 없는 인증 감사가 한 트랜잭션이다. 실패하면 모두 취소되고 같은 초대로 재시도할 수 있다. 계정 연결은 아동 대화 참여/기록/과거 열람을 자동 부여하지 않으므로 별도의 담당 관계 설정이 필요하다.

## 데이터 안전·잠금·마이그레이션

010은 추가형 마이그레이션이다. 기존 001~009를 바꾸지 않으며 기존 임상 내용/업로드/담당 관계·열람 순번은 보존한다. 새 프로필/영수증 테이블은 비어 있게 시작하고 원본 ID·버전 범위·연령/기준일 쌍·자기 프로필 주체·아동/방의 외래 키를 DB가 검사한다.

아동 등록은 기존 센터 일정 잠금부터 시작한다. 아동 조회/편집은 기존 `Relationships.inManagedRoom` 또는 `Conversations.inRoom`의 현재 역할·잠금·열람 검사를 재사용한다. 역할 분기 전 읽기는 권한을 부여하지 않고 보호된 서비스에서 다시 확인한다. 구성원 저장은 소속의 쓰기 잠금을 처음부터 확보해 존재하지 않는 프로필의 첫 저장도 직렬화하며 공유 잠금 두 개의 동시 승격을 피한다.

초대 수락은 초대 행을 잠근 뒤 계정→세션/사용자→대상 소속·발급자 권한 순서로 확인한다. 세션 조회 힌트만으로 권한을 부여하지 않으며 계정 잠금 뒤 실제 세션을 재검사한다. [비밀번호 변경 후속](password-change.md)에서 실제 PostgreSQL 두 연결의 변경/초대 수락 선후 경쟁·세션 폐기를 검증했다. 발급자/사용자 비활성화·관계 변경의 전체 경쟁·부하는 아직 별도 시험이 필요하다. 내부 SQL 유지보수는 같은 잠금 순서를 지켜야 한다.

## 변경 파일·검증과 남은 작업

이후 운영자 전용 [최초 새 센터 관리자 생성](center-bootstrap.md)을 추가했다. 기존 계정/센터를 덮어쓰거나 승격하지 않으며 이 문서의 기존 계정 초대 연결은 그대로 유지한다. 010 단계 결과와 최신 011 포함 전체 검증은 구분하며 최신 결과는 [서버 기반 문서](server-foundation.md)를 참고한다.

- `server/migrations/010-profiles.sql`: 센터별 구성원 표시명, 아동 운영 프로필/분리된 가족 관심사, 내용 없는 영수증과 DB 제약.
- `server/profiles.mjs`: 본인 표시명·관리자 명단, 아동 등록/조회/운영 편집·보호자 관심사·권한/버전/재시도.
- `server/auth.mjs`: 기존 계정 초대 수락, 현재 발급자 확인과 수락 시점 만료 재검사. 기존 인증 HTTP 경로는 바꾸지 않았다.
- `server/tests/profiles.test.mjs`: 12개 시나리오. 기존 데이터 보존·원문 비노출·새 아동 무권한·0/null·엄격 입력·권한 해제·실패 롤백·DB 제약.
- `server/tests/existing-accounts.test.mjs`: 9개 시나리오. 본인 세션/이메일·역할/센터·만료/철회·발급자 해제·정지 소속·재시도·처리 중 만료·실패 롤백.
- 기존 서버 테스트 8개: 010 업그레이드 목록 갱신. 기존 메시지/공유본/기록/첨부를 보존하는 검사는 유지한다.

최종 실행: `npm run test:server` 143개, `npm test` 29개, `npm run check`, `npm run build`, `git diff --check`. 모두 통과했다. 첫 기본정보 테스트의 실패는 동기 입력 거부를 비동기 거부 검증으로 감싼 테스트 호출 오류였으며 올바른 동기 예외 검사로 수정했다. 거부 규칙을 완화하지 않았다.

검증은 가상 데이터·단일 연결 인메모리 PGlite·기존 로컬 테스트다. 실제 운영 DB·아동/건강 자료·메일 발송·기기 간 연결을 사용하지 않았다. 이번에 화면을 변경하거나 개발 서버를 시작하지 않아 브라우저 검증은 재실행하지 않았다. 프로필 표시·초대 화면의 기존 계정 선택/확인·실제 메일·계정 복구·센터 최초 관리자 등록/소속 정지 해제의 운영 경로는 남아 있다.

이후 [기존 계정 선택·센터/역할 확인의 체험 화면](onboarding-ui.md#기존-계정-연결-화면-추가-2026-10-02)을 추가했다. 계정 선택은 가상 로그인 상태의 UX 검증이지 본인 인증이 아니다. 운영 연결 시 선택한 `accountId`를 본인 증명으로 보내지 않고 이 문서의 서버 세션 계약을 사용해야 한다. 체험 표시는 가상 이름이며 다른 센터의 표시명을 자동 반입하는 기능은 없다. 최신 로컬 36개·서버 207개·계정 브라우저 6묶음·레이아웃 179조건은 통과했지만 실제 인증/기기 연결·메일·복구·운영 준비는 여전히 남아 있다.

다음은 실제 검사/파일 저장 엔진과 메타데이터 처리·보존/파기 정책, 국내 인프라·메일·복구·백업/복원 준비다. 마지막에 API/화면 서버 연결과 기기 간 전체 흐름을 검증한다. 초대 수락만으로 운영 인증·국내 통제 또는 P1/전체 개편안이 완료된 것은 아니다. 실제 아동 자료는 아직 입력하지 않는다.

## 본인 표시 이름 로컬 설정 추가 2026-10-03

[구성원 UI 문서](member-profile-ui.md)에 가상 계정의 설정/해제·명단/대화 표시·기존 ID/원본·저장 실패/충돌 보호를 정리했다. 서버 `MemberProfiles.saveSelf`의 이름 검증은 공통 `src/profile-fields.js`를 재사용한다. 공백 정리 전에 제어문자를 거부하고 null만 명시적 해제로 처리한다. 인증된 주체·센터 소속·독립 버전·영수증·SQL·인증 HTTP 경로는 유지한다. 프로필 서버 파일은 아동 검증 12개에 구성원 공통 검증 1개를 더해 13개이며 전체 서버 208개·로컬 61개가 통과했다.

신규 표시 이름 브라우저 8묶음과 기존 7개 흐름·레이아웃 203조건을 통과했다. 실제 서버 표시 이름 변경/명단 갱신·인증·메일·기기 간 연결은 구현하지 않았다. 로컬 초대 시연의 새 계정에 아동 권한이나 지속 프로필을 자동 생성하지 않으며 운영 화면 연결은 기존 세션 계약을 따른다. 위 이전 단계의 결과는 당시 검증으로 유지한다.

## 아동 기본정보 로컬 편집 추가 2026-10-02

[로컬 기본정보 UI 문서](profile-ui.md)에 센터 편집·신규 등록·미입력/0·기준일·기존 데이터 호환과 최신 검증을 정리했다. `src/profile-fields.js`의 엄격한 내용 검증을 `server/profiles.mjs`에서도 재사용한다. 이름 앞뒤의 줄바꿈/탭 거부를 강화했으며 미래 날짜는 계속 DB 시계로 검사한다. 권한·영수증·독립 버전·SQL·HTTP 인증 경로는 유지한다. 서버 패키지에는 이 공통 모듈도 포함해야 한다.

로컬 44개·서버 207개, 기본정보 브라우저 6묶음·레이아웃 195조건과 기존 소통/기록/미디어/초대/관계 회귀는 통과했다. 서버 첫 실행의 재현되지 않은 프로세스 실패도 기본정보 UI 문서에 남겼다. 새 로컬 등록의 가상 치료사 선택과 서버 등록의 무담당 관계 계약은 다르며 운영 연결 때 별도 관계 확인이 필요하다. 로컬 데이터의 서버 자동 반입이나 실제 구성원 프로필 편집·인증·메일·기기 간 연결을 구현한 것은 아니다.
